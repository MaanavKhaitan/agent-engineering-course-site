Module 10 — Reliability, Cost & Performance

You have spent the last nine modules building an agent that works. This module is about making it work in production, at scale, without bankrupting you — which is a different problem. The good news: it is your problem. Reliability and cost for agents are not model problems or prompt problems. They are harness problems — retries, backoff, fallbacks, caching tiers, model routing, verification gates. This is systems engineering, and you already know how to do it. We are just going to point your SRE and cost-control instincts at a new substrate.

The mental shift to make up front: a model call is an unreliable network dependency with metered, non-trivial cost and high, variable latency. You have built reliable systems on top of flaky networks before. You have done tiered storage to manage cost, and cache hierarchies to manage latency. Every technique in this module is one of those moves, re-aimed at the loop you built in Modules 2–6.

Learning objectives

By the end of this module you will be able to:

  • Reason about agent reliability as a compounding-failure problem, and engineer “detect cheaply, recover locally” into the loop.
  • Apply typed error handling, backoff, fallbacks, schema-validation-and-retry, and forced verification — and know which the SDK already does for you.
  • Explain the quadratic-transcript cost problem and why prompt caching is what makes agentic loops economically viable at all.
  • Place cache breakpoints correctly, verify hits, and hunt down silent cache invalidators.
  • Route subtasks to the cheapest sufficient model, and reach for batch, max-token discipline, and task budgets as cost levers.
  • Cut latency with streaming, parallel tool calls, and model choice — while navigating the reliability/cost/latency triangle.

1. The core posture: every step can be wrong

Suppose a single agent step is 95% reliable — it picks the right tool, with the right arguments, and interprets the result correctly 19 times out of 20. That sounds fine. Now run a task that takes 100 steps. If errors are independent and unrecoverable, your success probability is 0.95^100 ≈ 0.6%. The agent essentially never finishes.

This is the same arithmetic as a distributed request that fans out across 100 services with no retries: per-hop reliability has to be absurdly high, or the system has to tolerate and recover from per-hop failure. You do not get the agent to 99.99% per step. You make per-step failure cheap to detect and cheap to recover from, so the recovered per-step reliability approaches 1, and the product over 100 steps stays high.

🛠️ Reframe: “the model was wrong” is not an incident, it is the expected case — the same way a TCP retransmit is not an incident. Your job is to build the loop so that a wrong step produces an observation the agent can act on, not a silent corruption that compounds. The cheapest recovery mechanism is the one already built into the loop from Module 3: errors become tool results, and the model takes another step. Everything below is elaboration on that.

✅ The reliability question is never “is the model good enough?” It is “when the model is wrong, does my harness notice, and can it recover before the error propagates?”

2. Reliability mechanics

(a) Retries, backoff, and typed errors

The Anthropic SDK already retries transient failures for you. By default max_retries=2, with exponential backoff, covering connection errors, 408/409, 429, and ≥500. So the network-flake layer is mostly handled:

import anthropic

# Bump retries for a flaky-network or high-contention deployment.
client = anthropic.Anthropic(max_retries=4)

# Or per-call, without mutating the client:
resp = client.with_options(max_retries=6).messages.create(...)

When do you add your own retry logic on top? When you need behavior the SDK doesn’t give you: honoring a retry-after header explicitly, a longer backoff ceiling, jitter tuned to your traffic, or a circuit breaker (below). Catch typed exceptions, most-specific first — string-matching error messages is the agent-era equivalent of parsing errno out of a log line:

import anthropic

try:
    resp = client.messages.create(...)
except anthropic.RateLimitError as e:
    # 429 — back off; the SDK already retried max_retries times before raising.
    retry_after = int(e.response.headers.get("retry-after", "30"))
    ...
except anthropic.APIStatusError as e:
    if e.status_code >= 500:
        ...  # transient; safe to retry
    else:
        raise  # 4xx is a bug in your request — retrying won't help
except anthropic.APIConnectionError:
    ...  # network failure before any response

⚠️ Idempotency is the retry trap that bites agents specifically. The SDK retries the model call safely — it produces no side effects. But your tool execution is a different story. If a tool call is POST /charge_card and you retry the whole step after a timeout, you can double-charge. This is exactly the at-least-once-delivery problem from message queues. The fix is the same: make side-effecting tools idempotent (idempotency keys, dedup tables) or gate them so a retry of the loop step does not re-execute a completed side effect. Read-only tools (grep, search) are free to retry; mutating tools are not.

(b) Fallbacks — degrade, don’t fail

When a model is overloaded (529) or declines a request, you want to fall through to an alternative rather than fail the task. The cleanest version of this for the refusal case is the server-side fallbacks parameter (currently on Fable 5), but the general pattern — try model A, on a specific failure class retry on model B — is something you can build for any model:

MODELS = ["claude-opus-4-8", "claude-sonnet-4-6"]

def call_with_model_fallback(messages, **kw):
    last = None
    for model in MODELS:
        try:
            return client.messages.create(model=model, messages=messages, **kw)
        except anthropic.APIStatusError as e:
            if e.status_code == 529:   # overloaded — try the next model
                last = e
                continue
            raise
    raise last

✅ Fallback is graceful degradation. A slightly cheaper or less-loaded model finishing the task beats the best model returning a 529. Pick the failure classes you fall through on deliberately — overload, yes; a 400 bad-request, no (that’s a bug, and the fallback model will reject it too).

(c) Schema validation and retry at the boundary

When a tool’s arguments or the model’s final output must conform to a schema, validate at the boundary and feed failures back. Two layers:

  1. Constrained decoding removes a whole class of malformed-output errors before they happen — strict: True on a tool definition, or client.messages.parse(..., output_format=Model) with a Pydantic model. The model is constrained to emit schema-valid JSON.
  2. Validate-and-retry catches what slips through (semantic errors constrained decoding can’t prevent — a date in the wrong range, a referenced ID that doesn’t exist).
from pydantic import BaseModel, ValidationError

class Booking(BaseModel):
    destination: str
    passengers: int

def parse_booking(messages):
    for attempt in range(3):
        resp = client.messages.parse(
            model="claude-opus-4-8", max_tokens=1024,
            messages=messages, output_format=Booking,
        )
        try:
            return resp.parsed_output           # validated Booking instance
        except ValidationError as e:
            # Errors-as-feedback: hand the failure back and let the model fix it.
            messages += [
                {"role": "assistant", "content": resp.content},
                {"role": "user", "content": f"That failed validation: {e}. Fix it."},
            ]
    raise RuntimeError("model could not produce a valid Booking")

(d) Forced verification — don’t trust “done”

The single highest-leverage reliability move for a coding or task-completing agent: do not trust the model’s claim that it finished. The model says “I’ve fixed the bug and all tests pass.” Run the tests. If they fail, that failure goes back into the loop as a tool result and the agent keeps going.

def run_until_verified(agent_loop, verify, max_rounds=5):
    for _ in range(max_rounds):
        agent_loop.run_until_model_claims_done()
        result = verify()                      # e.g. subprocess: pytest / build / lint
        if result.ok:
            return True
        agent_loop.add_tool_result(            # errors-as-feedback again
            f"Verification failed:\n{result.output}\nFix it and continue."
        )
    return False

📖 This is the evaluator-optimizer pattern from Module 6 collapsed into the loop, and it leans on the evals from Module 8 as the verification oracle. The model is the optimizer; your test suite / linter / type checker is the evaluator. Forced verification is what turns a 95%-per-step agent that claims success into one that demonstrates it — and it is pure harness code.

(e) Errors-as-feedback (the through-line)

Notice that (c) and (d) and the recovery story in §1 are all the same move: a failure is not an exception that aborts the run, it is an observation appended to the transcript. This is the Module 3 insight applied as a reliability strategy. An agent that sees its own failures self-corrects; an agent whose failures are swallowed flails or stops.

(f) Checkpointing and resume

For long runs (the overnight coding agent, the multi-hour research task), a crash at step 80 should not throw away 79 steps of work. Persist the transcript and tool-side state at intervals so you can resume. This is forward-referenced in Module 12 (durable execution); for now, treat it as: the conversation history is your checkpoint — serialize it.

(g) Timeouts and circuit breakers

Put a timeout on every tool call — a bash command that hangs should not wedge the whole agent. And if a downstream dependency (a flaky internal API a tool wraps) starts failing en masse, a circuit breaker that fails fast for 30 seconds beats hammering it with retries. Both are standard SRE patterns; they apply unchanged.

3. Cost engineering — the big one

The quadratic-transcript problem

Here is the cost fact that governs everything. The API is stateless: every step, you resend the entire growing transcript. Step 1 sends a small prompt. Step 50 sends the system prompt + tools + 49 turns of history + 49 sets of tool results. If the transcript grows roughly linearly with step count, and you resend it every step, your cumulative input-token cost over an n-step task is the sum 1 + 2 + ... + n ≈ n²/2. Token cost grows quadratically in the length of the task.

📖 Module 4 taught you to manage the context window (compaction, truncation) so it fits and stays relevant. That is the same growth curve, viewed from the cost side: the reason a long agent run gets expensive is this quadratic resend, and the reason it is bearable is the next section.

Prompt caching — what makes agents viable

Prompt caching turns that quadratic curve into something affordable. The mechanism: the API caches a prefix of your rendered prompt. On the next request, if the prefix matches byte-for-byte, those tokens are served from cache at ~0.1× the input price instead of full price. The cache write costs ~1.25× (5-minute TTL) or ~2× (1-hour TTL), so break-even is ~2 requests for the 5-minute TTL — trivially met inside any agent loop, which resends the same prefix every single step.

Mark the stable prefix with cache_control:

resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=4096,
    system=[{
        "type": "text",
        "text": LARGE_STABLE_SYSTEM_PROMPT,
        "cache_control": {"type": "ephemeral"},   # cache tools + system
    }],
    tools=TOOLS,                                  # tools render before system
    messages=conversation,                        # volatile, at the end
)

The one invariant that matters: caching is a prefix match, and any byte change anywhere in the prefix invalidates everything after it. Render order is tools → system → messages. This imposes an architectural constraint on how you build prompts:

  • Keep tools and the system prompt frozen. Sort tool definitions deterministically. Do not interpolate datetime.now(), a request UUID, or the current question into the system prompt header — that moves the volatile byte to the front of the prefix and nothing downstream caches.
  • Put volatile content at the END, after the last cache breakpoint — the per-turn question, timestamps, IDs.
  • For a growing multi-turn loop, put a breakpoint on the last block of the most recent turn; each step reuses the entire prior conversation as a cached prefix.

Verify it. Do not assume it.

u = resp.usage
print(u.cache_read_input_tokens)      # > 0 means you got a hit
print(u.cache_creation_input_tokens)  # tokens written to cache this request
print(u.input_tokens)                 # full-price, uncached remainder

If cache_read_input_tokens stays at 0 across requests with what you think is an identical prefix, a silent invalidator is at work. The usual suspects:

Silent invalidator Why it kills the cache
datetime.now() in the system prompt Prefix changes every request
uuid4() / request ID early in content Same
json.dumps(d) without sort_keys=True Key order varies → bytes differ
Tools built per-user or reordered Tools render at position 0 — nothing caches across users
Conditional system sections (if flag: system += ...) Every flag combo is a distinct prefix

These are insidious because nothing errors — your agent works perfectly, and your bill is silently 5–10× what it should be.

Worked example. A 10-step task. Suppose the cached prefix (tools + system + accumulating history) averages 20K tokens across the run, and each step adds ~2K of fresh tokens. On Opus 4.8 ($5 / MTok input):

  • Without caching: every step pays full price on the whole prefix. Cumulative input ≈ Σ (prefix at step i). With the prefix growing from ~20K to ~40K over 10 steps, that’s roughly 300K input tokens × $5/MTok ≈ $1.50 just in input, per task.
  • With caching: the stable prefix is served at ~0.1× after the first write. The same 300K tokens, with ~90% served from cache, costs roughly 30K × $5/MTok + 270K × $0.50/MTok ≈ $0.15 + $0.135 ≈ $0.29.

A ~5× reduction, and the savings grow with task length because the quadratic part is exactly the part that caches. This is not an optimization you bolt on later — it is the thing that moves an agentic loop from “economically absurd” to “ships.”

Model tiering and routing — the single biggest lever

Routing each subtask to the cheapest model that can do it is the largest cost lever you have. The tiers (input/output per MTok):

Model Price Use for
claude-haiku-4-5 $1 / $5 classification, routing, summarization, search sub-agents, commit messages
claude-sonnet-4-6 $3 / $15 most work
claude-opus-4-8 $5 / $25 the hard main loop, deep reasoning
claude-fable-5 $10 / $50 the hardest long-horizon reasoning

The architecture: a cheap classifier (Haiku) routes each incoming task, and cheap models handle the supporting work (compaction, search sub-agents, routing itself) while the frontier model runs only the hard core loop.

def route(task: str) -> str:
    """Haiku decides difficulty; the answer picks the worker model."""
    resp = client.messages.create(
        model="claude-haiku-4-5", max_tokens=16,
        messages=[{"role": "user",
                   "content": f"Reply with exactly SIMPLE or HARD.\n\nTask: {task}"}],
    )
    verdict = next(b.text for b in resp.content if b.type == "text").strip()
    return "claude-haiku-4-5" if verdict == "SIMPLE" else "claude-opus-4-8"

model = route(incoming_task)            # ~$0.0001 to decide
resp = client.messages.create(model=model, messages=[...], max_tokens=4096)

The routing call costs a fraction of a cent and can move a large slice of your traffic from $5/MTok to $1/MTok. ⚠️ One caching caveat: switching models mid-conversation invalidates the cache (caches are model-scoped). So tier at task boundaries, or run the cheap work in a sub-agent with its own context (Module 6) rather than swapping the model inside the main loop.

Other levers

  • Batch API — for anything not latency-sensitive (evals, bulk classification, offline processing), client.messages.batches.* runs at ~50% cost. Submit, poll, collect by custom_id.
  • max_tokens discipline — max_tokens is a hard ceiling, and you pay for what’s generated. A classifier doesn’t need max_tokens=4096; give it 16. Lowballing the main loop, though, truncates work mid-thought and forces a retry — so size it to the job.
  • Task budgets (beta, current Opus/Fable) — output_config={"task_budget": {"type": "tokens", "total": N}} tells the model a token budget for the whole agentic loop so it self-paces and wraps up gracefully. Distinct from max_tokens (an enforced per-response ceiling the model never sees); the task budget is a countdown the model is aware of.
  • Truncate tool outputs (Module 4) — a 50K-line log dumped into the transcript is paid for on every subsequent step (quadratically). Truncate or summarize before it enters context.
  • Turn off thinking/effort where you don’t need it — a routing or classification call doesn’t need extended reasoning. Lower effort = fewer tokens.

Know your unit economics

✅ The metric that matters is cost per task, and for a long-running agent your gross margin is downstream of harness design — caching, tiering, and context management together. The demo math and the production math are different planets: $0.15/task feels free in a demo. At 500K requests/day that is $75,000/day — $27M/year — and a silent cache invalidator that doubles it to $0.30/task is a $27M/year regression that throws no errors and breaks no tests. Instrument cost per task (Module 9), watch it, and treat a regression in it like any other production regression.

4. Performance and latency

Cost and reliability are about whether and how much; latency is about how it feels and whether the request even completes.

  • Streaming — with client.messages.stream(...) as stream: ...; stream.get_final_message(). Two wins: time-to-first-token drops (the user sees progress), and you avoid HTTP timeouts on long or high-max_tokens calls (the SDK refuses large non-streaming requests for exactly this reason). For any long generation, stream.
  • Parallel tool calls (Module 2) — when the model emits multiple tool_use blocks in one turn, execute them concurrently and return all results in a single user message. Three sequential 200ms tool calls become one 200ms round.
  • Parallel sub-agents (Module 6) — fan independent workstreams out across sub-agents instead of running them serially in one context.
  • Caching cuts TTFT — a cache hit isn’t only cheaper, it’s faster: the prefill on cached tokens is much quicker, so latency drops alongside cost.
  • Model choice — Haiku is materially faster than Opus. For latency-sensitive subtasks, the cheap model is often also the right model on speed grounds alone.
  • Prefetching / speculative work — if you can guess the next tool the agent will need, start it early. (Module 4’s cache pre-warming is the same idea applied to the prompt prefix.)

⚠️ The triangle. You are always navigating latency vs quality vs cost, and you cannot max all three. Higher k (more samples), more verification rounds, a bigger model, deeper thinking — all buy quality at the price of latency and dollars. There is no free corner; there is only the trade-off that fits this workload. A user-facing chat turn weights latency heavily; an overnight batch refactor weights quality and ignores latency. Make the trade explicitly, per workload, not by accident.

5. Putting it together — the production checklist

A production agent should have answers to all of these:

  • Typed exception handling, most-specific-first; SDK max_retries tuned for your environment.
  • Idempotency for every side-effecting tool (so a retried step doesn’t double-execute).
  • Model fallback on overload (529) → graceful degradation.
  • Schema validation at boundaries (strict/Pydantic), with validate-and-retry feeding errors back.
  • Forced verification after task-completing work (tests/build/lint) — never trust “done.”
  • Errors-as-feedback wired through the loop, not swallowed.
  • Checkpoint/resume for long runs.
  • Timeouts on every tool call; circuit breakers on flaky downstreams.
  • Prompt caching on a stable tools+system prefix; volatile content at the end; cache_read_input_tokens verified > 0.
  • No silent invalidators (audit for datetime.now(), unsorted JSON, per-user tools).
  • Model routing — cheapest sufficient model per subtask.
  • Batch API for non-latency-sensitive work; max_tokens and task budgets disciplined.
  • Streaming on long generations.
  • Cost-per-task and p95 latency instrumented (Module 9) and alerted on.

Real production issues

  • The demo-to-prod cost cliff. $0.15/task is invisible in a demo and $27M/year at 500K req/day. The number that was fine on day one is the number that defines your margin at scale. Instrument cost per task before you scale, not after the bill arrives.
  • Cache misses from silent invalidators. A datetime.now() someone added to the system prompt header, an unsorted json.dumps, a tool list that got reordered — any of these silently drops your cache hit rate to zero and doubles the bill, with no error and no failing test. The only defense is monitoring cache_read_input_tokens.
  • Non-idempotent tool retries causing double side-effects. A timeout retries the step; the step had already sent the email / charged the card. At-least-once delivery, agent edition. Idempotency keys or completion gates.
  • Retry storms amplifying an overload. A 529 spike triggers everyone’s retries simultaneously, which deepens the overload — the classic thundering herd. Jittered backoff and circuit breakers, not naïve fixed-interval retries.
  • The model declaring success without verifying. “All tests pass!” — they don’t. Ships broken work straight to a user. Forced verification is the only reliable fix; you cannot prompt your way out of it.
  • Latency from serial tool chains and deep sub-agent trees. Five sequential tool calls that could have been parallel, or a four-level-deep sub-agent tree where each level blocks on the one below. Latency is additive down a serial chain; flatten and parallelize.
  • Token cost of verbose models and outputs. A model that narrates every action, or a tool that returns 50K lines of log, pays the quadratic tax on every subsequent step. Truncate outputs; tune effort and verbosity down where you can.
  • Pricing and rate limits changing under you. Prices and limits move; a model gets deprecated. Don’t hard-code economic assumptions deep in the code — centralize them so a price change is a one-line edit, and re-baseline cost after any model migration.
  • The reliability/cost/latency tension. Higher k and more verification make the agent more reliable and slower and pricier. There is no setting that is best on all three axes — only the one that fits the workload. Choose it deliberately.

The throughline: every one of these is a harness problem, not a model problem. A wrong step, a cache miss, a double side-effect, a retry storm, an unverified “done” — these are reliability and cost-engineering problems, and reliability and cost engineering is precisely the systems work this audience already does well. You are not learning a new discipline. You are pointing an old one at a new dependency.

(a) Add prompt caching. Mark Scout’s system prompt and tool definitions with cache_control. Audit the prefix for silent invalidators — if there’s an injected timestamp or request ID anywhere in the system prompt, move it to the end of the messages (or remove it). Then compute the cost of a 10-step task with vs without caching using the per-MTok prices above, and confirm your measured numbers roughly match.

(b) Add a model router. Write a Haiku-based classifier that labels each incoming task SIMPLE or HARD and sends SIMPLE tasks to claude-haiku-4-5, HARD ones to claude-opus-4-8. Run a batch of mixed tasks through it and measure the cost delta vs running everything on Opus.

(c) Add robust error handling. Wrap Scout’s model calls in typed-exception handling with backoff. Add schema-validation-and-retry on one structured tool (Pydantic + parse, feeding ValidationError back to the model). Add a model fallback from Opus to Sonnet on a 529.

(d) Add forced verification. After any task where Scout writes or edits a file, have it run a check (the test suite, or a linter). Scout may only declare the task done if the check passes; on failure, feed the output back and let it continue (cap the rounds so it can’t loop forever).
