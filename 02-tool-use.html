Module 02 — Tool Use / Function Calling

A language model is a function from text to text. Tool use is the protocol that lets that function ask the outside world for things — and it is the single capability that turns a chatbot into an agent. This module is about the wire format, the design discipline, and the failure modes.

Learning objectives

By the end of this module you will be able to:

  • Explain the core mechanic: the model emits a structured request to call a tool and stops; your harness executes and feeds the result back. The model proposes; the harness disposes.
  • Define a tool: name, description (documentation the model reads at runtime), and a JSON Schema input_schema.
  • Hand-trace one full request/response cycle and write out the exact message structures — the part everyone gets wrong.
  • Handle parallel tool calls, the tool_choice modes, error results, and strict schema validation.
  • Apply tool design heuristics: when bash beats a dedicated tool, when to promote an action, why softening a description fixes over-triggering.
  • Recognize the SDK tool runner as the “automatic loop” and know why we build it by hand in Module 03.

1. The conceptual unlock: a planner that outputs intents

Before tool use, an LLM could only produce prose. If you asked “what’s the weather in Paris?”, it would confabulate a plausible-sounding answer, because answering is the only thing it can do.

Modern models are post-trained on a different contract. When you include tool definitions in the request, the model learns it has a second option: instead of emitting prose, it can emit a structured block that says “call get_weather with {location: 'Paris'}” — and then stop generating. It does not call anything. It cannot call anything. It has no network stack, no filesystem, no clock. It emits an intent, structured as JSON, and halts.

Your code — the harness — receives that intent, executes the real function (hit a weather API, read a file, run a query), and sends the result back into the model’s context on the next request. The model reads the result and continues: maybe it answers, maybe it requests another tool.

        ┌──────────── model (planner) ────────────┐
        │  reads context, emits ONE of:            │
        │   • prose  (stop_reason "end_turn")      │
        │   • tool_use block(s) (stop "tool_use")  │
        └──────────────┬───────────────────────────┘
                       │ intent
                       ▼
        ┌──────────── harness (executor) ─────────┐
        │  validates args, runs the real function, │
        │  enforces permissions, logs, returns a   │
        │  tool_result back into the next request  │
        └──────────────────────────────────────────┘

This separation is the whole game. The model is a planner with good judgment about which action to take and what arguments to pass; it has zero authority to take the action. Every guardrail you will ever build — permission prompts, audit logs, human-in-the-loop approval, rate limits — lives in the gap between “model proposes” and “harness disposes.” A systems analogy: the model is userland issuing a syscall; the harness is the kernel that decides whether to honor it. The model can request unlink(); only the kernel deletes the file.

The API is stateless. The model has no memory of prior turns. “Context” is just the message history you resend on every request — including the tool_use blocks it emitted and the tool_results you fed back. Lose track of that history and the conversation falls apart. We exploit this statelessness heavily in Module 03 when we build the loop.

📖 The model emitting tool_use and stopping is reported as resp.stop_reason == "tool_use". Hold that fact; it’s the pivot of the entire control flow.

2. The anatomy of a tool

A tool definition has exactly three load-bearing fields:

get_weather = {
    "name": "get_weather",
    "description": "Get the current weather for a city. Call this whenever "
                   "the user asks about current conditions, temperature, or "
                   "whether to bring an umbrella.",
    "input_schema": {
        "type": "object",
        "properties": {
            "location": {
                "type": "string",
                "description": "City name, e.g. 'Paris' or 'San Francisco, CA'",
            },
            "unit": {
                "type": "string",
                "enum": ["celsius", "fahrenheit"],
                "description": "Temperature unit. Defaults to celsius.",
            },
        },
        "required": ["location"],
    },
}
Field Consumed by Why it matters
name model + your dispatch code The model uses it to refer to the tool; you switch on it to route execution. Use specific names (search_orders, not search).
description the model, at runtime This is documentation written for an unusual reader: the model decides whether and when to call based on these words. Description quality measurably changes behavior.
input_schema model + (optionally) a validator Standard JSON Schema. Tells the model the shape of the arguments. With strict it also constrains generation.

The mental reframe a systems engineer needs: you are writing an API whose primary consumer is a language model. Your description is not a code comment — it is the prompt fragment that drives a routing decision. enum constrains the model the way a typed parameter constrains a caller. required vs. optional is a real contract. Treat these fields with the same care you’d give a public API, because that is exactly what they are.

Here are two more, to show range:

read_file = {
    "name": "read_file",
    "description": "Read a UTF-8 text file from the local workspace and return "
                   "its contents. Use this before editing a file so you can see "
                   "the current contents. Returns an error if the path does not exist.",
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {"type": "string", "description": "Workspace-relative path, e.g. 'src/app.py'"},
        },
        "required": ["path"],
    },
}

web_search = {
    "name": "web_search",
    "description": "Search the web and return the top results (title, url, snippet). "
                   "Call this when the question depends on current information not in "
                   "the conversation — recent events, prices, or facts past your training cutoff.",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "Search query, phrased as you would type into a search engine."},
            "max_results": {"type": "integer", "description": "How many results to return. Default 5."},
        },
        "required": ["query"],
    },
}

Provider note. OpenAI calls this “function calling.” The shape is near-identical: a tools array of function definitions with a JSON Schema, tool_calls in the response, and role: "tool" messages carrying results. The concepts in this module transfer directly; only the field names differ.

3. The full request/response cycle for ONE tool call

This is the section everyone trips on. We will trace a single tool call end to end and print the actual message structures at each step. Pay attention to what gets appended to messages — that is the part that bites people.

Step 0 — set up 

import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-6"

tools = [get_weather]  # the definition from §2

messages = [
    {"role": "user", "content": "What's the weather in Paris right now?"}
]

Step 1 — send tools + messages; the model asks for a tool 

resp = client.messages.create(
    model=MODEL,
    max_tokens=1024,
    tools=tools,
    messages=messages,
)

print(resp.stop_reason)   # -> "tool_use"
print(resp.content)

resp.content is a list of content blocks, not a string. With tool use it typically looks like this (often a text block of preamble, then one or more tool_use blocks):

[
    TextBlock(type="text", text="Let me check the current weather in Paris."),
    ToolUseBlock(
        type="tool_use",
        id="toolu_01A2b3C4d5E6f7G8h9",   # block.id — you MUST echo this back
        name="get_weather",               # block.name
        input={"location": "Paris"},      # block.input — already parsed into a dict
    ),
]

Three things to internalize:

  • block.input is already a parsed dict. You do not json.loads it.
  • block.id is the correlation key. The tool_result you send back must reference this exact id, or the API rejects the request.
  • stop_reason == "tool_use" is your signal that the model wants something. If it were "end_turn", the model is done and resp.content is the final answer.

Step 2 — execute the tool in your harness 

def execute_get_weather(tool_input: dict) -> str:
    location = tool_input["location"]
    # ... real implementation: call a weather API ...
    return "18°C, partly cloudy, light wind from the west."

# Pull out the tool_use block and run it
tool_use = next(b for b in resp.content if b.type == "tool_use")
result_string = execute_get_weather(tool_use.input)

Step 3 — append the assistant turn, then a user turn carrying the result

This is the crux. You append two messages:

  1. The assistant’s full content — verbatim, including the tool_use block. (If you drop the tool_use block, the API sees a tool_result with nothing to correlate to and 400s.)
  2. A user message whose content is a list of tool_result blocks — one per tool_use, each tagged with the matching tool_use_id.
messages.append({"role": "assistant", "content": resp.content})   # echo the WHOLE content

messages.append({
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": tool_use.id,    # must match the block.id from step 1
            "content": result_string,
        }
    ],
})

The conversation now reads, in full:

[
    {"role": "user",      "content": "What's the weather in Paris right now?"},
    {"role": "assistant", "content": [TextBlock(...), ToolUseBlock(id="toolu_01A2...", ...)]},
    {"role": "user",      "content": [{"type": "tool_result", "tool_use_id": "toolu_01A2...", "content": "18°C, partly cloudy..."}]},
]

Note the structural surprise: tool results are sent with role: "user". The result is “input to the model” the same way the original question was, so it rides on the user turn — even though no human typed it. The assistant turn holds the request; the user turn holds the result.

Step 4 — call again; the model uses the result to answer 

resp2 = client.messages.create(
    model=MODEL,
    max_tokens=1024,
    tools=tools,        # keep passing tools — the model may want another one
    messages=messages,
)

print(resp2.stop_reason)   # -> "end_turn"
print(resp2.content[0].text)
# -> "It's currently 18°C and partly cloudy in Paris, with a light westerly wind."

stop_reason == "end_turn" means the model is finished. That is one complete cycle: send tools+messages → tool_use + stop “tool_use” → execute → append assistant content + tool_result → send again → end_turn.

In Module 03 you’ll wrap steps 1–4 in a while loop that keeps going until stop_reason == "end_turn". For now, trace this by hand until the message shapes are muscle memory.

4. Parallel tools, tool choice, errors, strict schemas

Parallel tool use

A single response can contain multiple tool_use blocks. If you ask “compare the weather in Paris and Tokyo,” the model may emit two get_weather calls at once. You execute all of them and return all results in ONE user message:

tool_uses = [b for b in resp.content if b.type == "tool_use"]

messages.append({"role": "assistant", "content": resp.content})

tool_results = []
for tu in tool_uses:
    result = dispatch(tu.name, tu.input)   # your router
    tool_results.append({
        "type": "tool_result",
        "tool_use_id": tu.id,
        "content": result,
    })

messages.append({"role": "user", "content": tool_results})   # ALL results, one message

⚠️ Returning one tool_result per user message — splitting them across turns — is a classic bug. It silently teaches the model to stop making parallel calls, and it can desync the correlation. One assistant turn of tool_use blocks maps to one user turn of tool_result blocks. You may set disable_parallel_tool_use: true (inside tool_choice) to force at most one tool per response.

Tool choice modes

tool_choice controls whether the model may or must call a tool:

tool_choice Meaning
{"type": "auto"} Default. Model decides: prose or tool.
{"type": "any"} Model must use some tool (no plain prose answer).
{"type": "tool", "name": "get_weather"} Force this specific tool.
{"type": "none"} Model may not use tools this turn.

any and tool are useful when you’re using the model purely as a structured-output engine (e.g. classification: force a submit_category tool with an enum). auto is right for genuine agents, where the model should judge when a tool is warranted.

Error results — let the model self-correct

When a tool fails, do not crash the loop. Return a tool_result with is_error: True and an informative message. The model reads the error and adapts — retries with different arguments, picks another approach, or asks the user.

try:
    result = execute_read_file(tu.input)
    tool_result = {"type": "tool_result", "tool_use_id": tu.id, "content": result}
except FileNotFoundError:
    tool_result = {
        "type": "tool_result",
        "tool_use_id": tu.id,
        "content": f"Error: no file at '{tu.input['path']}'. Use the list_files tool "
                   f"to see available paths, then retry.",
        "is_error": True,
    }

The message string is doing real work here. "Error: ENOENT" tells the model nothing actionable; the version above tells it what went wrong and what to try next. We return to this under Real production issues.

Strict tool use — guaranteed-valid arguments

By default the model usually produces schema-valid arguments, but “usually” isn’t “always.” Add "strict": True to a tool definition to guarantee the emitted input validates against your schema. Strict mode requires the schema to set additionalProperties: false and list required:

book_flight = {
    "name": "book_flight",
    "description": "Book a flight.",
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {
            "destination": {"type": "string"},
            "date": {"type": "string", "format": "date"},
            "passengers": {"type": "integer", "enum": [1, 2, 3, 4, 5, 6]},
        },
        "required": ["destination", "date", "passengers"],
        "additionalProperties": False,
    },
}

strict constrains generation so the arguments are well-formed. It does not validate semantics — destination: "Narnia" is schema-valid and the model can still pass nonsense. Treat strict as “the JSON will parse and match the shape,” not “the inputs are sensible.” Your harness still validates meaning.

5. Tool design heuristics

You are designing an API for an unusual consumer. The usual API-design instincts mostly apply, with a few twists.

Write prescriptive descriptions. State when to call, not just what the tool does. “Call this when the user asks about current prices or recent events” gives measurably better triggering than “Searches the web.” On recent models — which reach for tools more conservatively — the trigger condition in the description is the single biggest lever on call rate.

Return informative results. The result string re-enters the model’s context. A bare exit code or a 10,000-line dump are both bad: the first starves the model of information, the second floods it. Return what the model needs to make the next decision, and nothing more.

Make errors recoverable. Covered above — informative is_error messages turn a dead end into a self-correction.

Don’t ship too many tools. A large, overlapping tool surface confuses the model and inflates every request (each definition costs tokens — see below). Keep the set focused. If you have dozens of tools, that’s a later-module problem (tool search, MCP) — not something to brute-force into one request.

Bash vs. a dedicated tool — the central tradeoff. A bash tool gives the model enormous leverage: it can do almost anything with a shell command. But it hands your harness only an opaque command string — the same shape for every action. A dedicated tool (send_email, edit_file) gives the harness a typed, named, interceptable hook.

  bash (broad leverage) dedicated tool (typed/gateable)
Coverage almost any action one action
Harness sees opaque string structured args
Gate a risky action hard (parse the string) easy (it’s a named call)
Render in a UI no yes (custom widget)
Parallel-safety unknown declarable
Audit grep logs structured event

When to promote an action from bash to a dedicated tool. Promote when you need to:

  • Gate it — security boundary. Hard-to-reverse actions (sending a message, deleting data, hitting an external write API) are natural candidates for a confirmation gate. send_email is trivial to gate; bash -c "curl -X POST ..." is not.
  • Enforce an invariant — a dedicated edit tool can reject a write if the file changed since the model last read it. Bash can’t.
  • Render it — some actions deserve custom UI. Claude Code promotes “ask the user a question” to a tool so it can render a modal and block the loop until answered.
  • Schedule it — mark read-only tools (grep, glob) as parallel-safe so the harness can fan them out; bash can’t be assumed safe.

Rule of thumb: start with bash for breadth, promote to dedicated tools when you need to gate, render, audit, or parallelize. The permission engine that does the gating is Module 03’s permission_gate; the full security treatment (tool args are untrusted, results can carry injected instructions) is Module 11. Here we’re just establishing the shape of the decision.

6. The SDK tool runner — the automatic loop

The Anthropic SDK ships a “batteries-included” helper that runs the whole loop for you. You decorate a typed Python function; the SDK derives the schema from its signature and docstring, calls the model, executes the tool, feeds the result back, and repeats until done.

from anthropic import beta_tool
import anthropic

client = anthropic.Anthropic()

@beta_tool
def get_weather(location: str, unit: str = "celsius") -> str:
    """Get current weather for a city.

    Args:
        location: City name, e.g. 'Paris'.
        unit: Temperature unit, "celsius" or "fahrenheit".
    """
    return "18°C, partly cloudy"   # real impl here

runner = client.beta.messages.tool_runner(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    tools=[get_weather],
    messages=[{"role": "user", "content": "Weather in Paris?"}],
)

for message in runner:    # each iteration is one model turn; loop ends when done
    print(message)

No manual messages.append, no tool_use_id plumbing, no stop_reason check. The runner does it all.

So why does this course build the loop by hand in Module 03?

  • You learn the machine by building it. The runner hides exactly the mechanics — append-assistant-content, correlate-by-id, stop on end_turn — that you must understand to debug a real agent.
  • Real harnesses need the manual control. Production agents intercept every tool call to enforce permissions, log structured events, support human-in-the-loop approval, truncate oversized results, and stream UI updates. The runner’s convenience is precisely the seam where that control has to live. You can’t insert a permission gate into a loop you don’t own.

The runner is the right tool for a quick script. An agent platform owns its loop. Module 03 builds that loop; this module gave you the pieces it assembles.

7. Tools you don’t have to write

Two escape hatches worth knowing now, covered in depth later:

  • Server-side / built-in tools. Anthropic hosts some tools — web_search, code_execution, plus client-executed reference tools like bash and text_editor. Server-side tools run on Anthropic’s infrastructure: you declare them in tools and the results come back in the same response, with no client-side execution loop. They’re a fast way to add web search or a sandboxed Python environment without owning that infrastructure.
  • MCP (Model Context Protocol). A standard for exposing tools from external servers, so you can plug in a whole catalog of tools without writing each definition by hand. Forward reference: Modules 07 and 13.

You don’t need these to build Scout. But know they exist before you hand-write your fiftieth tool definition.

🛠️ Exercise: scout/tools.py — two real tools, one hand-traced cycle

You’re building toward Scout, the research agent of this course. Today: implement two real tools and drive one manual tool-use cycle — no loop yet. The goal is to see the message shapes and hand-trace the cycle once.

Part A — implement the tools

Create scout/tools.py:

# scout/tools.py
import os

WORKSPACE = os.path.abspath(os.path.dirname(__file__))

# ---- Tool 1: read_file --------------------------------------------------

def read_file(path: str) -> str:
    """Read a UTF-8 text file from the Scout workspace."""
    full = os.path.abspath(os.path.join(WORKSPACE, path))
    # Confine to the workspace — path is untrusted model output (Module 11).
    if not full.startswith(WORKSPACE + os.sep):
        raise ValueError(f"Path '{path}' escapes the workspace.")
    with open(full, "r", encoding="utf-8") as f:
        return f.read()

READ_FILE_TOOL = {
    "name": "read_file",
    "description": "Read a UTF-8 text file from the Scout workspace and return its "
                   "contents. Call this when you need the contents of a known file.",
    "input_schema": {
        "type": "object",
        "properties": {
            "path": {"type": "string", "description": "Workspace-relative path, e.g. 'notes.txt'"},
        },
        "required": ["path"],
    },
}

# ---- Tool 2: web_search (offline stub) ----------------------------------

# Keep it runnable offline: a canned index. Swap for the `requests` library
# against a real search API later — the tool's CONTRACT does not change.
_FAKE_INDEX = {
    "anthropic": "Anthropic is an AI safety company; it builds the Claude family of models.",
    "tool use": "Tool use lets a model emit a structured request to call a function and stop.",
}

def web_search(query: str, max_results: int = 3) -> str:
    q = query.lower()
    hits = [f"- {k}: {v}" for k, v in _FAKE_INDEX.items() if k in q or q in k]
    if not hits:
        return f"No results for '{query}'."
    return "\n".join(hits[:max_results])

WEB_SEARCH_TOOL = {
    "name": "web_search",
    "description": "Search the web and return short result snippets. Call this when "
                   "the question depends on information not already in the conversation.",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "Search query."},
            "max_results": {"type": "integer", "description": "Max results. Default 3."},
        },
        "required": ["query"],
    },
}

TOOLS = [READ_FILE_TOOL, WEB_SEARCH_TOOL]
DISPATCH = {"read_file": read_file, "web_search": web_search}

Part B — drive ONE manual cycle and print every message

Create scout/one_cycle.py:

# scout/one_cycle.py
import json
import anthropic
from tools import TOOLS, DISPATCH

client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-6"

messages = [{"role": "user", "content": "Search for what 'tool use' means and summarize it."}]

# --- request 1: model asks for a tool ---
resp = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
print("=== response 1 ===")
print("stop_reason:", resp.stop_reason)            # expect "tool_use"
for b in resp.content:
    print(" block:", b.type, getattr(b, "name", ""), getattr(b, "input", ""))

assert resp.stop_reason == "tool_use"
tool_use = next(b for b in resp.content if b.type == "tool_use")

# --- execute in the harness ---
result = DISPATCH[tool_use.name](**tool_use.input)
print("\n=== executed", tool_use.name, "->", repr(result), "===")

# --- append assistant content, then user tool_result ---
messages.append({"role": "assistant", "content": resp.content})
messages.append({
    "role": "user",
    "content": [{"type": "tool_result", "tool_use_id": tool_use.id, "content": result}],
})
print("\n=== messages now ===")
# resp.content holds SDK objects; serialize loosely just to eyeball the shape
print(json.dumps([{"role": m["role"]} for m in messages], indent=2))

# --- request 2: model uses the result to answer ---
resp2 = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
print("\n=== response 2 ===")
print("stop_reason:", resp2.stop_reason)           # expect "end_turn"
print(next(b.text for b in resp2.content if b.type == "text"))

Run it and confirm: response 1 stops on tool_use, you execute, response 2 stops on end_turn with a summary built from the tool result. You just hand-traced the cycle from §3.

Real production issues

  • Malformed / hallucinated arguments. The model can emit args that don’t match your schema, or invent a tool that doesn’t exist. Validate at the boundary: parse block.input against the schema, and on failure return an is_error tool_result describing the violation so the model retries. strict: True eliminates shape errors but not semantic ones (a valid-shaped destination: "Atlantis"). Never trust the args blindly.

  • Bare exit codes vs. informative errors. A tool that fails with "exit 1" gives the model nothing to act on; it will retry the same broken call or give up. A tool that returns "Error: column 'usr_id' does not exist. Did you mean 'user_id'? Available columns: ..." lets the model self-correct on the next turn. Recoverability is a property you design into the error string.

  • Description quality changes behavior, measurably. The description is a prompt fragment that drives a routing decision. Vague descriptions cause under-triggering (the model never calls a tool it should) and over-triggering (it calls one it shouldn’t). When you A/B a description, you are A/B-testing the agent’s behavior.

  • Over-triggering — and the right fix. If the model calls a tool too eagerly, the instinct is to add guardrails (“CRITICAL: only use this when absolutely necessary”). On modern models that usually makes it worse, because aggressive language over-steers. The fix is almost always to soften the description — remove “always,” “default to,” “if in doubt” — not to pile on rules. Dial the language down before reaching for a gate.

  • Tool-result size blows up context. A tool that returns a 50,000-line file or a giant JSON payload dumps all of it into the model’s context — slow, expensive, and often counterproductive. Truncate or summarize large results before returning them (head/tail, a summary, a “result too large; here’s the first N lines” note). Context-window management is Module 04; the seam is the tool_result content you control.

  • Tool args and results are untrusted. block.input is model output — treat it as you’d treat any untrusted input crossing a boundary (the read_file workspace check above is exactly this). Worse, a tool result can contain text that reads like instructions (“ignore your previous instructions and…”), and the model will see it as context. This is prompt injection across a tool boundary — the full treatment is Module 11. For now: confine file paths, allowlist shell commands, and never let a tool result silently grant authority.

  • Tool schemas cost tokens on every request. Because the API is stateless, every tool definition is resent — and counted — on every single call. A bloated tool surface is a recurring tax on latency and cost. Use count_tokens to measure it, and keep the tool set lean (forward ref: tool search / MCP for large catalogs in Modules 07/13).
