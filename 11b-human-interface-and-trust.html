Module 11B — The Human Interface: Steering, Escalation & Trust

Module 11 was about keeping the agent inside the fence — guardrails, sandboxing, the permission gate, human-in-the-loop as a security control. This module is about the other half of the same problem: an agent you cannot make perfectly reliable still has to be useful, and the only way it becomes useful is if a human is willing to hand it real work. That willingness is not a function of the model’s benchmark scores. It is a function of how the human and the agent talk to each other.

Here is the thesis, stated plainly and meant to be taken literally: for agents, the human-agent interface is the mechanism by which you manage the risk of mistakes and earn the trust to grant autonomy. UX is not the polish you add at the end. It is the load-bearing trust-and-control layer. The gap between an impressive demo and “I’ll let it touch production / talk to real customers / move money” is overwhelmingly interaction design and recoverability, not raw capability.

And the sharp version of the claim, the one worth internalizing: the reliability problem and the UX problem are two sides of the same coin. A perfectly reliable agent would need no steering, no escalation, no legibility surface, no undo — you’d fire it and forget it. Because no such agent exists, every gap in reliability has to be covered by an affordance at the human boundary. The interface is where you spend whatever reliability you couldn’t build. Designing that interface is engineering, not decoration, and it’s what this module teaches.

This is deliberately a module about the design and engineering of the human/agent boundary — not about visual design, color, or layout. Every surface here is something you build into Scout’s loop.

Learning objectives

By the end you will be able to:

  • Articulate why the human interface is a risk-management and trust mechanism, not a cosmetic layer, and connect it to the reliability problem.
  • Implement steering of a running agent: streaming output, cancellable tool execution, and queuing/injecting user messages at loop boundaries — without killing the run.
  • Treat escalation as a first-class design surface: design “ask” into the toolset and calibrate ask-rate by reversibility, blast radius, and confidence.
  • Build a legibility surface that lets a human understand a multi-hour run in seconds, and use it as a cheap drift-detector.
  • Reason about inspecting and correcting a live run — why true mid-run correction is a frontier problem, and why append-an-event is the clean approach (and how it collides with prompt caching’s append-only invariant).
  • Deepen the approval/confirmation gate into a real product surface: previews, blast-radius rendering, “always allow,” batching, plan mode, and graduated autonomy levels.
  • Recognize the production failure modes — the demo-to-trust gap, ask-rate miscalibration, illegible long runs, over-automation — and design against them.

1. Why the interface is the trust layer

Start from a fact you already accepted in Modules 08–11: agents fail. They hallucinate tool arguments, misread state, pursue the wrong sub-goal, and drift over long runs. You mitigate with evals, observability, guardrails — but you never reach zero. The residual risk is permanent.

A reliable system you can’t fully trust is useless; a trustworthy interface around an unreliable system is deployable. The difference is entirely in the affordances at the boundary:

  • If stopping the agent is one keystroke and instantly safe, a user will let it run on far riskier tasks than if stopping means killing a process and cleaning up a half-finished mess.
  • If every action shows a preview and a diff before it commits, a user will grant write access they’d never grant to an opaque black box.
  • If a mistake is one git revert away, the user’s downside is bounded, so they tolerate more autonomy.

None of those properties live in the model. They live in the harness — in the interface you build. This is why two products on the identical model can have wildly different adoption: the one with better steering, clearer approvals, and cheaper recovery gets trusted with real work, and the other stays a demo.

That is the whole game. Autonomy granted is a function of how cheap inspection is and how survivable mistakes are. Every section below is one lever on that function.

2. Steering a running agent

Classic chat is request/response: you send, the model answers, done. Agents break that model. A Scout run is not a turn — it’s a trajectory that can last minutes to hours across many tool calls. During that time the user is not absent; they’re watching, and they need to be able to interrupt, redirect, or answer a question mid-flight, without killing the run.

That requires four engineering primitives. These are not exotic — every serious agent platform exposes exactly them, which is the tell that they’re the real load-bearing set:

  1. Streaming output, token-by-token, while tools run. Use client.messages.stream(...) and surface text_stream as it arrives. Streaming is not a latency nicety here — it’s the observability channel for the human steerer. A silent agent is an un-steerable agent; you can only redirect what you can see.

  2. Cancellable / interruptible tool execution. When the user hits interrupt mid-bash, what happens to the half-finished command? You need a policy: kill the subprocess, mark the tool result as interrupted, and feed that back to the model so it knows the action didn’t complete. The agent’s belief and reality must stay consistent.

  3. Queuing user messages typed mid-turn, injected at the next loop boundary. The user types “actually, focus on the backend” while the agent is three tool calls deep. You don’t splice it into the current turn — you enqueue it and inject it as a new message at the next loop boundary, where the message list is in a clean, consistent state.

  4. A permission / confirmation gate (Modules 03/11) — the synchronous pause point. Deepened in §6.

Why is instant, safe interruption so disproportionately load-bearing? Because it inverts the user’s risk calculus. If stopping is one keystroke and reversible, the cost of letting the agent try something is small — worst case you stop it and undo. People grant far more autonomy when the exit is cheap. The interrupt button is, paradoxically, the feature that lets you remove yourself from the loop.

This connects forward to Module 12: streaming and interruptibility are exactly what durable execution makes robust. A run that can suspend/resume can also pause cleanly for a human and pick up where it left off.

Scout’s loop, made steerable

Scout’s loop (Module 03) is roughly: build messages → call the model → if tool calls, execute them → append results → repeat. The steering version threads a queue and an interrupt flag through it:

import queue, threading

class Steerable:
    """Steering state shared between the UI thread and the agent loop."""
    def __init__(self):
        self.inbox = queue.Queue()      # user messages typed mid-run
        self.interrupt = threading.Event()

    def submit(self, text: str):        # called from the UI / input thread
        self.inbox.put(text)

    def stop(self):                     # the one-keystroke interrupt
        self.interrupt.set()

def drain(steer: Steerable) -> list[dict]:
    """Pull any queued user messages; called at loop boundaries only."""
    msgs = []
    while not steer.inbox.empty():
        msgs.append({"role": "user", "content": steer.inbox.get()})
    return msgs

def run_loop(client, messages, tools, steer: Steerable):
    while True:
        # --- inject queued steering at the boundary, never mid-turn ---
        messages += drain(steer)

        # --- stream the assistant turn so the human can see + react ---
        with client.messages.stream(
            model="claude-opus-4-8", max_tokens=16000,
            tools=tools, messages=messages,
        ) as stream:
            for text in stream.text_stream:
                render(text)                      # the steering observability channel
                if steer.interrupt.is_set():
                    stream.close()                # stop generating immediately
                    break
            response = stream.get_final_message()

        if steer.interrupt.is_set():
            messages.append({"role": "user",
                             "content": "[interrupted by user — awaiting new direction]"})
            steer.interrupt.clear()
            continue                              # loop back; pick up queued redirect

        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            break

        # --- execute tools; honor interrupt between (and inside) calls ---
        results = []
        for tu in (b for b in response.content if b.type == "tool_use"):
            if steer.interrupt.is_set():
                results.append({"type": "tool_result", "tool_use_id": tu.id,
                                "content": "Skipped: run interrupted by user.",
                                "is_error": True})
                continue
            results.append(execute_tool(tu, steer))   # see cancellable bash below
        messages.append({"role": "user", "content": results})

The cancellable tool — what to do with a half-finished bash:

import subprocess

def execute_tool(tu, steer: Steerable):
    if tu.name == "bash":
        proc = subprocess.Popen(tu.input["command"], shell=True,
                                stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True)
        while proc.poll() is None:
            if steer.interrupt.is_set():
                proc.terminate()                  # kill the half-finished command
                return {"type": "tool_result", "tool_use_id": tu.id,
                        "content": "Command terminated mid-execution by user interrupt.",
                        "is_error": True}          # tell the model it did NOT complete
            time.sleep(0.05)
        out, _ = proc.communicate()
        return {"type": "tool_result", "tool_use_id": tu.id, "content": out}
    # ... other tools

The key discipline: steering enters the conversation only at loop boundaries, always as appended messages. We never reach in and rewrite the in-flight turn. §5 explains why this is the only clean way, and §6 of the prompt-caching story (Module 10) explains why the cache forces it.

3. Escalation as a first-class design surface

The defining question of an autonomous agent is: when does it ASK the human, and when does it just ACT? This is the calibration problem, and it is where most agent products live or die.

The clean way to implement “ask” is to make it a tool. Give Scout an ask_human (or request_approval) tool alongside bash and edit. Now asking is a normal action in the agent’s vocabulary — the model decides to call it, the loop blocks for a human answer, and the answer comes back as a tool result. This reframes the human’s role: they move from operator IN the loop (approving every step) to manager ON the exception path (available when the agent decides it needs them).

There are two ways to get the calibration wrong, and they fail in opposite directions:

  • Asks too much. You’ve quietly rebuilt the human-in-the-loop you were trying to remove. Every action becomes a confirmation prompt; the human becomes a clicking machine; alarm fatigue sets in and they start rubber-stamping without reading — which is worse than no gate, because now the gate gives false assurance.
  • Asks too little. The agent barrels ahead and commits a costly, possibly irreversible mistake while unattended — a DROP TABLE, an email to the wrong customer, a force-push. The whole point of escalation was to catch exactly this, and it didn’t.

The calibration axis is the reversibility / blast-radius / confidence triple — and reversibility is the same criterion from Module 11’s gating discussion, reused here as a design knob:

Signal Ask Act
Reversibility Hard/impossible to undo (delete, send, deploy, pay) Cheaply reversible (read, local edit, scratch file)
Blast radius Affects prod, real users, money, external parties Affects only the workspace / a sandbox
Confidence Model is uncertain or arguments are ambiguous Model is confident, action is well-specified

The escalation tool, with policy baked in:

ASK_HUMAN_TOOL = {
    "name": "ask_human",
    "description": (
        "Ask the supervising human a question and wait for their answer. "
        "Call this BEFORE any action that is hard to reverse, affects production "
        "or real users, or when you are uncertain how to proceed. Do NOT call it "
        "for reversible, low-blast-radius actions you can confidently take."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "question": {"type": "string"},
            "proposed_action": {"type": "string"},
            "reversible": {"type": "boolean",
                           "description": "Whether the proposed action can be cheaply undone."},
        },
        "required": ["question"],
    },
}

def handle_ask_human(tu, steer: Steerable):
    q = tu.input["question"]
    answer = prompt_human(q, proposed=tu.input.get("proposed_action"))   # blocks the loop
    return {"type": "tool_result", "tool_use_id": tu.id, "content": answer}

Then enforce the policy in the harness too — don’t trust the model to self-gate. Classify each outgoing action by reversibility (the Module 11 classification) and force an approval for the irreversible ones regardless of whether the model asked:

def gate(tu) -> bool:
    """Return True if this action must be approved by a human before executing."""
    if tu.name == "bash":
        cmd = tu.input["command"]
        if any(p in cmd for p in ("rm -rf", "git push", "DROP", "curl -X POST", "kubectl delete")):
            return True               # irreversible / high blast radius → always ask
    if tu.name in ("send_email", "deploy"):
        return True
    return False                      # reversible, low blast radius → act

The art is tuning the ask-rate. Run Scout on a handful of representative tasks, log every ask_human call and every harness-forced gate, and look at the rate. Too high → loosen the descriptions and the gate predicates. Too low and you saw a near-miss → tighten them. This is an eval-able property (Module 08): you can build a small suite of tasks with known “should-ask” / “should-act” labels and measure precision/recall on the escalation decision, exactly like any other classifier.

🛠️ Exercise (escalation): Add ask_human to Scout with the policy above. Run it on three tasks of varying risk. Record the ask-rate. Deliberately mis-tune it once in each direction and feel the failure: an over-asking Scout is exhausting; an under-asking Scout does something you didn’t want.

✅ Self-check: Why enforce reversibility in the harness gate as well as in the tool description? (The description is a soft prompt the model may ignore or miscalibrate; the harness gate is a hard, non-bypassable control. Defense in depth — the same belt-and-suspenders logic as Module 11’s security gating.)

4. Making a long / autonomous run legible

You let Scout run overnight on a 6-hour task. In the morning, you have a 40,000-line transcript. The question that decides whether this product is usable is: can you understand what it did, and why, in seconds — or do you have to re-read the whole trace?

If the answer is “re-read the trace,” the product is dead on arrival for autonomous use. Nobody audits an overnight run line by line. So you must design legibility in — build a second, human-facing view of the run that is not the raw log.

The surfaces that matter:

  • A concise progress summary — where the run stands, what’s done, what’s left.
  • A “what I did and why” decision journal — the key decisions, each with the reasoning, not every tool call. “Chose to skip the staging deploy because the diff was config-only” is a journal entry; ls -la is not.
  • Surfaced uncertainty — the places the agent was unsure, made an assumption, or guessed. This is gold: it tells the human exactly where to look.

Why does this matter beyond convenience? Because a human glancing at a well-designed summary and going “wait, that’s not what I meant” is the cheapest drift-detector you have. It catches goal drift (Module 13 — agents wandering off-objective over long unsupervised runs) before any eval can, because the human has the actual intent in their head and the eval only has its proxy. Legibility is not a nicety; it’s an instrument — the human’s eyeball is a sensor, and the summary is what you connect it to.

Contrast sharply with the observability traces from Module 09. Those traces are for engineers debugging the agent — spans, token counts, tool latencies, full inputs/outputs. The legibility surface is for the supervising human steering the work — decisions and uncertainty, in their language, at their altitude. Same run, two completely different views, two different audiences. Don’t conflate them; a debugging trace shown as a “summary” is illegible, and a decision journal is useless for debugging a tool-call failure.

Implementation: give Scout a tool to write journal entries as it works, and synthesize a summary at the end. The journal entries cost a little context but buy you the entire legibility surface for free.

JOURNAL_TOOL = {
    "name": "log_decision",
    "description": (
        "Record a notable DECISION and the reasoning behind it, or an uncertainty/"
        "assumption you are making. Use this for choices a supervising human would "
        "want to review later — not for routine actions."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "decision": {"type": "string"},
            "why": {"type": "string"},
            "uncertain": {"type": "boolean"},
        },
        "required": ["decision", "why"],
    },
}

journal = []   # appended to by handle_log_decision(...)

def end_of_run_summary(client, messages, journal):
    """Synthesize the legibility surface — decisions + uncertainty, not raw logs."""
    resp = client.messages.create(
        model="claude-opus-4-8", max_tokens=1024,
        messages=messages + [{
            "role": "user",
            "content": (
                "Write a concise report for the human who left you running: "
                "(1) what you did, (2) why — the key decisions, "
                "(3) what you're UNSURE about or assumed. Decisions, not a log."
            ),
        }],
    )
    return {"summary": next(b.text for b in resp.content if b.type == "text"),
            "decision_journal": journal}

Then read only the summary and journal — not the transcript — and ask yourself whether you could catch a goal-drift mistake from them alone. ✅ Self-check: Why is the summary a better drift-detector than an eval? (The human holds the true intent; the eval holds a fixed proxy written in advance. The human catches “that’s not what I meant” — a divergence the eval’s proxy can’t represent because nobody anticipated it.)

5. Inspecting and correcting a live run

Steering at the boundary (§2) handles redirection. But two harder questions remain, and they’re where the frontier is.

INSPECT: can a human see a live run’s state? The honest answer is “not directly.” The agent’s durable state — its message list, scratch files, memory — is optimized for the next model call, not for a human to read. It’s a wall of tool-call JSON and intermediate reasoning. So inspection requires building a second, human-facing projection of that state: the same legibility surface from §4, but rendered live. You don’t show the human the raw state; you show them a view derived from it. This is exactly the read-model / write-model split from CQRS, applied to agents: the write model (durable state) serves the agent; the read model (projection) serves the human.

CORRECT: can a human fix a live run’s state mid-flight? This is genuinely hard, and most teams punt on it — for good reasons.

Editing a running agent’s state mid-flight is live surgery on a system that has beliefs about itself. If you reach in and change a fact the agent already “knows,” you create an inconsistency between what the agent believes (from earlier in its context) and what is now true. The agent’s later reasoning may still reference the old value; you get incoherence, not correction.

Worse, it collides head-on with prompt caching’s append-only / prefix-stable invariant (Module 10). Recall: caching is a prefix match — any byte change anywhere in the cached prefix invalidates everything after it. If you mutate message 5 of a 200-message run, you’ve (a) created the belief inconsistency above and (b) blown away the entire cache from message 5 onward, re-billing the whole tail at full price. The cache is structurally an append-only log; editing the past fights its deepest assumption.

So the clean approach is the same one §2 already used, and now you can see why it’s clean: steer by APPENDING an event/message, never by editing past state. Instead of rewriting “source senior candidates” to “source mid-level,” you append:

{"role": "user", "content": "Update: stop sourcing senior candidates. Pivot to mid-level. Ignore the earlier seniority instruction."}

The agent observes this at the next loop boundary, reconciles it against its prior context itself (it’s good at this — that’s what the model is for), and the cached prefix stays byte-stable, so the entire history before the new message is still a cache hit. Append-only steering is correct both as a state-consistency strategy and as a caching strategy. The two constraints point the same direction — which is a strong signal it’s the right design.

This append-an-instruction pattern is the same shape platforms standardize: an out-of-band “interrupt” or “user message” event that the orchestrator delivers at a safe boundary, leaving prior history intact. (Some setups even formalize a mid-conversation system message appended to the message list — an operator channel that preserves the cached prefix; see Module 10.)

True live correction — surgically rewriting the agent’s belief mid-turn so it’s instantly consistent and cache-friendly — has no clean general solution. Be honest about this with whoever you’re building for. The pragmatic workaround almost everyone ships: kill the run and restart from a corrected state file. Checkpoint the run (Module 12), let the human edit the checkpoint (which is at rest, so no in-flight inconsistency), and resume from the edited checkpoint. You’re not editing a live agent; you’re editing a paused one and starting fresh. It’s coarse, it’s correct, and it sidesteps both the consistency and the caching problems.

✅ Self-check: Why does appending an instruction preserve the cache while editing message 5 destroys it? (The cache key is the exact byte prefix. Appending leaves the entire prior prefix unchanged → full cache hit on the history. Editing message 5 changes a byte in the prefix → everything from message 5 onward is invalidated and re-billed.)

6. Approval & confirmation UX — deepening the gate

Module 03 gave you a yes/no permission gate; Module 11 gave you the security rationale. Here we treat the gate as what it actually is: a product surface, not an afterthought. A bad approval prompt either gets rubber-stamped (useless) or exhausts the user (abandoned). A good one makes the right decision cheap and obvious.

What a real approval prompt renders:

  • The action — what the agent wants to do, in plain language, not raw JSON.
  • A preview / diff of the change — for an edit, the unified diff; for a bash, the exact command; for an API call, the request. Seeing the change is the entire trust transaction. An approval without a preview is a blind signature.
  • The blast radius — what this touches. “Modifies 1 file in your workspace” vs. “Deletes 4 rows from the production users table.” This is the reversibility/blast-radius signal from §3, surfaced to the human at the decision point.
def render_approval(tu) -> str:
    if tu.name == "edit":
        return (f"EDIT  {tu.input['path']}\n"
                f"blast radius: 1 file (workspace, reversible via git)\n\n"
                f"{unified_diff(tu.input['path'], tu.input['new_text'])}")
    if tu.name == "bash":
        risky = gate(tu)
        return (f"BASH  {tu.input['command']}\n"
                f"blast radius: {'HIGH — irreversible / prod' if risky else 'low — workspace'}")
    return f"{tu.name}  {json.dumps(tu.input, indent=2)}"

Beyond the single prompt, the surfaces that reduce friction without reducing safety:

  • “Always allow X for this session.” After the user approves edit once, stop asking for edit this session. This directly fights alarm fatigue (§3). Scope it carefully — “always allow” should never silently cover the irreversible class.
  • Batching approvals. When the agent proposes five reversible edits, show them as one batch with five diffs and one approve button, not five sequential prompts. One decision, full visibility.
  • Plan mode / dry-run — the single highest-trust pattern. The agent proposes a complete step-by-step plan and waits for approval before executing anything. The human reviews the whole strategy up front, while it’s still free to change, rather than approving (or catching) actions one at a time after they’ve started. Plan mode front-loads the trust transaction to the cheapest possible moment.
  • Graduated autonomy levels — a user-facing dial. Expose the autonomy level as an explicit control the user sets per run:
Level Behavior
read-only Scout can read and analyze; every write/exec is gated.
auto-edit Reversible edits auto-apply; irreversible/external actions gated.
full-auto Everything runs; the human watches via the legibility surface and interrupts if needed.

The dial is the user’s primary lever for spending trust as they earn it. New task in an unfamiliar area → read-only. Routine task they’ve watched succeed ten times → full-auto. The same Scout, the same model — the human just chose how much rope to give it. (Plan mode and auto-accept levels are exactly the pattern shipped by coding agents like Claude Code and Cursor — strong evidence this is the standard, not a one-off.)

AUTO_ALLOW = {
    "read-only":  lambda tu: tu.name in ("read", "grep", "glob"),
    "auto-edit":  lambda tu: tu.name in ("read", "grep", "glob", "edit") and not gate(tu),
    "full-auto":  lambda tu: not gate(tu),     # gate() still stops the irreversible class
}

def needs_approval(tu, level: str) -> bool:
    return not AUTO_ALLOW[level](tu)

Notice gate() (the irreversible-class predicate from §3) is honored at every level including full-auto. The autonomy dial controls the reversible surface; the irreversible class is a hard floor. That’s the design rule: let the user dial up autonomy on what’s recoverable, never on what isn’t.

7. The audit / review surface — the performance review for your agent

Everything above is during the run. The audit surface is after: letting a human review what the agent decided and why, retrospectively. Think of it as the performance review for your agent.

This ties two earlier modules together into a flywheel:

  • It builds on the observability traces (Module 09) — the audit surface is a human-readable rendering of the trace, joined with the decision journal (§4).
  • It feeds evals (Module 08) — when a human reviews a run and finds a bad decision, that run becomes a new eval case. Human review of production runs is the single richest source of eval data you have. Review → find failure → add eval → fix → review again. The interface closes the loop.

And underpinning all of it: recoverability is part of the interface. The audit surface is only valuable if, having found a mistake, the human can undo it. So recoverability is a design requirement, not an afterthought:

  • Git for everything the agent touches — every edit is a commit, so every edit is one git revert away.
  • Dry-runs and previews (§6) — catch the mistake before it commits.
  • Confirmations on irreversible actions (§3) — the things git can’t undo (sent email, deployed code, charged card) get the hard gate.

The throughline of the whole module lands here: making mistakes survivable is what lets users grant autonomy. A user who knows any bad action is one revert away will let the agent run on far more, because their downside is bounded. Recoverability doesn’t reduce the rate of mistakes — that’s the reliability problem — it reduces their cost, which is the trust problem. Two sides of the same coin, again.

8. Adoption & trust dynamics in regulated / outward-facing domains

Sharpen the stakes. For an internal coding agent, a mistake costs some rework. For an outward-facing or regulated agent — recruiting, customer support, finance, healthcare — a wrong autonomous action is expensive and accountable: a discriminatory candidate rejection, a wrong financial figure quoted to a customer, a HIPAA-relevant disclosure. Here the model’s reliability is not the safety story, because you can never get it to zero and the cost of the residual is too high to eat.

The interface and recoverability are the safety mechanism. In these domains:

  • The escalation surface (§3) is where regulatory and policy judgment enters — anything with legal or financial consequence routes to a human by design, not by the model’s discretion.
  • The audit surface (§7) is the accountability record — who decided what, when, why, and who approved it. In a regulated domain this isn’t a nicety; it’s a compliance requirement.
  • Recoverability bounds the blast radius of the residual errors you can’t eliminate.

The autonomy a user (or an institution) grants is exactly the function we opened with: a function of how cheap inspection is and how survivable mistakes are. In a regulated domain both terms are scrutinized hard — inspection has to satisfy an auditor, and “survivable” has to satisfy a regulator. Which is precisely why, for these agents, the human-interface layer is the product, and the model is the commodity underneath it.

🛠️ Exercise: a human-interface layer for Scout

Real production issues

  • The demo-to-trust gap. The agent demos beautifully and then stalls the moment a human has to oversee it for real. The fix was never a better model — it’s steering, approval previews, legibility, and undo. Teams that treat UX as “later” ship demos, not products.
  • Ask-rate miscalibration → alarm fatigue. Too many confirmations and the human rubber-stamps blindly, which is worse than no gate because it manufactures false confidence. Too few and the agent commits an unattended irreversible mistake. Calibrate by reversibility/blast-radius; make the gate an eval-able classifier (§3).
  • Illegible long runs. You can’t tell what an overnight run did, so you can’t catch drift, so you can’t trust it overnight — a vicious circle. The decision journal + summary (§4) is the way out; the raw trace is not.
  • Can’t inspect or correct a live run. Durable state is built for the agent, not the human, and true mid-run correction has no clean solution. Ship the read-model projection for inspection and the kill-and-restart-from-checkpoint workaround for correction; don’t promise live surgery you can’t deliver.
  • Over-automation. Removing the human before the agent has earned the trust — defaulting to full-auto out of the gate. Earn autonomy with the dial; start gated, loosen as the human watches it succeed.
  • Steering that fights the cache. Implementing “correction” by editing past messages blows the prompt cache (Module 10) and creates belief inconsistency. Append events at boundaries; never rewrite history.
  • Regulated/outward-facing reality. For these agents the interface + recoverability are the safety mechanism, not model reliability — and the audit surface is a compliance artifact, not a convenience.

The thread that ties every one of these back to the thesis: each is a place where insufficient reliability had to be covered by interaction design, and the failure is what happens when the interface wasn’t there to catch it. The reliability problem and the UX problem are the same problem. You manage what you couldn’t make perfect by building the boundary where the human and the agent meet.

In Module 12 these surfaces stop being toy loop-hooks and become real infrastructure: streaming over SSE to a UI, durable suspend/resume that makes pause-for-approval natural (a run can wait days for a human and resume exactly where it left off), and checkpoints that make kill-and-restart-from-corrected-state a first-class operation rather than a hack.
