Module 07 — The Framework Landscape

You spent Modules 3 through 6 building Scout from nothing: a while loop that calls the model, a tool dispatcher, a context-management strategy, sub-agents. It works. It is maybe 400 lines. And it taught you the thing that matters most for this module — you now know, concretely, what an agent is underneath. A loop, a tool schema, a message list, a stop-reason check.

So when someone says “just use LangGraph” or “you should be on the OpenAI Agents SDK,” you are no longer in a position of taking it on faith. You can ask the only question that matters: what does this framework actually abstract, and is that abstraction worth the control I give up?

That is the entire frame for this module. We are not going to re-teach the loop — you built it. We are going to look at frameworks as packaging of the things you built, evaluate them on concrete axes, and develop an honest, opinionated decision procedure. Including the option you’ve already earned the right to choose: no framework at all.

One idea to carry through the whole module, because it sharpens every judgment you’ll make: every framework component encodes an assumption about what the model can’t do. A retry-with-reflection helper assumes the model won’t recover on its own. A rigid output-parsing layer assumes the model can’t be trusted to emit clean JSON. A verbose planning scaffold assumes the model won’t plan unprompted. Some of those assumptions were true in 2023 and are false now. As models improve, a fraction of every framework’s scaffolding quietly turns into dead weight — code that fights a model that no longer needs the help. Keep asking, for each abstraction: is this solving a real problem, or a problem the model already solved?

Learning objectives

By the end of this module you will be able to:

  • Articulate what a framework buys you over a hand-rolled loop, and what it costs in control, learning curve, and lock-in.
  • Evaluate any agent framework on a fixed set of axes (control-flow model, state/persistence, streaming, tool/MCP integration, multi-agent, observability, deployment, model-agnosticism, maturity).
  • Place LangGraph, the OpenAI Agents SDK, the Claude Agent SDK (+ Managed Agents), CrewAI, and Google ADK on those axes, and name the core abstraction and tradeoff of each.
  • Apply a decision procedure that maps your situation to a recommended choice — including “roll your own.”
  • Recognize the real production failure modes of frameworks: leaky abstractions, debugging through layers, version churn, and scaffolding rot.

What a framework actually gives you (and takes)

Start from what you have. Scout is an imperative loop. You call the model, you read stop_reason, you dispatch tools, you append results, you loop. You own every line. When something breaks you set a breakpoint and you are in the code that broke.

A framework offers a trade. In exchange for adopting its conventions and its abstraction, you get some subset of these for free:

  • Persistence and checkpointing — the loop’s state survives a process restart; you can resume, replay, or “time-travel” to a prior step.
  • Streaming plumbing — token and event streaming wired through the whole stack, not just the raw model call.
  • A tool/MCP integration layer — decorators or schema helpers that turn a function into a tool, plus a standard way to mount external tool servers.
  • Multi-agent primitives — first-class handoffs, sub-agents, or role-based crews instead of your hand-spawned sub-agent.
  • Observability hooks — traces, spans, and a UI to see what the agent did, usually paired with the vendor’s platform.
  • A deployment story — a blessed path from local loop to a running, scalable service.
  • An ecosystem — integrations, examples, a community that has already hit your bug.

And in exchange you pay:

  • Control. The loop is now theirs. When you want to do something the framework didn’t anticipate, you fight it.
  • A learning curve. Nodes, edges, state reducers, handoffs, crews — vocabulary you must learn before you’re productive.
  • Abstraction leak. The framework’s model of the world is not the model API’s model of the world, and at the seams that mismatch surfaces as confusing bugs.
  • Dependency and lock-in risk. Especially with the lab SDKs, you may be coupling your control flow to one model provider.

📖 The mature stance is not “frameworks bad” or “frameworks good.” It’s: understand the primitives — which you now do — so you can evaluate the trade on a per-axis basis. A framework that gives you durable checkpointing you genuinely need is a great deal. The same framework adopted for a single-turn classification task is pure overhead.

The axes

When you evaluate any framework — including ones invented after this module is written — score it on these:

Axis The question to ask
Control-flow model Imperative loop? Graph/state machine? Role-based crew? Handoff? How much determinism does it give you, and how much does it hide?
State / persistence / checkpointing Does it persist loop state? Can you resume after a crash? Replay? Time-travel?
Streaming Are model tokens and intermediate events streamable end-to-end?
Tool / MCP integration How do you define a tool? Does it speak MCP (Module 13) for interop?
Multi-agent Are sub-agents / handoffs / crews first-class, or do you build them?
Observability Built-in tracing? Tied to a specific platform (Module 9)?
Deployment Is there a blessed path to production (Module 12)? Durable execution?
Model-agnosticism vs. lock-in Can you swap the model provider, or are you married to one?
Learning curve & maturity How long to first useful agent? How stable is the API? How big is the community?

A tour of the major frameworks

APIs in this space churn fast — treat every snippet below as illustrative of the shape, not as a copy-paste contract. Always check the current docs. The point is the abstraction, not the exact method name.

LangGraph (from the LangChain team)

Philosophy: an agent is a graph of explicit state transitions, and you should be able to see and audit every one.

Core abstraction: nodes and edges over a shared state object. A node is a function that reads state and returns an update. An edge — often conditional — decides which node runs next. Your agent loop becomes a graph: a “call the model” node, a “run tools” node, and a conditional edge that routes back to the model on tool_use or exits on end_turn. That is exactly the control flow you hand-wrote in Scout, lifted into a declarative graph.

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import InMemorySaver

def call_model(state): ...        # returns {"messages": [...]}
def run_tools(state): ...         # executes tool calls, returns results

def route(state):                 # the conditional edge
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

graph = StateGraph(AgentState)
graph.add_node("model", call_model)
graph.add_node("tools", run_tools)
graph.set_entry_point("model")
graph.add_conditional_edges("model", route, {"tools": "tools", END: END})
graph.add_edge("tools", "model")

app = graph.compile(checkpointer=InMemorySaver())  # persistence for free

Best at: production-grade, stateful, auditable workflows — the regulated / high-stakes end of the spectrum where you need explicit control flow plus durable checkpointing and the ability to inspect or replay a run. The checkpointer is the headline feature: built-in persistence and time-travel that you’d otherwise build yourself. Pairs with LangSmith for tracing and LangGraph Platform for deployment. Model-agnostic.

Tradeoffs: the steepest concept curve here. Nodes, edges, state reducers, and channels are real machinery to learn, and for a simple agent it can feel like you’ve drawn an elaborate diagram of a while loop. The payoff is real only when you actually need the state machine to be explicit and durable.

OpenAI Agents SDK

Philosophy: keep it lightweight and opinionated; agents collaborate by handing off control to each other.

Core abstraction: the handoff. You define agents, each with instructions and tools, and an agent can transfer the conversation to another agent. Add guardrails (input/output validation), sessions (conversation state), and built-in tracing. It’s the GA successor to the experimental “Swarm.”

from agents import Agent, Runner

billing = Agent(name="Billing", instructions="Handle billing questions.")
triage = Agent(
    name="Triage",
    instructions="Route the user to the right specialist.",
    handoffs=[billing],
)
result = Runner.run_sync(triage, "I was double-charged.")

Best at: clean multi-agent designs with low ceremony, when you’re already in the OpenAI ecosystem. The learning curve is shallow — you can read the whole mental model in an afternoon. Integrates with Temporal for durable execution when you outgrow in-memory runs.

Tradeoffs: OpenAI-models-centric by default (you can point it at other providers, but the affordances and examples assume OpenAI). The handoff model is elegant but opinionated — if your control flow doesn’t decompose into agent-to-agent transfers, you’re swimming upstream.

Claude Agent SDK (Anthropic)

Philosophy: give you the production primitives from Claude Code’s harness lineage, so you’re building on the same machinery that powers a shipping coding agent.

Core abstraction: a harness of production primitives around the agent loop — tool use, hooks (intercept and gate tool calls before they execute), MCP integration, subagents, skills, and built-in context management. If you remember promoting actions to dedicated tools and gating them in Module 5, hooks are the framework-level version of that instinct: a clean interception point for every tool call.

from claude_agent_sdk import query, ClaudeAgentOptions

options = ClaudeAgentOptions(
    model="claude-opus-4-8",
    # tools, MCP servers, hooks, subagents configured here
)
async for message in query(prompt="Audit this module for dead code.", options=options):
    print(message)

Best at: Claude-centric agents that want the same battle-tested harness behavior as Claude Code — strong context management, hooks for governance, MCP-native tool mounting, and subagents out of the box.

Tradeoffs: Claude-centric. The affordances assume Claude models, so it’s the wrong choice if model-swapping across providers is a hard requirement.

Managed Agents (also Anthropic): a different shape entirely — a hosted offering rather than a library you run. You create an Agent once (model, system prompt, tools), then create a Session per run; Anthropic runs the agent loop and hosts a sandboxed container where the agent’s tools execute. You stream events back and send messages and tool results in. This is the “I don’t want to host the loop or the sandbox” option. We treat deployment depth in Module 12 — for now, just know the shape exists: create Agent once → create Session per run → Anthropic runs the loop.

CrewAI

Philosophy: model the team. A “crew” of role-playing agents collaborates on tasks.

Core abstraction: role-based agents plus tasks. You declare agents with a role, a goal, and a backstory, then assign tasks and let the crew execute (sequentially or in parallel).

from crewai import Agent, Task, Crew

researcher = Agent(role="Researcher", goal="Find the facts", backstory="...")
writer = Agent(role="Writer", goal="Draft the summary", backstory="...")
crew = Crew(agents=[researcher, writer], tasks=[research_task, write_task])
result = crew.kickoff()

Best at: the fastest path from idea to running prototype. The role/task metaphor is intuitive and the API is high-level, so you get a multi-agent demo working quickly. Model-agnostic.

Tradeoffs: higher-level and more opinionated means less control when you need to do something off the paved path. The same abstraction that makes the demo fast can fight you when the real requirements arrive.

Google ADK (Agent Development Kit)

Philosophy: Google’s agent framework, with tight integration into Vertex AI and Gemini.

Core abstraction: structured agents and workflows with first-class Google-cloud and Gemini integration, while remaining reasonably model-agnostic.

Best at: teams already on Google Cloud / Vertex who want native integration and deployment into that ecosystem.

Tradeoffs: the gravity well is Google’s stack; the payoff scales with how much of your infrastructure already lives there.

Briefly worth knowing

  • Pydantic AI — type-safe and Pythonic; if you love Pydantic’s validation model, this brings it to agents.
  • Microsoft AutoGen / AG2 — research-flavored multi-agent conversation framework.
  • Mastra — a TypeScript-native agent framework, for teams whose stack is JS/TS rather than Python.
  • LlamaIndex — retrieval-centric; the natural reach when your agent is fundamentally a RAG pipeline with tools bolted on.
  • Strands — another entrant in the model-agnostic agent-framework space; worth a look when surveying.

📖 A note on MCP (Module 13): the Model Context Protocol is becoming the standard wire format for tool and data servers, and increasingly every framework above speaks it. That matters for your decision: a tool you expose as an MCP server is portable across frameworks. MCP is steadily turning “which framework” into a less load-bearing question for the tool layer — you can keep your tools and swap the harness.

A decision framework

Match the tool to the constraint that actually binds you. The four that matter most:

  1. Control-flow determinism — how much do you need the path to be explicit, auditable, resumable?
  2. Model affinity — are you committed to one provider, or must you stay portable?
  3. Team preference — speed-to-prototype, or control and minimal deps?
  4. Production / regulatory needs — checkpointing, durability, audit trails?
Your situation Lean toward Why
High-stakes / regulated; need explicit, auditable, resumable control flow LangGraph Graph state machine + durable checkpointing + time-travel are its core competence.
Speed-to-prototype is the constraint CrewAI Highest-level, fastest idea→demo; role/task metaphor needs no ceremony.
Committed to OpenAI models; want clean multi-agent OpenAI Agents SDK Handoff model is tight and low-ceremony; native OpenAI integration.
Committed to Claude; want Claude Code’s harness (hooks, subagents, context mgmt) Claude Agent SDK Production primitives from a shipping agent, MCP-native.
Want Anthropic to run the loop and the sandbox Managed Agents Hosted: create Agent once, run Sessions; no infra to own.
Deep in Google Cloud / Vertex / Gemini Google ADK Native integration where your infra already lives.
Full control, minimal deps, simple or deeply custom harness needs Roll your own (what you built) No abstraction to leak, no version churn, you own every line.

The flowchart version, compressed:

Need explicit/durable/auditable control flow?  ── yes ─▶  LangGraph
        │ no
Strong single-model affinity + want vendor integration?  ── yes ─▶  that lab's SDK
        │ no                                                         (OpenAI / Claude / Google)
Speed-to-prototype the binding constraint?  ── yes ─▶  CrewAI
        │ no
Simple needs, or you want full control / minimal deps?  ── yes ─▶  roll your own

This is a synthesis heuristic, not a law. Real systems blend: a hand-rolled loop that mounts MCP tools; a LangGraph core with a CrewAI prototype that proved the idea; a lab SDK for the model-facing parts and your own code for orchestration.

Do you even need a framework?

You have already shipped an agent without one. So this is a real question, not a rhetorical one.

Reach for your own loop when:

  • Your needs are simple. A single-turn tool-using agent, or a short fixed pipeline, does not need a state-machine framework. The loop you wrote is less code than the framework’s “hello world.”
  • You want full control. When the control flow is the product — bespoke gating, custom scheduling, an unusual context strategy — a framework’s opinions are friction, not help.
  • You need to deeply customize the harness. If you’re doing things no framework anticipated, you’ll spend more time escaping the abstraction than you’d spend writing the loop.
  • You want minimal dependencies. Every framework is a large dependency tree with its own release cadence and CVEs. Your loop depends on one SDK.

The hidden costs of frameworks — the failure modes to weigh:

  • Debugging through abstraction layers. When the agent misbehaves, the stack trace runs through the framework’s internals, not your code. You debug their state machine, with their mental model, often without a clean breakpoint where your logic lives.
  • Leaky abstractions. The framework’s model of an agent and the model API’s actual behavior diverge at the seams — a new content-block type, a stop reason the framework doesn’t surface, a streaming event it swallows. The leak shows up as a bug you can’t fix without reading the framework’s source.
  • Version churn. This space moves fast. Breaking changes between minor versions are common; an upgrade can rewrite your control flow out from under you.
  • Thin-wrapper reality. A surprising amount of any framework is a loop you could have written — the same while, the same stop_reason check, the same message append. You’re sometimes adopting a dependency to get 40 lines you already understand.

📖 The honest industry pattern, mid-2026: many strong teams converge on a thin custom harness plus a few targeted libraries, rather than an all-in framework. They keep the loop — because they understand it and it never leaks — and they reach for a library exactly where it earns its keep: a checkpointer, an observability SDK, an MCP client. That is not anti-framework dogma; it’s the same per-axis evaluation this module is teaching, applied honestly. The framework wins the axes where it genuinely saves you work, and you keep the rest.

🛠️ Exercise

Goal: form an evidence-based opinion, not a vibe. You will rebuild a slice of Scout in one framework, then write down — concretely — what it gave you and what it took.

Default to LangGraph (it’s the most production-representative of the control-flow-explicit camp). If you have strong model affinity, the stretch goal lets you compare against a lab SDK.

Part 1 — Reimplement Scout’s core in LangGraph

Take Scout’s agent loop plus two of its tools (pick the two you understand best — say, a file-read tool and a shell/bash tool) and express them as a LangGraph graph:

  1. A model node that calls the model with the current message state and tool schemas.
  2. A tools node that executes any requested tool calls and appends their results to state.
  3. A conditional edge out of model that routes to tools when stop_reason (or the equivalent tool-call signal) indicates tool use, and to END otherwise.
  4. An edge from tools back to model.
  5. A checkpointer so the run is persistent.

Then exercise the persistence: run the agent, interrupt it mid-task (kill the process), and resume from the checkpoint. Confirm it picks up where it left off.

✅ Check: the graph terminates on end_turn, loops on tool use, and a resumed run does not repeat tool calls it already made before the interrupt.

Part 2 — Reflect in notes.md

Write honest answers, with specifics:

  • What did the framework give you for free? Be concrete. Persistence you didn’t write. Time-travel/replay. A graph object you can inspect or visualize. Streaming plumbing. Name the lines of your Scout code that this replaced.
  • What did it take? The boilerplate to declare nodes and edges. New concepts (state reducers, channels) you had to learn. The indirection — when you set a breakpoint, where did you actually land?
  • The decisive question: for your use case, did the checkpointer (and the rest) earn the concept curve? Would you ship Scout on this, or keep your loop and add only a checkpointing library?

Stretch

Reimplement the same slice in the OpenAI Agents SDK or the Claude Agent SDK and compare developer experience head-to-head. Where did each one make the easy thing easy? Where did each one make the custom thing hard? Add a short comparison table to notes.md. The deliverable is a defensible opinion you could give a teammate who asks “which one should we use?”

Real production issues

War stories, condensed, so you recognize them before they cost you a sprint:

  • The abstraction fought your model of the world. You needed to inject a system-level instruction mid-conversation, or handle a content-block type the framework didn’t model, or read a stop reason it abstracted away. The framework’s worldview and the API’s worldview disagreed, and you lost a day at the seam.
  • You debugged through the layers. A tool wasn’t being called. The bug was four frames deep in the framework’s router, not in your tool. Without the framework you’d have set one breakpoint; with it you read source code for an abstraction you didn’t write.
  • A minor version broke your graph. An upgrade for a security patch also changed how state reducers compose, and your control flow silently changed behavior. Pin versions; read changelogs; budget for churn.
  • The framework was a thin wrapper. You profiled what it actually did for you and found it was your while loop with a dependency tree attached. The honest move was to delete it and keep the 40 lines.
  • Lock-in surfaced late — especially with lab SDKs. The control flow was quietly coupled to one provider. When you needed to evaluate a cheaper model from a different vendor, the “model-agnostic in principle” SDK turned out to be agnostic in principle only.
  • Scaffolding rotted as the model improved. A reflection-retry loop, a verbose output parser, an aggressive planning prompt — all added to compensate for an older model — now fought a model that did the right thing on its own. The scaffolding became a net negative, and nobody had revisited the assumption it encoded.
  • You picked a heavy framework for a light task. A state-machine framework wrapped a single-turn classifier. All cost, no benefit.

The thread through all of these: the failure is rarely the framework being bad. It’s a framework adopted for the wrong axis, or kept past the point its assumptions held. You now have the primitives to make that call deliberately — which is the whole point of having built Scout first.
