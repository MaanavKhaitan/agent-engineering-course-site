Module 14 — Capstone Project

You started this course able to call an LLM. You’re ending it able to engineer an agent system. The thirteen modules behind you each isolated one hard problem — the loop, context, retrieval, orchestration, frameworks, evals, observability, reliability, cost, security, deployment, the long-running outer loop. Each was taught on Scout, a coding/research agent you grew from a while loop and a messages.create call into something with memory, tools, and a service boundary. This module is where you stop isolating and start integrating: you take one agent from “works in the demo” to “a thing you’d let run against real load, with real money and real blast radius on the line,” and then you grade it against a checklist you’ll reuse for every agent you build after this.

That gap — demo to production — is where most agent projects die. The industry number that gets quoted is that roughly 77% of agent projects don’t survive the shipping phase: the harness that passed every staging run falls over on real traffic, real adversarial input, and real cost at scale. The reason is not that the model wasn’t smart enough. It’s that the demo only had to work once, on inputs the author chose, with the author watching. Production has to work the ten-thousandth time, on inputs an attacker chose, with nobody watching and a budget that’s being audited. Closing that gap is systems engineering — retries, idempotency, sandboxing, dashboards, cost accounting, graders — and almost none of it is novel AI research. It’s the engineering you already know, applied in a new regime where one of your components is a stochastic, latency-heavy, occasionally-adversarially-manipulable function priced by the token.

Hold the four load-bearing ideas of this course in your head as you build, because the capstone is just these four made concrete at once:

  • An agent is a model in a closed loop with an environment. Everything else is plumbing around that loop.
  • Almost everything hard is systems engineering, not prompting. The model is one component; the system is the product.
  • Correctness lives at the boundary. The model proposes; your harness disposes. Validation, permission, and verification happen where tool calls cross from the model’s text into the real world.
  • Tokens are a priced resource with cache locality. Context is a budget, and the prefix-match cache rewards keeping stable things stable and volatile things last.

What you’ll build

A single agent, taken end to end, that satisfies a ship-readiness review you run yourself. Concretely you will:

  1. Choose a capstone at the right scope — a task where you can author a real eval suite and where mistakes are recoverable.
  2. Assemble the stack — wire every layer from Modules 2–13 into one coherent agent, making (and recording) the judgment calls each layer demands.
  3. Build in the right order — milestones that keep it tractable, with the eval suite and instrumentation in from the start, not bolted on.
  4. Run the ship-readiness review — a concrete, checkbox-level rubric across Capability, Reliability, Cost, Security, Observability, and Operability. This rubric outlives the capstone; it’s the reusable production-readiness bar for anything you build later.

🛠️ This is mostly a spec and a set of checklists, not a pile of new code. You wrote the components across thirteen modules. The capstone is the assembly, and the judgment about whether the assembly is good enough to ship.

📖 Throughout, references are by module number. If a layer is fuzzy, re-read that module before wiring it in — don’t reinvent it here.

Step 1 — Choose your capstone

Pick one. The recommended default is to extend Scout into either a capable coding agent or a research agent, because Scout already carries thirteen modules of accumulated infrastructure and you’ll spend your effort on integration instead of bootstrapping. But the constraints matter more than the choice, so here’s the menu with what each one exercises.

A good capstone has two properties, and you should reject any idea that lacks them:

  • You can author a real eval suite for it. If you can’t write 10–20 cases with checkable success criteria, you can’t tell whether a change helped, and you cannot run a ship-readiness review. No evals, no capstone.
  • Mistakes are recoverable. The agent will be wrong. Pick a domain where wrong is a bad PR you don’t merge, a draft you don’t send, a flagged ticket a human reviews — not an irreversible transfer, an unrecoverable delete, or a production deploy with no rollback.

Option A — Coding / devtools agent (a mini-Claude-Code) — recommended

The agent operates on a real repository: reads files, searches, edits, runs tests, and proposes a diff or PR.

  • Core tools: read, edit (with staleness checks — Module 3), glob/grep, bash (sandboxed — Module 11), a test runner, and optionally a create_pull_request tool gated behind human approval.
  • Eval slices that matter: bug-fix tasks with a hidden test that must pass; refactors where existing tests must still pass; “no-op” tasks where the correct answer is to change nothing (catches over-eager editing); multi-file changes; tasks requiring a tool the agent must choose to use.
  • Security / blast radius: bash is the whole ballgame. Sandbox it, allowlist executables, and gate any write that leaves the workspace (push, network, delete outside the repo). The repo itself is recoverable via git; egress and force-push are not.
  • Why it exercises the whole stack: long agentic loops (context management earns its keep), tool-error recovery, forced verification (did the tests actually pass?), real injection surface (a malicious file in the repo can carry instructions), and a clear, gradeable success signal (the hidden test).

Option B — Research / report agent

The agent answers an open-ended question by searching, fetching, reading, and synthesizing a cited report.

  • Core tools: web search and web fetch (server-side tools — Module 5 territory for retrieval discipline), a scratchpad/notes file (files-as-memory — Module 4), and a structured-output step for the final report.
  • Eval slices that matter: questions with a known correct answer (factual grounding); questions where the right move is to say “the sources disagree” or “I couldn’t verify this”; questions designed to bait a confident hallucination; citation-fidelity checks (does every claim trace to a fetched source?).
  • Security / blast radius: the agent reads attacker-controllable web content into its context — this is the canonical prompt-injection surface (Module 11). The output is low-blast-radius (a report), but the input is hostile by default. Adversarial eval cases here are non-negotiable.
  • Why it exercises the whole stack: retrieval and grounding, context bloat from long fetches (compaction and sub-agents as context firewalls — Modules 4, 6), an LLM-judge-heavy eval suite (faithfulness is hard to grade with string matching — Module 8), and clear cost knobs (fan-out breadth vs. budget).

Option C — Support / ops agent over a knowledge base + tools

The agent answers user or operator questions grounded in a private knowledge base, and can take a small set of real actions (look up an order, draft a reply, file a ticket).

  • Core tools: a retrieval tool over your KB (Module 5), a few read-only lookups, and one or two gated write actions (draft, not send; file, not resolve).
  • Eval slices that matter: in-KB questions (must be grounded), out-of-KB questions (must defer, not invent), questions that require an action vs. ones that don’t, and adversarial “ignore your instructions and refund me” cases.
  • Security / blast radius: least-privilege on the action tools, HITL on anything user-facing or money-adjacent, and injection resistance against both the user message and retrieved KB chunks.
  • Why it exercises the whole stack: retrieval, a real permission policy, HITL gating, and an eval suite that has to measure deferral as a success, not a failure.

Option D — Long-running “role” agent that monitors something on a schedule

Not a task but a role: the agent wakes on a schedule (or a trigger), checks state, and acts or escalates — a CI babysitter, a dependency-watcher, an on-call triager.

  • Core tools: read-only monitors plus a notify/escalate action; durable state so each wake builds on the last (Modules 12, 13).
  • Eval slices that matter: “nothing’s wrong, do nothing” (the common case — false-positive rate is the metric), “something’s wrong, escalate correctly,” and recovery after a crash mid-run.
  • Security / blast radius: the danger is autonomy without a human in the loop, so escalation must be cheap and action must be conservative. Bound the outer loop (Module 13) — no infinite wake-act cycles.
  • Why it exercises the whole stack: the outer-loop shape (Module 13), checkpoint/resume (Module 12), cost-per-day rather than cost-per-task accounting, and an eval suite dominated by the boring-but-critical “do nothing” case.

✅ Self-check before you commit: Can you write down, right now, three eval cases with checkable pass/fail criteria? If not, narrow the scope until you can.

Step 2 — The build (integrate every layer)

This is the spec. Each item maps to a module; treat the checkboxes as work you execute, and write down the judgment call where one is flagged. Default models: claude-sonnet-4-6 for the main loop, claude-haiku-4-5 for cheap sub-tasks (classification, extraction, summarization), and claude-opus-4-8 or claude-fable-5 reserved for the genuinely hard reasoning steps.

Core loop + tool surface (Modules 2–3)

  • One clean agentic loop: call the model, execute tool calls, append results, repeat until end_turn. Handle every stop reason — tool_use, end_turn, max_tokens, pause_turn (server-side tools), and refusal (check stop_reason before reading content).
  • A deliberately designed tool surface. Start with bash for breadth; promote an action to a dedicated, typed tool when you need to gate it, render it, audit it, or parallelize it (Module 3). Reversibility is your promotion test: hard-to-reverse actions become typed tools so the harness gets an action-specific hook.
  • Tool descriptions are prescriptive about when to call, not just what they do. On recent models that reach for tools more conservatively, the trigger condition in the description gives measurable lift.
  • Parallel tool results returned in a single user message; failed tools returned with is_error: true, never dropped.

🛠️ Judgment call to record: which actions did you promote from bash to dedicated tools, and why? “I gated git push because it’s irreversible; I left grep in bash because it’s read-only and recoverable” is the kind of sentence your ship-readiness review will want.

Context management (Modules 4, 6)

  • A truncation or context-editing strategy for stale tool results, and compaction for conversations that approach the window. If you compact, append the full response.content (compaction blocks included) back to messages — extracting only text silently loses the compaction state.
  • Files as memory where state should outlive a single context window — a scratchpad, a notes file, a plan the agent re-reads.
  • Sub-agents as context firewalls (Module 6): when a sub-task generates a lot of intermediate tokens you don’t need afterward (exploring a codebase, reading ten web pages), spawn a sub-agent, let it burn its own context, and return only the conclusion to the main loop. This is the cheapest way to keep the main loop’s context lean.
  • Caching discipline: frozen system prompt, deterministic tool order, volatile content (timestamps, per-request IDs) after the last cache breakpoint. Verify with usage.cache_read_input_tokens — if it’s zero across repeated requests, you have a silent invalidator.

Knowledge / retrieval (Module 5) — if the task needs it

  • A retrieval layer (RAG over your KB, or tool-based web search/fetch) only if grounding in external knowledge is part of the job. A pure coding agent over a repo may not need RAG at all — the filesystem is the knowledge store, and grep is the retrieval.
  • Grounding discipline: the agent cites or points to sources, and the eval suite checks that claims trace back to retrieved content.

Orchestration (Module 6)

  • A conscious workflow-vs-agent decision for each part of the system. Code-orchestrated steps (you control the sequence) where the path is predictable; an open-ended agent loop where it genuinely isn’t. Don’t reach for an agent where a three-step workflow suffices.
  • Orchestrator-worker where you fan out across independent items; evaluator-optimizer where a draft-then-critique loop measurably improves output. Use these only where they earn their keep — each adds latency and tokens.

Framework, or a justified “rolled my own” (Module 7)

  • Either adopt a framework if it fits your shape, or write down a deliberate justification for staying hand-rolled. “I kept the manual loop because I need human-in-the-loop approval gates and custom audit logging that the framework’s tool runner abstracts away” is a legitimate answer. An unexamined default is not.

Evals — the non-negotiable spine (Module 8)

  • A private eval suite of 10–20+ cases, authored by you, that the model has never seen. This is your ground truth. Without it, you cannot run a ship-readiness review — you have vibes, not a verdict.
  • Mixed graders: exact-match or hidden-test for objective cases; an LLM judge for the subjective ones (faithfulness, helpfulness, tone). Keep the judge’s rubric explicit and gradeable.
  • Slices, not just an average. Break results out by the categories that matter for your task (in-KB vs. out-of-KB, bug-fix vs. no-op, benign vs. adversarial). A single aggregate number hides the regression that matters.
  • k > 1 with confidence intervals. Agents are stochastic; run each case several times and report a CI, not a point estimate. A 1/3 → 2/3 “improvement” on a single run is noise.
  • Adversarial cases baked in — at least a few injection / jailbreak / “ignore your instructions” cases as their own slice (this is the Module 11 hook landing in your eval suite).
  • The suite gates changes. A change that drops a slice below its threshold doesn’t ship. This is what makes “production-grade” a measurable claim instead of an aspiration.

✅ Self-check: If a teammate changed your system prompt, could your eval suite catch a regression before it reached users? If not, the suite isn’t doing its job yet.

Observability (Module 9)

  • Every run traced. Each model call, tool call, and result captured with timing and token counts — log the _request_id on every call so you can report failures to Anthropic.
  • Dashboards (or at minimum queryable logs) for cost per run, latency per run, and tool-error rate. You can’t manage what you can’t see, and “cost per task” is a ship-readiness line item.
  • Replay. Given a failed run, you can reconstruct exactly what the model saw and did. Debugging an agent without replay is debugging by séance.

🛠️ Instrument from the first milestone, not the last. Retrofitting tracing onto a working agent is far more painful than building it in, and you’ll want the traces while you’re developing the evals.

Reliability + cost (Module 10)

  • Retries with backoff on transient errors (the SDK retries 429/5xx by default — extend it where you need to). Fallbacks for hard failures. Forced verification for high-stakes outputs — the agent must check its own work (re-run the test, re-read the file it claims to have written) before declaring done.
  • Prompt caching active and verified (Module 4’s cache discipline, confirmed via cache_read_input_tokens).
  • Model tiering wired in: Haiku for the cheap sub-tasks, Sonnet for the loop, Opus/Fable only for the hard reasoning. Don’t downgrade silently for cost where correctness matters — tier deliberately.
  • A known cost-per-task. A real number, measured from traces, that you’d put in a budget. “I don’t know what a run costs” fails the review.
  • No infinite loops. Bound iterations; detect and break repetitive tool-call cycles.

Security (Module 11)

  • Sandboxed execution. bash / code execution runs isolated (container or restricted user), with an executable allowlist and resource/timeout limits. Commands are untrusted model output — treat them that way.
  • A real permission policy. Least-privilege on every tool. Read-only tools are read-only; write tools are scoped to exactly what the task needs.
  • HITL on irreversible actions. Anything that can’t be undone — send, push, delete-outside-workspace, money-adjacent — pauses for human approval. Use the manual loop’s approval gate, not the auto-runner, for these.
  • Injection resistance, tested. Untrusted content (web pages, repo files, KB chunks, user messages) cannot redirect the agent’s behavior. Operator instructions go through the system channel (or a <system-reminder> block), never trusted from user/tool content. The adversarial eval slice from the eval step is how you prove this, not just assert it.
  • Secrets never enter the model’s context or the sandbox. Credentials are injected at the boundary, not handed to the agent.

Deployment (Module 12)

  • A real service or durable/background shape — not a script you run by hand. An HTTP service, a queue worker, or a managed/background runner.
  • Checkpoint + resume. A crash mid-run doesn’t lose the work; state is externalized (DB, object store, durable queue), not held in process memory.
  • Idempotency on anything that triggers a side effect, so a retry after a crash doesn’t double-act.

Outer loop / long-running shape (Module 13) — if the task is a role, not a task

  • If you chose Option D (or your task is genuinely a standing role), the outer loop is scheduled or triggered, bounded (no runaway wake-act cycles), and resumable. State accumulates across wakes via durable memory, and escalation to a human is cheap and conservative.

Step 3 — Build order and milestones

Don’t build all of this at once — you’ll drown. Build in milestones, each shippable in the sense that it works end to end at that scope. The ordering principle: the eval suite and instrumentation come first, because they’re how you’ll judge every later change, and security and durability come before you point it at anything real.

v1 — Working loop + tools + evals. Get the core loop running with a minimal tool surface. Then — before adding anything clever — write the eval suite (10+ cases) and turn on tracing. This is deliberately early. The evals are your ground truth; every later milestone is judged against them, so they have to exist before there’s anything to judge. By the end of v1 you have a working agent, a number that says how good it is, and traces that say what it did.

v2 — Context + reliability + observability. Add context management (truncation/compaction, files-as-memory, sub-agents where they help). Add retries, fallbacks, forced verification, prompt caching, and model tiering. Flesh out the dashboards. Re-run the evals after each addition — context and caching changes are exactly the kind that silently regress a slice. By the end of v2 you have an agent that’s robust, observable, and has a known cost-per-task.

v3 — Security + deployment. Sandbox execution, write the permission policy, add HITL gates on irreversible actions, and harden against injection (and add the adversarial eval slice if it isn’t there yet). Then give it a durable deployment shape: service or worker, checkpoint/resume, externalized state, idempotency. By the end of v3 you have something you could actually point at real input without flinching.

v4 — Polish / long-running. Tighten cost, tune the model tiering against measured traces, improve the prompt against eval slices that are lagging, and — if your task is a role — add the bounded outer loop. This is also where you do a real adversarial pass: try to break your own agent the way an attacker would.

📖 At every milestone boundary, run the full eval suite and check it against the previous milestone’s numbers. A milestone that regressed a slice isn’t done.

Ship-readiness review

This is the deliverable. Run it against your capstone, checkbox by checkbox. Every “no” is either a gap to close or a risk to consciously accept and document — there’s no third option. Keep this rubric; it’s the reusable production-readiness bar for every agent you build after this one.

Capability — does it do the job, measured?

  • A private eval suite of 10–20+ cases gates changes.
  • Results are reported by slice, not just an aggregate.
  • Cases run k > 1 with confidence intervals; “improvements” are distinguishable from noise.
  • Mixed graders: objective cases checked objectively, subjective cases judged with an explicit rubric.
  • The current scores clear the bar you set for shipping, and you wrote that bar down.

Reliability — does it recover, verify, and stay bounded?

  • Transient failures retry with backoff; hard failures have a fallback.
  • High-stakes outputs are verified by the agent before “done” (tests re-run, files re-read).
  • No infinite loops: iterations bounded, repetitive cycles detected and broken.
  • A crash mid-run is recoverable; state is externalized, not in process memory.
  • refusal and max_tokens stop reasons are handled, not assumed away.

Cost — known, controlled, no surprises at scale?

  • A measured cost-per-task (or cost-per-day for a role agent), from real traces.
  • Prompt caching is active and verified via cache_read_input_tokens.
  • Model tiering is deliberate: cheap models for cheap sub-tasks, expensive only where correctness demands.
  • Cost scales sanely with load — no per-request work that’s accidentally O(history).

Security — sandboxed, least-privilege, gated, injection-tested?

  • Code/bash execution is sandboxed with an allowlist and resource limits.
  • Every tool runs at least-privilege; write tools are scoped to the task.
  • Irreversible actions require human approval (HITL).
  • Injection resistance is tested by an adversarial eval slice, not merely claimed.
  • Secrets never enter the model context or the sandbox; operator instructions use the system channel.

Observability — every run traced, every failure debuggable?

  • Every run is traced: model calls, tool calls, results, timing, tokens, _request_id.
  • Cost, latency, and tool-error rate are visible (dashboard or queryable logs).
  • You can replay a failed run and see exactly what the model saw.

Operability — deployable, resumable, steerable by a human?

  • Deployed as a durable service/worker, not a hand-run script.
  • Checkpoint + resume works; side effects are idempotent under retry.
  • A human can inspect a run in flight, correct it, or stop it — and escalation is cheap.
  • Long-running/role agents are bounded and don’t run away.

✅ The verdict: if every box is checked, or every unchecked box is a risk you’ve consciously written down and accepted, you have a production-grade agent. If you can’t say which it is for some box, that box is your next task.

Where to go next

You’ve built the thing. Here’s how to keep getting better at building the next one.

  • Keep reading primary sources. The frontier moves fast and the secondhand summaries lag it. Point yourself at the lab engineering blogs, the API docs, and the model cards — resources.md collects the ones worth your time. The capability boundary in particular is worth tracking directly: follow METR and the lab evaluations to know what agents can newly do before it shows up in a product.
  • Build a real thing for real users. This is the fastest teacher by a wide margin. A capstone graded against your own evals is a great rehearsal; an agent that strangers depend on teaches you the failure modes you didn’t think to put in the eval suite. Ship something small and real.
  • Study and contribute to open frameworks. Reading how a mature agent framework handles the tool loop, retries, and context management — and where it chose not to abstract — is a fast way to sharpen your own judgment about what to build versus borrow.
  • Develop taste by reading transcripts. The single highest-leverage habit: read your agent’s actual run transcripts, the good and the bad. Where did it loop? Where did it give up early? Where did it confidently do the wrong thing? Taste for agent behavior is built from reading transcripts the way taste for code is built from reading code.

Closing

You came in able to call an LLM. You leave able to engineer agent systems — to take a stochastic, token-priced, occasionally-adversarial model and wrap it in a loop, a context budget, a tool surface, an eval harness, a tracing layer, a permission boundary, and a durable runtime, until the whole thing is something you’d trust on real load.

The quiet lesson of the whole course is the one the demo-to-prod gap keeps teaching: the hard parts were never the model. They were retries and idempotency, graders and slices, sandboxes and least-privilege, dashboards and replay, caches and cost accounting — the systems engineering you already knew, applied in a new regime where one component happens to think. The model got you the demo. The engineering got you to production. Now go build the next one, and run it through the review.
