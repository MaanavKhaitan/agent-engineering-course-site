Module 0B — The Python You Need for Scout

Deep-dive. Scout — the agent you build across this course — is ~4,000 lines of Python, and it deliberately uses the language the way production agent code does: dataclasses and Pydantic at the boundaries, generators and asyncio for the serving layer, threads and process groups for steering and sandboxing, context managers and contextvars for tracing. If you’re an experienced engineer whose Python stops at “functions, classes, list comprehensions,” this module fills the specific gaps between that and Scout’s source.

This is not a Python course. Every section is anchored to a real construct in the Scout repo, explains just enough of the language mechanics to read and modify that code confidently, and tells you why the construct was chosen — which is usually the more interesting lesson.

How to use it: skim it once now so you know what’s here, then come back when a construct bites you mid-module. Sections 1–8 pay off from Module 3 onward (the sync loop); sections 9–12 matter for Modules 12–13 (steering, serving, durability); 13–15 explain infrastructure you’ll otherwise trip over silently.

Learning objectives

By the end you should be able to:

  • Read modern type annotations (str | None, list[dict], Callable[..., str], type[BaseModel]) and know what they do and don’t enforce.
  • Use dataclasses and Pydantic models for the two different jobs they do in Scout (internal records vs. validated boundaries).
  • Recognize functions-as-values, closures, and dependency injection via callables — the pattern behind Scout’s tools, gates, and human-responders.
  • Write and read context managers, including @contextmanager-based ones with correct exception behavior.
  • Explain what a generator is, what an async generator is, and why Scout’s serving loop is one.
  • Reason about Scout’s three concurrency substrates — threads, asyncio, subprocesses — and say which one is right for a given job.
  • Explain why Path.resolve() beats os.path.abspath for security, and what flush() + fsync() actually guarantee.
  • Spot the import-time and module-global-state landmines that shape Scout’s design (one run per process, lazy imports, sys.path insertion).

1. Modern typing: annotations as documentation, not enforcement

Scout is written against Python 3.10+, which changed how type hints look:

# scout/loop.py
def run(task: str, workdir: str | None = None,
        gate: PermissionGate | None = None, model: str = MODEL,
        verify_cmd: str | None = None, ...) -> Transcript:

The things worth knowing:

  • X | None replaces Optional[X] (PEP 604), and list[dict], dict[str, str], tuple[bool, str] replace typing.List etc. (PEP 585). You’ll see zero from typing import List in modern code.
  • Annotations are not enforced. Python evaluates them (mostly) and stores them, but passing an int where the hint says str raises nothing. They’re for readers and for static checkers (mypy/pyright). The one place Scout gets runtime enforcement from annotations is Pydantic (§3) — that’s precisely the difference between the two.
  • Callable[..., str] means “any callable, any arguments, returns str.” Scout’s Tool.fn: Callable[..., str] says: a tool implementation is just a function that returns a string. Callable[[str], str] would pin one string argument.
  • type[BaseModel] means “a class object that is BaseModel or a subclass” — not an instance. Tool.args_model: type[BaseModel] | None holds the class itself so dispatch can call tool.args_model.model_validate(...) later.
  • String forward references: in service.py, RUNS: dict[str, "Run"] quotes Run because the class is defined a few lines below the annotation. The quotes defer evaluation.
  • The or 0 idiom next to Optional fields: the Anthropic SDK types cache counters as Optional[int], so Scout writes (getattr(usage, "cache_read_input_tokens", 0) or 0). getattr with a default handles the attribute missing; or 0 handles the attribute present but None. You need both, and this pattern is everywhere in code that consumes SDK objects.

Where you’ll see it: every signature in scout/loop.py; tracing.cost_of for the Optional dance; service.py for forward refs.

2. Dataclasses: records without boilerplate

Scout uses @dataclass for internal records — things that carry data between functions but never validate untrusted input:

# scout/loop.py
from dataclasses import dataclass, field

@dataclass
class Tool:
    name: str
    description: str
    input_schema: dict
    fn: Callable[..., str]
    args_model: type[BaseModel] | None = None

@dataclass
class Transcript:
    answer: str
    messages: list
    input_tokens: int
    output_tokens: int
    iterations: int
    cost_usd: float = 0.0
    model: str = MODEL
    journal: list = field(default_factory=list)
    report: str = ""

The decorator generates __init__, __repr__, and __eq__ from the class-level annotations. What you must know:

  • Fields with defaults must come after fields without (they map to positional parameters of the generated __init__).
  • field(default_factory=list) is mandatory for mutable defaults. journal: list = [] would be one shared list across every Transcript instance — the classic mutable-default trap, promoted from function arguments to class definitions. default_factory is a zero-arg callable invoked per instance. It also takes lambdas: Span.span_id: str = field(default_factory=lambda: uuid.uuid4().hex[:8]) mints a fresh id per span.

  • Methods and properties work normally. tracing.Span computes latency_ms as a @property — an attribute-shaped method, read as span.latency_ms with no parentheses:

    @property
def latency_ms(self) -> float:
    return round((self.end - self.start) * 1000, 1)
  • dataclasses.asdict(obj) recursively converts a dataclass to a plain dict — tracing.Trace.flush uses {**asdict(s), "latency_ms": s.latency_ms} to serialize spans to JSONL (note the computed property has to be added by hand; asdict only sees fields).

Dataclass vs. Pydantic — the rule Scout follows: if the data comes from your own code (a Tool definition, a finished Transcript), a dataclass is enough. If the data crosses a trust boundary — model output, an HTTP request body — use Pydantic, because there you need validation, not just structure. Keep this distinction; it’s load-bearing in the next section.

3. Pydantic: validation at the untrusted boundaries

Pydantic models look like dataclasses but enforce their annotations at runtime — construction parses and validates, and bad data raises ValidationError with a readable complaint. Scout uses them at exactly three boundaries:

(a) Tool arguments — model output is untrusted input:

# scout/loop.py
class WriteFileArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")   # unknown args are a bug signal
    path: str = Field(min_length=1)
    content: str
  • Field(min_length=1) attaches constraints beyond the type. Elsewhere you’ll see Field(ge=1, le=5) (graders’ judge score) and Field(description=...) — descriptions matter because they’re shown to the model when the schema is used for structured output.
  • ConfigDict(extra="forbid") rejects keys not in the schema. Default Pydantic ignores extras; for tool calls an invented argument means the model misunderstood the tool, and you want that surfaced, not swallowed.

  • The methods you’ll use: Model.model_validate(data) (dict → validated instance), instance.model_dump() (instance → plain dict), model_dump(exclude_none=True) (drop None fields — checkpoint.serialize uses this to keep session logs clean). Pydantic v2 names; you’ll still see v1’s parse_obj/dict() in older code.

    The full pattern in dispatch:

    try:
    tool_input = tool.args_model.model_validate(tool_input).model_dump()
except ValidationError as e:
    return _result(block.id, f"Invalid arguments — fix them and call again:\n{e}", error=True)

    The ValidationError’s text goes back to the model as an error tool-result. That’s the schema-validation-and-retry loop from Module 3: Pydantic’s error messages are good enough that the model reads them and fixes its own call.

(b) Structured output — client.messages.parse(..., output_format=Decomposition) in scout/orchestrator.py makes the API guarantee the response parses into your Pydantic model, and resp.parsed_output is a typed instance. Covered properly in Modules 1 and 6; the Python-side point is that the class itself is passed as the schema.

(c) HTTP request bodies — FastAPI (§12) sees a Pydantic parameter (StartReq in service.py) and automatically parses + validates the JSON body against it, returning a 422 to the client on mismatch. You write zero parsing code.

4. Functions as values, closures, and injection

The single most load-bearing Python fact in Scout: functions are objects. You store them in fields and dicts, pass them as arguments, and build behavior by wiring callables together instead of building class hierarchies.

Functions in data structures — the tool registry is a list of dataclasses holding function references, plus a lookup dict:

Tool(name="read_file", ..., fn=tools.read_file)      # no parentheses: the function itself
TOOLS_BY_NAME = {t.name: t for t in TOOLS}
out = tool.fn(**tool_input)                           # called later, args unpacked from a dict

**tool_input unpacks a dict into keyword arguments — the bridge between “the model emitted JSON args” and “an ordinary Python function runs.” (The mirror image, def f(**kwargs), collects them.)

Injection via callable parameters — wherever Scout needs “ask a human,” the asking mechanism is a parameter with a callable default:

class PermissionGate:
    def __init__(self, ask=input, level: str = "read-only"):
        self._ask = ask          # input() in real runs; a scripted fn in tests

The CLI injects ask=ask_via_reader (routes through its stdin-owning thread), the service injects a function that raises EOFError (headless runs fail closed), and tests inject lambda prompt: "y". Same pattern for run(human=...) (the ask_human responder) and run_planned(approve=...). This is dependency injection with no framework — a callable parameter is the interface. When you see a Scout parameter typed Callable[...], read it as “a strategy the caller chooses.”

Closures — a nested function captures variables from its enclosing scope, and the capture is by reference, alive after the outer function’s frame would have died. loop.main() builds its whole CLI out of closures: reader(), ask_via_reader(), on_sigint() all share gate_waiting, gate_answers, and active without any of them being global.

The one-element-list trick — inside main():

active: list[Steerable | None] = [None]   # the live run's steering, if any
...
active[0] = steer          # in the main thread
live = active[0]           # read in the reader thread and the signal handler

Why a list holding one item instead of a plain variable? Because a closure can read an outer variable freely, but assigning to it inside the nested function would create a new local instead (you’d need nonlocal active). Mutating a container sidesteps that entirely, and the same object is visible to every closure sharing it. When you see a single-element list in threaded code, it’s a mutable cell, not a weird collection.

Module-level global — run() declares global _subagent_spend, _human_responder because it assigns those module-level names (same rule as closures: assignment makes a name local unless declared otherwise). Note what Scout’s comments admit about this: module globals are process-wide state, which is exactly why the eval harness runs one trial per process (§12).

5. Iteration idioms you’ll see on every page

Scout’s hot paths are written in compact iteration idioms. Once you can sight-read these five, the loop code stops looking dense:

Generator expressions + join — the standard way to extract text from a response’s content blocks:

answer = "".join(b.text for b in resp.content if b.type == "text")

A generator expression ((...) implied by the call) is a lazy sequence: nothing is built in memory, join consumes it. The same shape with square brackets is a list comprehension (eager). You’ll write this exact line a dozen times in this course.

next() on a generator — take the first match:

note = next(b.text for b in summary.content if b.type == "text")

Raises StopIteration if nothing matches; next(gen, default) returns the default instead. Scout uses the raising form deliberately — a summarizer response with no text block should blow up.

for/else — the else clause runs only if the loop completed without break:

# scout/loop.py, run_subagent
for calls in range(1, SUBAGENT_MAX_ITERS + 1):
    ...
    if resp.stop_reason != "tool_use":
        answer = ...
        break
else:
    answer = "Subagent hit its iteration cap without a final answer. ..."

This is the cleanest way to express “loop with an exit condition, plus a fallback if the budget ran out” — precisely the shape of a bounded agent loop. Under-known, worth adopting.

Dict merge by unpacking — {**content[-1], "cache_control": {...}} builds a copy of a dict with one key added/overridden. _mark_last_block leans on this to add a cache marker without mutating the caller’s transcript — copy-not-mutate is a correctness requirement there (the API caps cache breakpoints per request, so markers must never accumulate). Similarly messages[:-1] + [new_last] copies a list with the last element replaced.

Truthiness defaulting and formatting — out if out.strip() else f"(no output; exit code ...)", "; ".join(notes) or "all assertions passed" (empty string/list is falsy, so or supplies the default); f-string format specs f"{n:,}" (thousands separators), f"{pct:.0%}" (percent), f"{cost:.4f}", and f"{message!r}" (!r = repr(), quotes strings — useful for showing exactly what a value was).

Also in the background: enumerate(findings, 1) (index from 1), zip(docs, metas) (parallel iteration), set/dict comprehensions (sorted({p for p in written if p.endswith(".py")}) — a set comprehension deduplicating paths), and collections.defaultdict in stats.py/trace_view.py for group-by aggregation.

6. Decorators: the four you must recognize

A decorator is just a function applied to a function/class at definition time: @deco above def f means f = deco(f). You rarely need to write one for agent work, but you must recognize what each of these does, because they look identical and do wildly different things:

Decorator In Scout What it actually does
@dataclass Tool, Span, Transcript Code generation: writes __init__/__repr__/__eq__ from annotations
@property Span.latency_ms Turns a method into a computed read-only attribute
@contextmanager tracing.span, trace_run Turns a generator into a with-statement context manager (§7)
@app.post("/runs") service.py Registration: stores your function in FastAPI’s routing table. Note it’s a decorator factory — app.post(path) returns the actual decorator
@tool scout/lg_agent.py (LangGraph) Wraps a function into a framework Tool object, deriving the schema from your signature and docstring

The general reading rule: a bare @name transforms or registers the function; a called @name(args) is a factory that returns the transformer. If behavior seems to happen “by magic” when a module is imported, look for registration decorators — importing service.py is what populates FastAPI’s route table.

7. Context managers: with, and writing your own

with expr as x: calls expr.__enter__(), binds the result to x, runs the block, and guarantees __exit__ runs afterward — on success, on exception, on early return. It’s try/finally with a name. You know the file case; Scout uses it for subtler resources:

  • tempfile.TemporaryFile(...) as a subprocess output buffer (tools.py) — auto-deleted on exit.
  • redirect_stdout(log), redirect_stderr(log) (evals/harness.py) — temporarily rebind the process’s stdout/stderr so a trial’s console noise lands in agent_log.txt. Two managers in one with, comma-separated.
  • ThreadPoolExecutor(max_workers=5) as pool — exit waits for the pool to drain.
  • async with client.messages.stream(...) as stream — the async variant (§10); exiting it is what aborts the HTTP request on interrupt.

Writing one with @contextmanager — the part most engineers haven’t done. Decorate a generator that yields exactly once; code before the yield is __enter__, code after is __exit__, and the yielded value is what as binds:

# scout/tracing.py
@contextmanager
def span(name: str, span_type: str):
    tr = _current_trace.get()
    if tr is None:            # tracing disabled — still a valid context manager
        yield None
        return
    s = Span(name=name, span_type=span_type, parent_id=..., start=time.time())
    tr.spans.append(s)
    tr._stack.append(s.span_id)
    try:
        yield s               # the with-block runs here
    except Exception as e:
        s.error = repr(e)     # record...
        raise                 # ...but never swallow
    finally:
        s.end = time.time()
        tr._stack.pop()

Three details that make this production-grade rather than demo-grade:

  1. An exception in the with block is raised at the yield. If you want cleanup regardless, you must wrap the yield in try/finally yourself. Forgetting this is the classic @contextmanager bug — the stack would never pop and every later span would be misparented.
  2. Record-and-reraise: the except clause captures the error onto the span, then raise re-raises it unchanged. Observability must never change control flow.
  3. The degenerate path still yields (yield None): a generator-based context manager must yield exactly once on every path, which is why callers write if s is not None: before touching the span.

trace_run shows the paired pattern: acquire in __enter__ (set the contextvar), release in finally (flush to disk, reset the var). Nesting falls out for free — spans stack because with blocks nest.

8. Exceptions as control flow (and as model feedback)

Agent loops are unusually exception-rich, because a failed operation usually shouldn’t crash anything — it should become feedback the model can read. The Python mechanics Scout leans on:

Except-clause ordering is first-match-wins, so specific classes come first. The retry wrapper is the canonical example:

# scout/loop.py, _create_with_retry
try:
    return client.messages.create(model=model, **kw), model
except anthropic.RateLimitError as e:          # 429: honor retry-after
    ...
except anthropic.InternalServerError as e:     # 5xx incl. 529: maybe fall back
    ...
except anthropic.APIConnectionError as e:      # network: just retry
    ...
# anything else (BadRequest, Authentication...) propagates on purpose

A blanket except APIError would erase the retryable/non-retryable distinction — a malformed request would be retried four times before failing identically. The absence of a catch-all is a design decision; read missing except-clauses as intent.

Custom exceptions as typed refusals — security/paths.py defines class PathError(Exception) and raises it when a model-supplied path escapes the workspace. The tool layer catches broadly (except Exception as e: return _result(..., f"Tool raised: {e}", error=True)) and converts any tool failure into an error tool-result. So a PathError never crashes the loop; its message rides back to the model, which adapts. One broad catch is correct here, at the boundary where every failure has the same handling — the opposite of the retry wrapper, where failures diverge.

Raising to fail closed — the service’s gate is built with ask=_no_tty, a function whose entire body is raise EOFError. The gate already catches EOFError/KeyboardInterrupt around its ask call and returns “denied: no interactive user.” Injecting a raising callable reuses that path: headless approval fails closed with zero new code.

raise vs raise e vs exception state: bare raise inside an except re-raises the current exception with its traceback intact (used in span). Also note _create_with_retry stores err = e inside each clause and raises it after the loop — Python deletes the as e name when the except block exits, so you must capture it if you need it later.

9. Generators, and the agent loop as an event stream

You’ve met generator expressions (§5); a generator function is any function containing yield. Calling it runs nothing — it returns an iterator that executes lazily, pausing at each yield, resuming on the next request. ingest.chunk_text is a plain example; the interesting one is architectural.

Module 13’s central move is changing the loop’s type. The sync loop, run(), is an ordinary function: it blocks for the whole run, prints progress to a terminal nobody may be watching, and returns one Transcript at the end. A web service can’t consume that shape — the caller is a browser holding an SSE connection that needs events as they happen. So scout/scout_async.py rewrites the same loop as an async generator:

async def scout_loop(task, steer=None, ...):        # async def + yield = async generator
    ...
    for iteration in range(1, max_iters + 1):
        ...
        async for text in stream.text_stream:
            yield {"type": "token", "text": text}
        ...
        yield {"type": "tool_use", "name": block.name, "input": block.input}
        r = await asyncio.to_thread(dispatch, block, gate, steer)
        yield {"type": "tool_result", ...}
    ...
    yield {"type": "final", "text": redact(answer), "usage": {...}}
    return                                           # ends the stream (no value)

What to internalize:

  • async def + yield = async generator; consume with async for event in scout_loop(...). Same laziness, but the generator may await between yields.
  • return inside a generator ends iteration (raises StopIteration/StopAsyncIteration under the hood); it cannot carry a value to async for. The run’s “result” is just the last event — which is why the protocol has an explicit {"type": "final"} event rather than a return value.
  • Control inverts. run() owns its run; scout_loop is driven — it only executes while someone iterates it. The driver (service._drive) pumps events into an asyncio.Queue, and the SSE endpoint drains that queue to the wire. Generator = producer, queue = buffer, endpoint = consumer.
  • The event dicts (token / tool_use / tool_result / final / interrupted) are the protocol. Yield-per-step is what makes the agent legible to a UI; the same shape underlies every streaming agent API you’ll meet.

If you take one Python idea from this module, take this one: a long-running agent is naturally a generator — a process that emits a typed event stream and pauses between steps — and the sync-function version is the special case where you only care about the last event.

10. asyncio: one thread, many concurrent runs

asyncio is cooperative concurrency on one thread: functions declared async def are coroutines; await marks the points where a coroutine parks and lets the event loop run something else. No parallelism (still one thread) — the win is that waiting is free, and an agent service is almost all waiting (on the model API, on subprocesses, on clients).

The pieces Scout’s service uses, and why:

  • asyncio.create_task(coro) (service.start_run) starts a coroutine detached: the POST handler returns a session_id immediately while the run proceeds in the background. The returned handle is stored on the Run object — partly to await/cancel later, partly because of a real footgun: the event loop holds tasks weakly, so a task nobody references can be garbage-collected mid-run. Keep the handle.
  • asyncio.Queue — the async-native producer/consumer channel between the driver and the SSE endpoint. await queue.get() parks the endpoint until an event arrives; no polling, no locks.
  • await asyncio.to_thread(dispatch, block, gate, steer) — the bridge for blocking code. Scout’s tools are synchronous (file I/O, a bash command that runs 30 s); calling one directly inside a coroutine would freeze the event loop and every other run’s stream with it. to_thread runs it on a worker thread and awaits the result. Rule: anything blocking inside async def must be awaited or pushed to a thread.
  • async with / async for — the streaming API call is an async context manager yielding an async iterator (stream.text_stream). Exiting the async with early (on interrupt) is what aborts the underlying HTTP request — the context manager is the cancellation mechanism.
  • asyncio.CancelledError — _drive catches it, marks the run interrupted, and re-raises. Cancellation in asyncio is delivered as an exception at an await point, and swallowing it breaks the loop’s shutdown machinery. Catch to clean up, always re-raise.

One subtlety worth noticing because it’s counterintuitive: scout_loop’s interrupt flag is a threading.Event, not asyncio.Event — because dispatch runs on a worker thread (via to_thread) and run_bash polls the flag from that thread. asyncio.Event isn’t thread-safe and can’t be waited on from outside the loop. When one object must be visible to both worlds, the threading primitive is the right one.

11. Threads, queues, and events: steering a live run

The interactive CLI (Module 12) is where classic threading shows up, and Scout keeps it deliberately minimal: no shared mutable structures guarded by locks, just message passing over queue.Queue and signaling over threading.Event — both thread-safe by construction.

# scout/steering.py
class Steerable:
    def __init__(self):
        self.inbox: queue.Queue = queue.Queue()   # user messages typed mid-run
        self.interrupt = threading.Event()        # "stop what you're doing"

The CLI (loop.main) starts one daemon thread that owns stdin for the whole session (threading.Thread(target=reader, daemon=True).start() — daemon means it won’t block interpreter exit, right for a thread parked forever on input()). Typed lines are routed by state: to the gate’s answer queue if the gate is waiting (gate_waiting Event), to the live run’s inbox if one is active, else treated as the next task. The agent loop, on its own thread and its own schedule, calls steer.drain() at loop boundaries and steer.interrupt.is_set() between tool calls. Producer and consumer never share anything but the queue and the flag.

Three other things to know:

  • threading.Lock does appear once — scout/idempotency.py wraps its check-then-write in with _lock: because dispatch can run on multiple worker threads and “read the store, maybe append” is a race without it. Note the lock is a context manager: acquire/release via with, exception-safe.
  • ThreadPoolExecutor (orchestrator.py) is the easy parallelism for I/O-bound work: with ThreadPoolExecutor(max_workers=5) as pool: findings = list(pool.map(research_worker, sub_qs)) fans five API-calling workers out in parallel. The GIL is irrelevant here — the threads spend their lives blocked on network I/O, where the GIL is released. (For CPU-bound work threads would buy nothing; that’s what processes are for.)
  • Signal handlers vs KeyboardInterrupt — Ctrl-C default behavior raises KeyboardInterrupt wherever the main thread happens to be executing — mid-SDK-read, mid-list-append — which tears the run down messily. loop.main installs signal.signal(signal.SIGINT, on_sigint) instead: the handler just sets steer.interrupt (or re-raises to quit when idle), converting an asynchronous detonation into a flag checked at safe points. This “signal → flag → poll at boundaries” conversion is the standard shape for interruptible long-running work. Handlers run on the main thread only, between bytecode instructions — keep them tiny.

12. Subprocesses, process groups, and process-level isolation

Scout shells out constantly — the run_bash tool, the Docker sandbox, verification, the eval harness — and uses two distinct subprocess styles for two distinct needs.

subprocess.run — when you can wait: subprocess.run(cmd, shell=True, cwd=..., capture_output=True, text=True, timeout=120) blocks until done and gives you proc.returncode, proc.stdout, proc.stderr (text=True decodes to str). Used where blocking is fine: _run_verify, the pytest grader. Catch subprocess.TimeoutExpired and convert to a result — a hung check must not hang the loop.

Popen + poll — when you need to intervene mid-flight: run_bash must honor a user interrupt while the command runs, so it can’t block in run(). Instead (tools._run_bash_unsafe, and the same shape in security/sandbox.py):

proc = subprocess.Popen(command, shell=True, stdout=buf, stderr=subprocess.STDOUT,
                        text=True, cwd=WORKSPACE, start_new_session=True)
while proc.poll() is None:                  # None = still running
    if cancel is not None and cancel.is_set():
        _kill_group(proc); return "terminated by user interrupt"
    if time.monotonic() > deadline:
        _kill_group(proc); return "timed out"
    time.sleep(0.05)

Four hard-won details, each of which is a real bug if you miss it:

  1. Output to a temp file, not stdout=PIPE. An OS pipe buffer is ~64 KB; if nobody reads it, a chatty command fills it and blocks forever — deadlocked against your poll loop, which is waiting for exit. A file has no such limit; seek(0) and read after exit.
  2. start_new_session=True + os.killpg. shell=True means your child is a shell whose children do the work (sleep 120 in date > f && sleep 120). Killing only the shell orphans them. start_new_session makes the shell a process-group leader, and os.killpg(proc.pid, SIGTERM) signals the whole group.
  3. Escalate TERM → KILL (_kill_group): send SIGTERM, proc.wait(timeout=2), and only then SIGKILL. Give processes a chance to clean up; don’t let them decline.
  4. time.monotonic() for deadlines, never time.time() — wall-clock time can jump (NTP); monotonic can’t.

shlex: quoting untrusted strings into shells. shlex.quote(p) makes an arbitrary path safe to interpolate into a shell command (_pick_verify_cmd); shlex.split(seg) tokenizes a command line respecting quotes — the basis of the read-only-bash classifier in security/policy.py. If you build shell strings with f-strings and no shlex.quote, a filename with a space (or worse) breaks you.

Processes as the isolation boundary. The eval harness runs every trial as a subprocess (python harness.py --worker <json>, re-invoking sys.executable on its own file — see the if sys.argv[1] == "--worker" branch in __main__). Two reasons, both instructive: (1) Scout’s workspace is a module global (scout.tools.WORKSPACE), so concurrent trials in one process would trample each other — module globals are process-scoped state, and the honest fix for parallelism is one process each; (2) a subprocess gives a hard timeout with a guaranteed kill — a hung trial becomes a failed record, never a hung suite. (The docstring also notes ProcessPoolExecutor deadlocked intermittently on macOS spawn — a reminder that plain subprocess is often the most robust multiprocessing there is.)

The three substrates, in one line each: asyncio = many waiting I/O tasks, one thread, cheapest; threads = blocking I/O made concurrent, shared memory, needs care; processes = true isolation and parallelism, communicate via files/pipes/argv, most expensive. Scout uses all three, each where its trade-off wins.

13. Modules, imports, and import-time landmines

Python executes a module’s top level the first time it’s imported, then caches it (sys.modules). Scout leans on this — and gets bitten by it — in ways you should recognize:

  • Import-time side effects and ordering. scout/llm.py runs load_dotenv() before anthropic.Anthropic() at module top level, because the client reads the API key from the environment at construction. Reorder those two lines and everything breaks with a missing-key error. When you see top-level statements in a specific order, assume the order is load-bearing.
  • Module globals are ambient process state. tools.WORKSPACE, loop._journal, loop._human_responder, retrieval._collection — all module-level, all effectively singletons per process. Convenient (no threading of parameters through ten layers), with the cost you’ve now seen twice: parallelism must be process-per-run. Scout’s comments flag this trade-off explicitly every time; copy that habit.
  • Lazy imports for heavy optional deps. retrieval.py imports voyageai and chromadb inside functions, cached in _vo/_collection globals, so from scout import retrieval (which loop.py does unconditionally) stays fast and doesn’t require those packages until retrieval is actually used. Import-inside-function is also the standard circular-import escape hatch: security/gate.py imports scout.tools inside _diff_preview because the gate loads before scout does.
  • sys.path surgery. Scout isn’t an installed package, so files that need cross-package imports do sys.path.insert(0, repo_root) before from security.paths import safe_path (see tools.py, tracing.py, evals/harness.py). The # noqa: E402 comments acknowledge the style violation (import not at top of file) that this forces. It works; a pyproject.toml + pip install -e . is the grown-up alternative — but recognize the pattern, because half the research code you’ll read does exactly this.
  • if __name__ == "__main__": — you know it; note the harness’s twist of dispatching on sys.argv[1] == "--worker" inside that block, making one file both the suite driver and the per-trial worker.

14. Paths, files, and durability: resolve(), JSONL, fsync

pathlib over os.path. Modern code builds paths with the / operator (SESSIONS_DIR / f"{session_id}.jsonl"), reads with path.read_text(), globs with path.glob("*.jsonl"), and gets stem/parent/suffix as attributes. Scout mixes both styles (older modules use os.path); write new code with pathlib.

resolve() vs abspath is a security distinction, not a style one. os.path.abspath normalizes .. lexically — it never touches the filesystem. Path.resolve() also follows symlinks to the real target. The difference is an exploit: a symlink planted inside the workspace (evil -> /etc) passes an abspath-prefix check, then open() dereferences it and reads the host file. security/paths.safe_path resolves both the root and the candidate, then checks containment on the dereferenced result:

root = root.resolve()
candidate = (root / user_path).resolve()
if candidate != root and root not in candidate.parents:
    raise PathError(f"path escapes project root: {user_path!r}")

Two pathlib behaviors it exploits: joining with an absolute path replaces the left side entirely (root / "/etc/passwd" → /etc/passwd, which then fails containment — absolute paths are rejected for free), and candidate.parents is the ancestor sequence, giving a correct containment test without string-prefix hacks (startswith("/work") would wrongly pass /work-evil).

Append-only JSONL + flush + fsync is Scout’s entire durability layer (scout/checkpoint.py):

with open(log_path(session_id), "a", encoding="utf-8") as f:
    f.write(json.dumps(event) + "\n")
    f.flush()
    os.fsync(f.fileno())

Know the three buffer layers: your write() fills a Python buffer; flush() pushes it to the OS; only os.fsync(fd) forces the OS to put it on disk. Without the fsync, a machine crash can lose a step the loop already acted on — which breaks the “durable, then proceed” invariant the whole resume design rests on. The read side handles torn writes: a half-written final line (crash mid-append) is dropped as “a step that never completed”; a torn line anywhere else is real corruption and raises. One file format, one invariant, and you get crash-resume — Module 13 builds on exactly this.

(tempfile.mkdtemp / TemporaryFile round this out: fresh disposable directories per eval trial, self-deleting buffers for subprocess output.)

15. contextvars: implicit context without globals

Last, the most obscure construct in the repo — and the one most likely to be new even to strong Python engineers. Scout’s tracing needs the “current trace” visible to span() calls buried many layers deep, without threading a trace parameter through run → call_model → _create_with_retry. A plain module global would work for one run at a time — but breaks the moment two runs share a process, and asyncio makes that the normal case (§10: many concurrent runs, one thread — so even thread-locals don’t help; the tasks interleave on the same thread).

contextvars.ContextVar is the primitive built for this: a variable whose value is scoped to the current execution context, which Python maintains per-thread and per-asyncio-task:

# scout/tracing.py
_current_trace: contextvars.ContextVar = contextvars.ContextVar("trace", default=None)

@contextmanager
def trace_run(name: str):
    tr = Trace(name)
    token = _current_trace.set(tr)     # set returns a token...
    try:
        yield tr
    finally:
        tr.flush()
        _current_trace.reset(token)    # ...which restores the PREVIOUS value

set() returns a token; reset(token) restores whatever was there before — so nested trace_runs unwind correctly, like a stack. Anything called underneath — however deep — does _current_trace.get() and finds the right trace, and span()’s if tr is None: yield None makes the whole tracing layer a no-op when nothing set the var. This is the same mechanism every serious observability SDK (OpenTelemetry included) uses for context propagation. If you’ve ever wondered how a tracing library “just knows” the current span with no arguments passed — this is how.
