Module 13 — Frontier & Advanced Patterns

You have built an agent (Modules 1–6), evaluated it (Module 8), instrumented it (Module 9), made it reliable and cheap (Module 10), secured it (Module 11), and given it durable execution (Module 12). You can ship the thing. This module is the one that goes stale fastest, and that is exactly why it exists: the field is moving, and the most valuable skill you can leave this course with is a map — a way to read the frontier so you can tell which new capability is real, which is demo-ware, and which of your hard-won harness code is about to be deleted by the next model.

The honest framing up front: most of what gets called “the frontier” in agents right now is one of two things. Either it is a genuine capability shift — agents completing longer tasks, models trained against their own tools — or it is a packaging shift: the same inner loop from Module 3, wrapped in a new product surface (a standing identity, a cron schedule, an outer restart loop) and given a more ambitious name. Both matter. But they fail differently, and conflating them is how teams ship a “digital employee” that demos beautifully and drifts into confidently doing the wrong thing for six hours overnight. This module is about telling them apart.

Learning objectives

By the end of this module you will be able to:

  • Distinguish the three things people mean by “long-running agent” — long-horizon reasoning, long-running execution, and persistent agency — and reason about each separately.
  • Explain the outer loop and the “Ralph Wiggum” technique, why the dumbest version of it accidentally gets the architecture right, and what “loop engineering” makes you design explicitly.
  • Cite the one quantitative capability trend worth anchoring on (METR’s task-length doubling) and state its honest caveat.
  • Predict which parts of your harness will appreciate and which will depreciate as models improve, and invest accordingly.
  • Place computer use and MCP correctly in your toolbox — what each is for, and where each is still brittle.
  • Name the binding constraints on long-running agents (verification, drift, the human-inspection problem) and explain why they are harder than raw capability.

1. From task to role: the three senses of “long-running”

The phrase “long-running agent” is doing too much work. It bundles three different engineering problems that happen to co-occur, and you cannot design well until you split them:

  1. Long-horizon reasoning — one big task that requires many coherent steps. “Migrate this service from REST to gRPC.” The hard part is staying on-goal across hundreds of model turns without losing the thread. This is a model-capability problem, and it is the one METR measures (§3).

  2. Long-running execution — the operational problem of staying alive: the process survives restarts, resumes after a crash, doesn’t lose state when a tool call hangs for an hour. This is durable execution — Module 12 — and it is solved infrastructure (initializer/worker patterns, hosted loops, checkpointing). It is plumbing, and good plumbing.

  3. Persistent agency — a standing identity with accumulated memory and an open-ended charter, operating across many sessions over days and weeks. Not “do this task” but “be the on-call triage agent.” This is the “AI employee” / “digital worker” framing: a company gives an agent a name, credentials, a permission scope, and a human manager, and lets work arrive at it over time.

Most of the breathless writing is about (3), but (3) is mostly built out of (1) and (2). An honest read is that persistent agency today is partly aspirational — the demos are real, the production deployments are narrow, and the gap between them is the subject of §7.

What is actually architecturally new

If you strip the marketing, persistent agency changes three concrete things about how you build:

Work arrives over time. A task agent is a function: input → trajectory → output → exit. A role agent is a service. It mostly sits blocked on the outside world — a new ticket, a scheduled tick, a webhook — and wakes to handle an event. The LLM is no longer “the program”; it is the handler logic the service invokes when an event arrives. This is the most useful reframe in the whole module: a persistent agent is an event-driven service where an LLM decides the handler body. Everything you know about event-driven services — idempotency, queues, backpressure, dead-letter handling — applies directly and is mostly absent from “agent” tutorials.

The human moves from the loop to the exception path. In an interactive agent (Module 3), a human is in the loop on every turn. In a role agent, the human is out of the loop by design — the whole point is unattended operation — and only re-enters on an exception: the agent escalates because it is stuck, hit a confirmation gate (Module 11’s blast-radius controls), or tripped a drift detector. Designing the exception path well is now the high-leverage work, because it is the only place a human can correct a run before damage compounds.

Continuity lives in durable state, not context. A conversation’s continuity lives in its context window. A role agent outlives any single context window — it gets compacted (Module 4), restarted, run fresh. So “what this agent is, what it has learned, what it is responsible for” must live in durable external state (a memory store, a database, the filesystem), not in the transcript. The transcript is ephemeral scratch; the durable state is the agent. Get this backwards and your agent forgets who it is every time the context compacts.

A worked example: the recruiting-coordinator agent

Make it concrete. You are asked to build an agent that owns “first-round recruiting coordination” — not a task, a charter. It should monitor an inbox, schedule screens, nudge stalled candidates, and escalate edge cases.

As a service, its shape is:

  • Triggers (work arrives): a new application webhook, a candidate reply, a daily 9am “chase stalled threads” tick.
  • Durable state (the agent is this): per-candidate status, what’s been promised, scheduling constraints, a running log of decisions. Not the context window.
  • Handler (the LLM call): given this event plus the relevant slice of durable state, decide the next action — draft a reply, propose times, or escalate.
  • Blast-radius gates (Module 11): “send an email to a candidate” is irreversible and outward-facing, so it goes behind a confirmation policy or a strict template, not raw model output.
  • Exception path: candidate asks something off-script, or a scheduling conflict can’t be resolved → stop and ping the human recruiter with context.

Notice what dominates: almost none of this is “prompt the model better.” It is event plumbing, state design, and gate placement. The model is one component. That ratio — mostly systems, a little model — is the signature of a real persistent-agent build, and the inverse ratio is the signature of a demo.

📖 Why this is the flagship example. Role-based / recruiting agents recur as the canonical “AI employee” demo precisely because recruiting coordination is a long-lived charter with discrete events, low-but-nonzero blast radius, and a natural human-escalation path. It is the easiest place to make persistent agency look solved — which is also why it is the easiest place to ship something that drifts.

2. The outer loop and “loop engineering”

Module 3 built the inner loop: model → tool → result → model, iterating until the task is done within a single context window. The frontier added a second loop around it.

The outer loop is brutally simple: restart the agent on the same goal, repeatedly, until the goal is met. Fresh process, fresh context, same objective.

The Ralph Wiggum technique

The purest expression of this — named by Geoffrey Huntley after the Simpsons character, with affection — is literally:

while :; do cat PROMPT.md | claude -p ; done

Run the agent against a prompt. When it finishes (or dies, or rots), the loop just runs it again. Forever, or until you stop it. The prompt says, roughly, “read the current state, figure out what’s left to do, do the next increment, update the state.” That’s the whole technique.

It looks like a joke. It accidentally gets the long-running architecture right, for three reasons that are worth internalizing because they are the same three reasons §1’s persistent agents work:

  • Fresh context each iteration = no rot. Module 4’s nemesis is context degradation — the slow accumulation of stale tool output, contradictory notes, and goal reinterpretation that builds up over a long single run. The outer loop sidesteps it entirely: every iteration starts from a clean window. There is nothing to rot because nothing carries over in context.
  • State lives in the filesystem = durable. What does carry over is on disk: a TODO.md, a progress file, the actual code being written. This is Module 12’s durable-state principle arrived at by the dumbest possible route. The filesystem is the checkpoint.
  • The model re-derives “what’s next” from ground truth. Because it can’t rely on a remembered plan (there is no memory across iterations), each pass re-reads reality — the current files, the current test output, the current todo list — and decides the next step from that. It is continuously re-grounding against the world instead of against its own increasingly-unreliable narrative of the world.

That third point is the deep one. Goal drift (§7) is largely a story about an agent trusting its own stale summary of where it is. The Ralph loop can’t drift the same way, because it has no stale summary to trust — it has to look.

The technique spread through YC startups precisely because it is so cheap to try and works embarrassingly well for grind-it-out tasks (build this CLI, port this module, get this test suite green). Anthropic eventually shipped an official plugin around the pattern. None of that makes it magic — it burns tokens, it can loop forever on a goal it can’t actually complete, and it has no taste — but it is the existence proof that the architecture of long-running agents is simple. The hard parts are elsewhere.

Loop engineering

Once you take the outer loop seriously, the unit of design stops being the prompt and becomes the loop. “Loop engineering” is just naming the four questions you must now answer explicitly:

  1. What persists across iterations? The durable state. Exactly which files / records carry the agent’s progress, and what format keeps them legible to a fresh-context model.
  2. What is verified each pass? Before an iteration declares progress, what external check confirms it? Tests pass, the file exists, the API returns 200. This is the anti-drift mechanism — see §7.
  3. When does it terminate? A naive while :; never stops. A real loop has a completion gate (programmatic or LLM-judged — Module 8) and a budget/iteration cap so a stuck goal doesn’t run up an infinite bill.
  4. When does it escalate? If the loop makes no progress for N iterations, or repeats the same failed action, it should stop and ask a human — the exception path from §1.

🛠️ Notice these are the same four knobs that define a persistent agent (§1: triggers, state, termination, escalation). The outer loop and the role agent are the same architecture at different cadences — one restarts in a tight loop, the other wakes on events over days. Learn the loop and you’ve learned both.

This shows up in product surfaces as goal-directed primitives — e.g. a /goal command that hands the loop an objective and lets the agent decide when it’s met rather than counting turns — and scheduled / background agents that fire the loop on a cron or a queue. Those are just §1’s “work arrives over time” with a UI on it.

✅ When you hear “agent,” ask which loop. Most clever-prompt tricks live in the inner loop and depreciate (§4). The durable wins — what persists, what’s verified, when it stops — live in the outer loop and they are yours to engineer, not the model’s to obsolete.

3. The capability trend worth anchoring on

If you anchor on one number from the frontier, anchor on this one. METR (Model Evaluation & Threat Research) measures the length of task an agent can complete autonomously — operationalized as the human-time-to-complete of tasks the model can finish at a given reliability. Their headline finding: that length has been doubling roughly every seven months, and recent data suggests the doubling time is shortening toward ~4 months. The 50%-reliability time horizon sits in the tens of minutes and is climbing.

Why this is the right thing to track: it is a capability measurement that maps directly onto the engineering question you actually care about — “how much can I hand the agent before it falls apart?” A task-length horizon of ~minutes means agents reliably do bounded sub-tasks and you orchestrate; a horizon of hours means you can hand off genuinely long-horizon work (§1, sense 1). The doubling trend is the single best forecast of how much harness scaffolding you’ll be able to delete next year (§4).

Now the caveat, and it is load-bearing: reliability over long horizons lags raw capability badly. The “50% reliability” qualifier matters enormously. An agent that completes a 1-hour task half the time is a research result; it is not something you deploy unattended against a 1-hour task, because the other half of the time it fails — and, worse, it often fails silently, by drifting (§7) rather than crashing. The headline number describes a frontier of what is possible at coin-flip odds, not what is trustworthy. The gap between “an agent can sometimes do this” and “I will let an agent do this overnight without watching” is the entire subject of §7, and it is widening even as the headline number improves.

📖 Track the trend; do not deploy the trend. The doubling curve tells you where to place bets for next year’s architecture. It does not tell you that this year’s agent can be trusted with this year’s longest measured task.

4. RL-trained agents and the disappearing harness

Here is the structural force that will obsolete more of your code than any single feature: models are increasingly trained against their own harnesses.

Early agents were a frontier model wrapped in a thick scaffold of human-engineered glue — retry logic, retrieval pipelines, output parsers, tool-format coaxing, prompt patterns to stop the model doing dumb things. Each of those scaffold components encodes an assumption about what the model can’t do. The output parser exists because the model used to emit malformed JSON. The retrieval scaffold exists because the model couldn’t decide what to fetch. The “CRITICAL: you MUST use the tool” prompt exists because the model under-called tools.

Reinforcement learning is now moving those capabilities into the weights. Research lines like Search-R1 and ReSearch train models to do agentic retrieval — to decide when and what to search — as a learned behavior rather than a scaffolded one. The Anthropic models you’ve used throughout this course are trained against tool-use formats directly. The general direction is unmistakable: capability migrates from the harness into the model.

The consequence is a one-line principle with enormous practical weight:

Every harness component encodes an assumption about what the model can’t do — and that assumption gets invalidated as models improve.

So the strategic question for an engineer is no longer “what scaffold makes this work?” It is “what am I building that appreciates as models get better, versus what depreciates?”

Depreciates (the model absorbs it) Appreciates (the model can’t give you this)
Prompt tricks that coax behavior (“you MUST…”) Your evals — the ground-truth definition of “good” for your task (Module 8)
Output parsers / format-repair logic Your proprietary data and the pipelines that produce it
Retrieval scaffolding the model can now drive Your integrations — the connections to your systems, with auth and side effects
Tool-format coaxing Your guardrails — the blast-radius and trust controls (Module 11)
Multi-step decomposition the model now does itself Your domain context and the human-in-the-loop interfaces around it

The depreciating column is real work you may need today — Module 10’s schema-validate-and-retry exists because today’s models still occasionally fail. But it is a wasting asset. Build it deliberately, comment it as a model-gap workaround, and expect to delete it. The appreciating column is where durable engineering value lives: a model getting smarter makes your eval suite, your data, and your secure integrations more valuable, because there’s a more capable engine to point at them.

🛠️ A useful habit: when you write a piece of harness, label it. Is this compensating for a current model limitation (depreciating — write it cheap, plan to delete it), or is it durable infrastructure (appreciating — invest in it)? The teams that stay ahead spend their best engineering on the second column and treat the first as disposable.

✅ This is also a defensibility argument. “Our agent has a clever prompt” is not a moat; the next model erases it. “Our agent has ten years of labeled domain data, a battle-tested eval harness, and audited integrations into systems no one else can touch” is a moat that grows with model quality.

5. Computer use: the universal-interface bet

Computer use lets an agent operate a graphical interface the way a person does: it receives a screenshot, reasons about it, and emits mouse and keyboard actions (click here, type this, scroll). Anthropic’s computer use and OpenAI’s computer-using-agent are the two flagship implementations; Claude models support it as a client-side tool (you run the screen; the model decides the actions).

The bet behind it is large and worth stating plainly: if an agent can use a screen, it can use any software — no API required. Every legacy system, every internal tool with no integration, every SaaS app that never shipped a usable API becomes reachable through the one interface every application already has: the GUI. That is a genuinely universal adapter, and for the long tail of software that will never expose an API, it may be the only adapter.

How it works, mechanically, is just the Module 3 loop with vision and a different action space:

screenshot → model reasons → action (click/type/scroll) → new screenshot → …

The model never touches an API; it looks at pixels and moves a cursor.

And now the honest part. Computer use today is powerful, slow, and brittle. It is slow because every step is a full screenshot round-trip plus vision processing — seconds per click, where an API call is milliseconds. It is brittle because pixel-level grounding is error-prone: a moved button, an unexpected modal, a slow-loading page, and the agent clicks the wrong thing or stalls. The error rate per action, compounded over a multi-step GUI flow (Module 10’s 0.95^N arithmetic), gets ugly fast. It is also high blast-radius by nature — it’s driving a real UI with real buttons.

Where it fits: reach for computer use when there is no API and the alternative is a human doing the clicking. It is a last-resort universal adapter, not a default. If a tool exposes an API or an MCP server (§6), use that — it is faster, more reliable, and easier to gate. Computer use earns its slot when the only interface is the screen. Treat it as the brilliant, twitchy specialist it is, not the workhorse.

📖 The capability trend (§3) bears directly on computer use: as models get better at vision grounding and longer horizons, the brittleness recedes and the universal-adapter bet looks better. It is a “wait and watch the curve” capability — under-powered for most production today, plausibly transformative on a 12–24 month horizon.

6. MCP and the tool ecosystem

The Model Context Protocol (MCP) is the converging interoperability standard for connecting agents to tools and data — the “USB for agent tools.” The problem it solves is combinatorial: before MCP, every (agent harness × tool) pair needed bespoke integration glue. MCP makes tools and data sources speak one protocol, so you write a tool/data server once and use it across any MCP-speaking harness — Claude, other models, IDEs, custom agents.

The result is an ecosystem of MCP servers — GitHub, Slack, databases, search, internal systems — that you can compose into an agent’s tool surface without writing per-harness adapters. For a team, this is leverage: expose your internal systems as one MCP server and every agent surface you adopt can use them.

Two practical notes for when your tool count gets large:

  • Deferred / dynamic tool loading. Loading hundreds of tool schemas into context upfront is wasteful and degrades tool selection (Module 2’s “too many tools confuse the model”). The pattern is tool search: keep most tools’ schemas out of context and let the model search/discover the few it needs per request, appending their schemas dynamically. Crucially, well-designed dynamic loading appends schemas rather than swapping them, which preserves the prompt cache (Module 10) — a detail that matters for cost at scale.
  • Security caveats (Module 11, applied). MCP’s strength — easy composition of third-party servers — is also its supply-chain risk. An MCP server is code (or a remote endpoint) you are granting into your agent’s trust boundary. A malicious or compromised server can exfiltrate whatever the agent can see, inject instructions via tool output (prompt injection through tool results), or abuse credentials you handed it. Treat every MCP server the way Module 11 taught you to treat any dependency: vet the source, scope its credentials minimally, isolate its egress, and never assume tool output is trusted text. The convenience of “just add this server” is exactly the attack surface.

✅ MCP is the integration layer that appreciates (§4): it is durable plumbing into your systems, not a prompt trick. Build your internal capabilities as MCP servers and that investment survives every model upgrade — and works across whatever harness wins.

7. The open problems: easy to build, hard to trust

This is the section that matters most, because it is where the marketing and the engineering reality diverge hardest. The blunt version:

Long-running agents are easy to build and hard to trust. Verification and the human-agent interface — not raw capability — are the binding constraints.

You can stand up a “persistent AI employee” in an afternoon (§1 + §2 give you the whole architecture). It will demo beautifully. Then you let it run unattended for hours and it drifts — and the failure modes below are why “it demoed well” tells you almost nothing about whether you can trust it.

Goal drift

The central failure of long unsupervised runs. The agent slowly stops doing what you asked and starts doing something subtly adjacent, while remaining fluent and confident the whole time. Three mechanisms:

  • Reinterpretation across compaction. Every time the context compacts (Module 4), the goal gets re-summarized — and summaries lose nuance. “Refactor the auth module without changing behavior” becomes “refactor the auth module” becomes “improve the auth module” over successive compactions, and now the agent is rewriting behavior you told it to preserve. Each compaction is a lossy generation of telephone, and the goal degrades a little each time.
  • Error accumulation in persistent state. A persistent agent’s durable state (§1) is supposed to be its strength, but a bad entry compounds. One wrong fact written to a memory store — a mislabeled candidate status, an incorrect assumption recorded as fact — gets read back as ground truth on every subsequent iteration and silently warps everything downstream. The durable state is only as good as its worst write.
  • Confidently working on the wrong thing. The most dangerous compound of the above: the agent is productive and fluent while building the wrong thing. It’s not erroring. It’s not stuck. It’s cheerfully spending six hours and a real budget perfecting a solution to a problem you didn’t have. Nothing in the transcript looks alarming.

Verification at scale: who authors success criteria?

The only defense against drift is verification — but verification has a foundational hole. Who writes the success criteria, and against what are they grounded?

  • If a human authors them, you have Module 8’s evals, and they’re trustworthy but they don’t scale to every sub-goal a long-horizon agent invents along the way.
  • If the agent authors its own success criteria, you have a circularity problem: an agent that has drifted will write success criteria that match where it drifted to, and then triumphantly verify against them. Self-graded homework. The agent that’s confidently wrong (§above) is also confidently right about having succeeded.

The partial answer is to ground self-set criteria in external signals — tests that actually run, APIs that actually return, the world pushing back (this is why the Ralph loop’s per-pass verification, §2, matters; it re-grounds against reality, not against the agent’s narrative). But “ground everything in an external check” is much easier to say than to engineer for an open-ended charter, and it is an open problem, not a solved one.

The human inspect/correct problem

When a long run is going wrong, you want to look inside and fix it. Both halves are genuinely hard.

  • Inspection of a 6-hour, post-multiple-compaction run is not like reading a 20-line transcript. The thing you need to catch — the moment the goal quietly reinterpreted — may be buried in a compaction boundary you can’t even see anymore.
  • Correction is harder still. Mutating a running agent’s state is dangerous: edit its durable state mid-run and you risk corrupting it in ways the agent can’t reconcile, because it has in-flight assumptions built on the old state. The emerging discipline is to steer by appending events, not by editing state — you don’t reach in and rewrite the agent’s memory; you send it a new instruction/event (“actually, stop and reconsider X”) and let it reconcile, the same way you’d correct a service by sending it a message rather than reaching into its database. (This is exactly why §1’s “the human is on the exception path” and Module 12’s event-sourced state matter: append-only correction is the only safe correction.)

Blast radius and trust

Tie it back to Module 11. An unattended agent’s mistakes are unattended too. A drifted agent with email access sends drifted emails. A drifted agent with deploy access deploys the wrong thing. The longer and more autonomous the run, the larger the blast radius of any single drift — and the later you’ll notice. This is why the gates (§1, Module 11) live on irreversible, outward-facing actions specifically: those are the ones where unattended drift becomes an incident instead of a wasted iteration.

Where this leaves you

The capability frontier (§3) is racing ahead. The trust frontier — verification, drift detection, inspectability, safe correction — is lagging, and it is the actual bottleneck for production long-running agents. A team that obsesses over “can the model do a longer task?” and ignores “can I tell when it’s quietly doing the wrong one?” will ship something that demos and then drifts.

📖 The durable skill — the thing this whole course has been building toward — is taste for where the model still needs scaffolding, and where it no longer does. You cannot get that taste from a changelog or a benchmark. You get it from reading transcripts: watching real runs, seeing exactly where this model drifts, over-thinks, under-tools, or confidently fabricates, and where it has quietly gotten good enough that your old scaffold is now just in the way. That is why Module 9’s observability is the foundation for everything here. The frontier changes; the skill of reading what your agent actually did, and adjusting, does not.

🛠️ Exercise: build an outer loop for Scout

Smaller and exploratory — the goal is to feel the long-running architecture and its failure modes firsthand, not to ship anything.

(a) Build a Ralph-style loop. Write a script that repeatedly runs Scout against a goal in PROMPT.md, with all state on the filesystem (a TODO.md or progress.json), until a completion condition or a max-iterations / budget cap. Each iteration must: start with fresh context, read the state file, do one increment, update the state file, exit. The loop, not the model, owns continuity.

# Sketch — the loop is the unit of design (§2). Scout is your agent from earlier modules.
import json, pathlib, anthropic

client = anthropic.Anthropic()
state_path = pathlib.Path("progress.json")
MAX_ITERS, stuck_limit = 25, 3
stuck = 0

def load_state():
    return json.loads(state_path.read_text()) if state_path.exists() else {"todo": [], "done": []}

for i in range(MAX_ITERS):
    state = load_state()                       # durable state, NOT context
    goal = pathlib.Path("PROMPT.md").read_text()

    # Fresh context every pass — the model re-derives "what's next" from the state file (§2).
    result = run_scout_one_increment(          # your Module-3 inner loop, single increment
        goal=goal, state=state,
        model="claude-opus-4-8",
        thinking={"type": "adaptive"},         # adaptive thinking — no budget_tokens on Opus 4.8
    )
    write_state(result.updated_state)          # persist progress to disk

    if goal_met(result):                       # (b) termination gate — programmatic or LLM-judge
        print(f"done in {i+1} iterations"); break
    if made_no_progress(state, result):        # (b) escalation: stuck N times → ask the human
        stuck += 1
        if stuck >= stuck_limit:
            escalate_to_human(state); break
    else:
        stuck = 0

(b) Add the gates. A termination check — an LLM-judge (callback to Module 8) or a programmatic “is the goal met?” test — and an escalation hook: if the loop makes no progress stuck_limit times in a row, stop and ask the human instead of grinding forever. These are two of the four loop-engineering knobs from §2.

(c) Give it a real multi-step goal. Something with genuine sub-structure: “build a small CLI tool with passing tests” or “research X and produce a cited report.” Watch it grind across iterations.

(d) Observe and document the drift. This is the actual point. Where does it lose the thread? Does it repeat work it already finished (state-file format too vague to read back cleanly)? Does it confidently mark something done that isn’t? Does it reinterpret the goal as the TODO.md gets summarized? Write down each failure and map it to a mechanism in §7. You will learn more from one drifted run you diagnosed than from re-reading §7.

(e) Stretch — add a fresh-context verifier. Each iteration, spawn a separate sub-agent with a clean context whose only job is to check the current state against the original goal in PROMPT.md and flag drift. Note how a fresh-context check catches reinterpretation that the working agent — carrying its own drifted narrative — cannot see in itself. That asymmetry is the §7 verification problem in miniature.

Real production issues

  • Fragile loops that drift under long unsupervised runs. The central one. The loop demos perfectly in a 5-minute run and drifts in a 5-hour one. Test at production duration, not demo duration — short runs systematically hide the failure mode.
  • Goal reinterpretation across compaction boundaries. “Don’t change behavior” survives turn 1 and is gone by compaction 4. Pin the immutable goal somewhere that never gets compacted (a re-read-every-pass PROMPT.md, not the transcript), and re-ground against it each iteration.
  • Error accumulation in persistent state. One bad memory write becomes ground truth forever. Treat writes to durable state as high-stakes: validate before persisting, version it (Module 12), and make it possible to audit and redact a bad entry.
  • Confidently working on the wrong thing for hours. No error, full fluency, real budget, wrong deliverable. Only external verification catches this — the agent’s own confidence is worthless as a signal.
  • Outward-facing unattended mistakes (blast radius). A drifted agent’s irreversible actions are also unattended. Gate irreversible/outward actions behind confirmation or strict templates (Module 11); never wire raw model output straight to send/deploy/delete in an unattended loop.
  • The difficulty of inspecting/correcting a live run. You can’t easily read a 6-hour post-compaction run, and editing its state mid-flight corrupts it. Build inspection in from the start (Module 9), and correct by appending events, not mutating state.
  • Depreciating scaffolding. Today’s clever harness trick is deleted by next quarter’s model — and worse, an obsolete scaffold can fight a now-capable model (the “you MUST use the tool” prompt makes a model that now self-decides over-call it). Label scaffolding as a model-gap workaround; re-evaluate it on every model upgrade.
  • Computer-use brittleness. Slow, pixel-fragile, high blast radius. Don’t put it on the critical path of a production flow that has any API alternative; reserve it for the no-API long tail and budget generous retries.
  • MCP supply-chain risk. A third-party MCP server is inside your trust boundary. Vet it, scope its credentials, isolate egress, and treat its output as untrusted (prompt-injection vector) — Module 11 applied.
  • The demo-to-production gap. The honest closing issue: an impressive demo and a trustworthy production agent are different artifacts. The bottleneck between them is verification and the human interface, not capability. Budget your engineering accordingly — most of it goes into trust, not into making the model do more.
