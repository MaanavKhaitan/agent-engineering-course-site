Module 09 — Observability, Tracing & Debugging

You already know distributed tracing. You know what a span is, you know context propagation, you know how to read a flame graph and spot the slow downstream call. This module is not going to re-teach any of that. It’s going to show you what’s different when the thing you’re instrumenting is an agent — and why the observability stack you’d reach for on a normal service is necessary but nowhere near sufficient.

Here’s the thesis up front, because the rest of the module hangs off it: an agent’s behavior is a causal chain, and the interesting failures live in the relationship between steps, not inside any single step. A microservice request fails because this span returned a 500. An agent run fails because the model misread a tool result five steps ago, formed a wrong belief, and then executed flawlessly on that wrong belief for the next twelve steps. Every individual span is status: ok. The trace is a disaster. Your normal logs — request in, response out, latency, error rate — will show you a clean, successful, expensive run that produced garbage. You will not be able to debug it, cost-control it, or improve it, because you cannot see it.

Teams that ship good harnesses instrument them like high-traffic production services, because that’s what they are: nondeterministic, multi-step, expensive, and failure-prone in ways that don’t surface as exceptions. You cannot improve what you can’t see. For agents, “seeing” means capturing the full session as a replayable causal chain.

Learning objectives

By the end of this module you will be able to:

  • Articulate why agents need first-class observability more than ordinary services, and why call-level LLM monitoring is not agent observability.
  • Map the trace/span data model onto an agent run, and name what each span must carry that a normal RPC span does not.
  • Build a from-scratch trace logger (decorator + context manager) that writes per-run JSONL, and a tree-printer + summary over it.
  • Instrument Scout’s loop with Langfuse, and place LangSmith and Braintrust correctly in the landscape.
  • Debug a multi-step failure by finding where the chain went wrong (usually far upstream of the symptom) and replaying it deterministically.
  • Wire production trace sampling into online evals — closing the loop back to Module 8.

Why agents need this more than normal services

Four properties of agents each break a load-bearing assumption of conventional observability.

Nondeterminism. The same input produces different trajectories. A bug that appears one run in twenty is not reproducible by re-running — the model just does something else. Without a recording of exactly what happened, the bug is gone. (This is why replay, below, is not a nice-to-have.)

Multi-step causality. A single user request fans out into 5, 20, 80 model calls and tool calls. The failure is rarely in the step that threw. It’s a belief the model formed early and carried forward. Your trace has to preserve the whole chain so you can walk backward from symptom to cause.

Cost. Every step burns tokens, and tokens are money and latency. A run that silently takes 40 steps instead of 8 costs 5x and you’ll never notice from a latency dashboard that says “p95: 45s, within SLO.” You need per-step token accounting to see it. (Module 10 is where you fix cost; here you measure it.)

Invisible failure. The worst one. The agent returns a confident, well-formed answer that is wrong. HTTP 200. No exception. No log line that says “I made this up.” In production agent fleets it’s common for a meaningful fraction of tasks to fail this way — silently, looking exactly like success. Your error-rate dashboard reads 0.1% while the real task-failure rate is 18%. The only way to see the gap is to capture full traces and grade their content, not their status codes.

✅ Checkpoint. If your mental model is “agent observability = log the prompt and completion and track token spend,” you have LLM monitoring, not agent observability. The difference is the full-session causal chain. Hold that distinction — everything below builds on it.

The data model: traces and spans, agent-flavored

Lean on what you know. A trace is one full agent run — one session, one user request driven to completion. A span is a nested step within it: each model call, each tool call, each sub-agent invocation, each retrieval. Spans nest exactly the way you’d expect — a sub-agent span contains the model and tool spans of that sub-agent’s own loop. A trace ID threads the whole thing; span IDs and parent-span IDs give you the tree. None of this is new.

What’s new is two things.

The payload is huge, semi-structured text. A normal span carries http.method=GET, http.status=200, db.rows=42 — small, structured, cheap. An agent span carries the full rendered prompt (which can be tens of thousands of tokens), the full completion, the tool arguments, the tool result (which might be a 5,000-line file the model just read). The “attributes” on an agent span are prompts and completions and tool I/O. This changes everything downstream — storage cost, query patterns, PII exposure, redaction needs (more in Real production issues).

The interesting failure is semantic and lives between spans. On a microservice, you find the bad span by its status code and you’re basically done. On an agent, every span succeeded. The failure is: span 7 was a read_file that returned an old version of the config; span 8’s model call read it correctly but the file was stale; spans 9 through 20 confidently built on a wrong fact. No span is red. The bug is the relationship between span 7’s output and span 20’s behavior. You find it by reading the transcript as a narrative, not by filtering for errors.

The consequence: capture the full session, not just call-level metrics. A dashboard of “mean tokens per call” and “tool call p99 latency” is useful but it is aggregate. To debug a specific bad run you need that run’s complete, ordered, nested trace with every payload intact. Aggregates tell you that something is wrong; the full trace tells you what.

📖 OpenTelemetry note. OTel has emerging GenAI semantic conventions — standardized span names (gen_ai.completion), attributes (gen_ai.usage.input_tokens, gen_ai.request.model), and event shapes for LLM and agent operations. They’re still stabilizing in mid-2026, but they matter: they’re the interop substrate that lets you emit one trace and view it in any OTel-compatible backend. Treat them as the standard you instrument toward, even when you’re using a vendor SDK that wraps them. We’ll come back to lock-in vs. portability at the end.

What every span must carry

Per-span, capture:

  • Full prompt + completion (or a reference/hash if you’re storing payloads out-of-band for size or PII reasons).
  • Tool name, arguments, and result for tool spans.
  • Token counts — input, output, cache_read, cache_creation — straight off resp.usage. This is the raw material for cost.
  • Latency (you already do this).
  • Model and params — model ID, effort, max_tokens, whatever shapes the call.
  • stop_reason — end_turn, tool_use, max_tokens, refusal. A run that ends on max_tokens truncated mid-thought; a run that ends on refusal was declined. These are first-class signals, not footnotes.
  • Errors — tool failures, API errors, denials from the permission gate.
  • The trace/session ID threading it all.

Per-run (aggregate the spans), compute:

  • Steps per task — the single best health metric. A task that used to take 8 steps now takes 30: something regressed.
  • Tool-error rate — per tool. The insight you will never get from anecdote: “the search tool has a 30% error rate” is invisible one run at a time and screaming at you across a thousand traces.
  • Cache-hit rate — cache_read / (input + cache_read). Drops silently when someone interpolates a timestamp into the system prompt (Module 4’s silent invalidators).
  • Compaction frequency — how often you’re hitting the context ceiling.
  • Total tokens and cost.
  • Success — from an eval or a label, not from stop_reason. (The whole point: success is semantic.)

🛠️ Build it from scratch first

Before reaching for a platform, build the data model by hand. It’s ~60 lines, it makes the abstraction concrete, and — genuinely — a JSONL-per-run tracer is a legitimate production tool. You’ll understand exactly what Langfuse is doing for you when you adopt it, instead of treating it as magic.

We’re instrumenting Scout’s loop from Module 3. Recall its shape: a while loop calling client.messages.create(...), dispatching tool_use blocks through a permission gate, feeding tool_result blocks back. We want a span for every model call and every tool call, all sharing one trace ID, written to one file per run.

The tracer 

# scout/tracing.py
import json, time, uuid, contextvars
from contextlib import contextmanager
from dataclasses import dataclass, field, asdict
from pathlib import Path

# The current trace travels implicitly via a contextvar, so the model-call and
# tool-call wrappers don't have to thread a `trace` argument through every layer.
_current_trace: contextvars.ContextVar = contextvars.ContextVar("trace", default=None)

@dataclass
class Span:
    name: str
    span_type: str                       # "model" | "tool" | "agent"
    span_id: str = field(default_factory=lambda: uuid.uuid4().hex[:8])
    parent_id: str | None = None
    start: float = 0.0
    end: float = 0.0
    input: dict = field(default_factory=dict)
    output: dict = field(default_factory=dict)
    tokens: dict = field(default_factory=dict)   # input/output/cache_read/cache_creation
    cost_usd: float = 0.0
    error: str | None = None

    @property
    def latency_ms(self) -> float:
        return round((self.end - self.start) * 1000, 1)

class Trace:
    def __init__(self, name: str, log_dir: str = "traces"):
        self.trace_id = uuid.uuid4().hex[:12]
        self.name = name
        self.spans: list[Span] = []
        self._stack: list[str] = []          # parent span ids, for nesting
        Path(log_dir).mkdir(exist_ok=True)
        self.path = Path(log_dir) / f"{self.name}-{self.trace_id}.jsonl"

    def flush(self):
        with self.path.open("w") as f:
            f.write(json.dumps({"trace_id": self.trace_id, "name": self.name}) + "\n")
            for s in self.spans:
                f.write(json.dumps({**asdict(s), "latency_ms": s.latency_ms}) + "\n")

@contextmanager
def trace_run(name: str):
    tr = Trace(name)
    token = _current_trace.set(tr)
    try:
        yield tr
    finally:
        tr.flush()
        _current_trace.reset(token)

@contextmanager
def span(name: str, span_type: str):
    tr = _current_trace.get()
    if tr is None:                            # tracing disabled — no-op
        yield None
        return
    s = Span(name=name, span_type=span_type,
             parent_id=tr._stack[-1] if tr._stack else None,
             start=time.time())
    tr.spans.append(s)
    tr._stack.append(s.span_id)
    try:
        yield s
    except Exception as e:
        s.error = repr(e)
        raise
    finally:
        s.end = time.time()
        tr._stack.pop()

Two design notes worth pausing on. The contextvar is doing the same job OTel’s context propagation does — making the active trace ambient so deep call sites don’t have to pass it explicitly. And the _stack is what gives you nesting: a tool span opened inside a model span gets the model span as its parent, so sub-agent trees fall out naturally.

Pricing helper 

# Opus 4.8: $5 / $25 per 1M in/out; cache reads ~0.1x input, writes ~1.25x.
PRICES = {"claude-opus-4-8": (5.0, 25.0)}

def cost_of(model: str, usage) -> float:
    pin, pout = PRICES.get(model, (0.0, 0.0))
    return round(
        (usage.input_tokens / 1e6) * pin
        + (usage.output_tokens / 1e6) * pout
        + (getattr(usage, "cache_read_input_tokens", 0) / 1e6) * pin * 0.1
        + (getattr(usage, "cache_creation_input_tokens", 0) / 1e6) * pin * 1.25,
        6,
    )

Wiring it into the loop

The instrumentation is two wrappers. Around the model call:

def call_model(client, messages, system, tools):
    with span("model_call", "model") as s:
        resp = client.messages.create(
            model="claude-opus-4-8", max_tokens=4096,
            system=system, tools=tools, messages=messages,
        )
        if s is not None:
            s.input = {"messages": messages[-1:], "n_messages": len(messages)}  # last turn + depth
            s.output = {"stop_reason": resp.stop_reason,
                        "content": [b.model_dump() for b in resp.content]}
            u = resp.usage
            s.tokens = {"input": u.input_tokens, "output": u.output_tokens,
                        "cache_read": getattr(u, "cache_read_input_tokens", 0),
                        "cache_creation": getattr(u, "cache_creation_input_tokens", 0)}
            s.cost_usd = cost_of("claude-opus-4-8", u)
        return resp

And around each tool dispatch (Scout’s dispatch from Module 3):

def dispatch(tool_use_block, gate):
    with span(f"tool:{tool_use_block.name}", "tool") as s:
        if s is not None:
            s.input = {"args": tool_use_block.input}
        result = run_tool_with_gate(tool_use_block, gate)   # your Module 3 logic
        if s is not None:
            s.output = {"is_error": result.get("is_error", False),
                        "content": result["content"][:2000]}  # truncate huge results
        return result

Then the top-level call site opens the trace:

with trace_run("scout-session"):
    run_scout_loop(user_prompt)        # everything inside is now traced

Notice what we captured per model span: last message + history depth (full prompt is recoverable but huge), the content blocks of the response (so we keep tool_use blocks, not just text), stop_reason, all four token counts, and cost. That’s the full per-span checklist from above. And note we truncate tool results to 2,000 chars in the output view — the trade-off between storing everything (replayable but expensive) and storing enough to debug. For real replay you’d store the untruncated result keyed by span ID; here we keep it simple.

Reading the trace: tree + summary

A JSONL file is not a debugging tool until you can read it as a narrative. The pretty-printer turns the flat span list back into the nested tree, and the summary computes the per-run metrics:

# scout/trace_view.py
import json, sys
from collections import defaultdict

def load(path):
    with open(path) as f:
        lines = [json.loads(l) for l in f]
    return lines[0], lines[1:]          # header, spans

def print_tree(spans):
    children = defaultdict(list)
    roots = []
    for s in spans:
        (children[s["parent_id"]].append(s) if s["parent_id"] else roots.append(s))
    def walk(s, depth):
        tok = s["tokens"].get("output", 0) if s["tokens"] else 0
        err = "  ERROR" if s["error"] else ""
        extra = (f"  stop={s['output'].get('stop_reason')}"
                 if s["span_type"] == "model" else "")
        print(f"{'  '*depth}{s['name']:<28} {s['latency_ms']:>7}ms "
              f"{tok:>5}tok ${s['cost_usd']:.4f}{extra}{err}")
        for c in children[s["span_id"]]:
            walk(c, depth + 1)
    for r in roots:
        walk(r, 0)

def summary(spans):
    model = [s for s in spans if s["span_type"] == "model"]
    tools = [s for s in spans if s["span_type"] == "tool"]
    tool_errs = sum(1 for s in tools if s["output"].get("is_error"))
    tok = lambda k: sum((s["tokens"] or {}).get(k, 0) for s in model)
    print("\n--- run summary ---")
    print(f"model calls (steps): {len(model)}")
    print(f"tool calls:          {len(tools)}  errors: {tool_errs} "
          f"({100*tool_errs/max(len(tools),1):.0f}%)")
    print(f"tokens in/out:       {tok('input')} / {tok('output')}")
    print(f"cache hit rate:      "
          f"{100*tok('cache_read')/max(tok('input')+tok('cache_read'),1):.0f}%")
    print(f"total cost:          ${sum(s['cost_usd'] for s in model):.4f}")

if __name__ == "__main__":
    _, spans = load(sys.argv[1])
    print_tree(spans)
    summary(spans)

Run it and you get the run as a tree — every model call, every nested tool call, latency and tokens and cost on each line, stop_reason on model calls, ERROR flags where things failed — followed by the summary block. That summary line “tool calls: 14 errors: 4 (29%)” is the “tool X has a 30% error rate” insight, made visible. You built it.

✅ Checkpoint. You now have, in ~120 lines, the core of every agent observability platform: nested spans, per-span token/cost capture, a tree view, and run-level aggregates. Everything a vendor adds is operational scale on top of this model — a database, a UI, search, multi-run analytics, retention. Worth understanding what you’re paying for.

Swap in Langfuse

For a single dev loop, JSONL files are great. For a fleet — thousands of runs a day, multiple engineers, “show me every run last week where the search tool errored” — you want a backend with a database and a UI. Langfuse is the open-source baseline here: self-hostable (so it’s data-residency friendly — your prompts and completions never leave your infra), and as of January 2026 it’s backed by ClickHouse, which acquired it — a signal that the storage layer underneath is built for the high-cardinality, high-volume trace workloads agents generate.

Two ways to instrument. The decorator is the fastest:

from langfuse import observe, get_client

langfuse = get_client()

@observe()                              # this function becomes a span
def dispatch(tool_use_block, gate):
    result = run_tool_with_gate(tool_use_block, gate)
    langfuse.update_current_span(
        input={"tool": tool_use_block.name, "args": tool_use_block.input},
        output={"is_error": result.get("is_error", False)},
    )
    return result

@observe()
def run_scout_loop(user_prompt):        # the whole run becomes the trace
    ...

Any @observe()-decorated function called inside another becomes a child span — the nesting you built by hand with _stack, done by the decorator via the same kind of context propagation. For the model call specifically, Langfuse ships an Anthropic wrapper that auto-captures the request, response, model, and — critically — usage, so you get token counts and cost without writing the cost_of plumbing:

from langfuse.anthropic import Anthropic   # drop-in for anthropic.Anthropic

client = Anthropic()
# Every client.messages.create(...) inside an @observe() context is now a span
# with prompt, completion, model, stop_reason, and token usage captured.
resp = client.messages.create(
    model="claude-opus-4-8", max_tokens=4096,
    system=system, tools=tools, messages=messages,
)

If you need finer control than the decorator gives — custom span boundaries, manual nesting — there’s langfuse.start_as_current_span(...) as a context manager, which is the direct analog of your hand-built span(). Set a stable session_id per Scout run and every span lands under one trace in the UI, where you get the tree view, token/cost rollups, latency breakdowns, and search across runs — the same data model you built, operationalized.

📖 The alternatives, placed correctly.

  • LangSmith — best when your stack is LangChain / LangGraph. The tracing is deeply native to those frameworks; spans map onto chains, agents, and graph nodes with near-zero instrumentation. If you’re not on LangChain, its advantage mostly evaporates.
  • Braintrust — eval-first. Its center of gravity is treating evals as CI gates: you wire trace-derived test cases into a suite that blocks a deploy on regression. Generous free tier. Reach for it when your discipline is “no agent change ships without passing the eval gate” (the Module 8 mindset, productized).

Which one? Default to Langfuse if you want open-source, self-hosting, or data residency — it’s the safe baseline and the data model is the one you just learned. Choose LangSmith if you live in LangChain/LangGraph. Choose Braintrust if eval-gated CI is the workflow you’re building around. And whichever you pick, prefer the OTel GenAI conventions underneath so the trace outlives the vendor.

Debugging multi-step failures

This is the part your microservice instincts mislead you on, so go slow.

The workflow:

  1. Capture the full trace. You can’t debug what you didn’t record — and because of nondeterminism, you can’t reliably reproduce it by re-running. The trace is the evidence.
  2. Find where the chain went wrong. The symptom — wrong final answer, infinite loop, blown budget — appears at the end. The cause is almost always upstream. Read the transcript forward as a narrative and find the first span where the model’s belief diverged from reality. That’s your bug. It is rarely the span that looks broken.
  3. Form a hypothesis. “At span 7 the model read a stale config and believed the flag was off; everything after is correct reasoning on a wrong premise.”
  4. Replay. Re-run the loop logic against the recorded model responses to confirm the hypothesis deterministically.

Step 4 is the superpower, so let’s build it.

Replay

The idea: record every (request, response) pair from the model during a run. Then re-run your loop with the model mocked — instead of calling the API, you replay the recorded responses in order. Now your loop logic runs deterministically against the exact trajectory that failed. You can add logging, set breakpoints, fix a dispatch bug, and re-run as many times as you want, and it’s the same run every time. The nondeterminism is frozen.

# scout/replay.py
import json
from pathlib import Path

class Recorder:
    """Wrap the client; record every model response to a file."""
    def __init__(self, client, path):
        self._client = client
        self._path = Path(path)
        self._records = []
    def create(self, **kwargs):
        resp = self._client.messages.create(**kwargs)
        self._records.append(resp.model_dump())   # full response, serializable
        return resp
    def save(self):
        self._path.write_text(json.dumps(self._records))

class Player:
    """Replay recorded responses in order. No network, fully deterministic."""
    def __init__(self, path):
        self._records = json.loads(Path(path).read_text())
        self._i = 0
    def create(self, **kwargs):
        from anthropic.types import Message
        rec = self._records[self._i]
        self._i += 1
        return Message.model_validate(rec)         # reconstruct the SDK object

Record on a live run, replay forever after:

# Record:
rec = Recorder(anthropic.Anthropic(), "fail-run.json")
run_scout_loop(prompt, client=rec); rec.save()

# Replay against your loop logic, no API calls, deterministic:
run_scout_loop(prompt, client=Player("fail-run.json"))

Because Player.create reconstructs the real SDK Message object, your loop’s resp.stop_reason, resp.content, resp.usage all work unchanged — the loop can’t tell it’s talking to a recording. Now the failing run reproduces on demand. You step through it, you find that span 7 returned a stale read, you fix the staleness check, and you replay to confirm the chain now goes right. That is how you debug nondeterministic systems: you make them deterministic.

📖 And this is how you build taste. Reading transcripts — not metrics, the actual prompt/completion/tool-IO narrative of real runs — is the single highest-leverage habit in agent engineering. It’s the same skill Module 8 leaned on for writing evals: you cannot write a good judge or a good unit eval for a failure mode you’ve never seen in a real transcript. Replay and transcript-reading are two sides of one practice.

Common failure signatures in a trace

Once you’ve read a few hundred traces, the shapes become recognizable:

  • Context starvation — the model is reasoning without a fact it needs, because compaction (Module 4) dropped it or it was never retrieved. In the trace: a model span whose input is missing something an earlier span produced. Often co-occurs with a compaction span just upstream.
  • A bad tool result the model trusted — a tool returned wrong/stale/empty data, the model took it at face value, everything downstream is built on it. The tool span looks is_error: false (it didn’t crash, it just lied). The classic upstream-cause bug.
  • Tool-arg hallucination — the model calls a tool with an argument it invented (a file path that doesn’t exist, an ID it made up). In the trace: a tool span whose input doesn’t correspond to anything any prior span surfaced, usually followed by an error result and a confused recovery.
  • Infinite loop — the same tool span with the same args repeating. Trivially obvious in the tree, invisible in a latency metric until the run blows its budget. (Your steps-per-task metric catches this in aggregate.)
  • Sub-agent solved the wrong problem — a sub-agent span tree that’s internally coherent and successful but answers a question the parent didn’t ask, because the delegated instruction was ambiguous. You have to open the child trace to see it; the parent just sees a plausible result come back.

Online evals: closing the loop to Module 8

Observability and evals are two sides of the same coin. Traces are the substrate evals run on, and production failures become new eval cases. Module 8 built the eval methodology; this is where it meets production.

The pattern is continuous: sample live traces, run a grader on each, alert on drift. Three layers stack here:

  • Unit evals on discrete steps — programmatic, cheap, run on every (or sampled) trace. “Did the write_file span ever write outside the project root?” “Did any tool span exceed 3 retries?”
  • LLM-as-judge regression suites — the Module 8 judge, run against sampled production traces, scoring final-answer quality on traces where you have no ground-truth label. This is how you measure the real task-failure rate — the 18% that stop_reason hides.
  • Continuous production sampling for drift — grade, say, 2% of all traces on a rolling basis, track the score over time, and alert when it drifts down. A model update, a prompt change, a tool that started returning a new error shape — drift catches regressions your CI evals didn’t anticipate.
def online_eval(trace_path, sample_rate=0.02):
    import random
    if random.random() > sample_rate:
        return
    _, spans = load(trace_path)
    final = next(s for s in reversed(spans)
                 if s["span_type"] == "model" and not s["output"].get("stop_reason") == "tool_use")
    score = llm_judge(final["output"]["content"])   # your Module 8 judge
    log_score(trace_path, score)                     # to Langfuse, a metrics sink, etc.
    if score < THRESHOLD:
        flag_for_review(trace_path)                  # ← becomes a new eval case

That last line is the flywheel. A low-scoring production trace gets flagged, a human looks at it, and if it’s a real failure it becomes a permanent regression case in your Module 8 suite. Observability feeds evals; evals catch regressions; caught regressions harden the suite. The trace you captured to debug today is the eval case that prevents the same failure tomorrow.

Real production issues

  • The 18%-fail-silently problem. Worth restating because it’s the whole reason this module exists: a large fraction of agent task failures produce HTTP 200, no exception, no error log — a confident wrong answer. Your ops dashboards are blind to it by construction. Only content-level grading of sampled traces surfaces it. If you take one thing from this module: error rate is not failure rate.
  • PII and cost in captured prompts. You are now logging full prompts and completions — which means full user data, possibly PII, possibly secrets the user pasted. This is a security surface (Module 11): you need redaction at capture time, sampling to limit volume, and a retention policy. “We log every prompt forever” is a breach waiting to happen and a compliance problem in regulated domains. Redact before it hits storage, not after.
  • Trace volume and cost at scale. Agent traces are big (huge text payloads) and numerous (many spans per run). Storing 100% of full payloads for a high-traffic fleet gets expensive fast. Sampling strategies: keep 100% of metadata (cheap, enables aggregates and the steps/error/cost metrics) but sample full payloads — and bias the sample toward the interesting tail (always keep failed runs, runs over a step threshold, runs that hit refusal or max_tokens). Head-based random sampling throws away exactly the failures you most need.
  • Symptom far from cause. Internalize that the red span is rarely the bug. The discipline is reading backward from symptom to the first divergence, not jumping to the span that threw. New engineers waste days “fixing” the downstream span that was correctly processing upstream garbage.
  • Nondeterminism makes bugs non-reproducible — without replay. “Works on the rerun” is not a fix; it’s the bug hiding. Record-and-replay is the only reliable way to reproduce, and you should build it into the harness early, not bolt it on during an incident.
  • Vendor lock-in vs. OTel portability. Vendor SDKs are convenient and their auto-instrumentation saves real work. The risk is that your traces become a proprietary asset you can’t move. Mitigate by instrumenting toward the OTel GenAI conventions — emit standard spans and attributes, let the vendor consume them. Then switching backends is a config change, not a re-instrumentation project.
  • Instrumenting through framework abstraction layers. If you’re on a framework (Module 7), the loop is inside the library — you don’t own the call site where you’d drop a span. This is exactly why the framework-native integrations (LangSmith for LangChain, Langfuse’s callback handlers) exist: they hook the framework’s internals. The flip side, and the Module 7 warning made concrete: when the framework owns the loop, your observability is only as good as its instrumentation hooks. If it doesn’t surface a span boundary you need, you can’t add one. Evaluate that before you adopt.
  • Observability is the prerequisite for everything downstream. You cannot do cost control (Module 10) without per-step token accounting. You cannot detect drift without continuous trace grading. The industry framing — that something like 40% of enterprise AI failures will trace to inadequate eval and monitoring rather than to model capability — is a way of saying: the model is usually good enough; the failure is that nobody could see what it was doing. Instrumentation is not the polish you add at the end. It’s the foundation the rest of the production stack stands on.

  1. Your error-rate dashboard shows 0.2% over the last day, but users are complaining the agent “gets things wrong a lot.” Both can be true. Explain how, and what you’d instrument to measure the real number.
  2. Why does re-running a failed agent task usually fail to reproduce the bug, and how does record-and-replay solve it? What exactly are you mocking?
  3. A run produces a wrong final answer at span 40. You read the trace. Where do you start looking, and why is span 40 almost certainly not where the bug is?
  4. Name three things an agent model span must carry that a normal RPC span does not, and say what each one lets you compute or debug.
  5. You’re storing full traces for a fleet doing 500K runs/day and the bill is alarming. Describe a sampling strategy that cuts cost without blinding you to failures.
