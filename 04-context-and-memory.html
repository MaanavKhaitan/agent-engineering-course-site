Module 04 — Context Engineering & Memory

In Module 03 you built Scout: a tool-using agent that loops model → tool → model until the task is done. It works on toy tasks. Now point it at something real — “fix the failing test in this package” — and watch it die. Not because the model gets confused, but because around iteration 40 the API starts returning 400s, or the responses get slower and vaguer, or it simply stops finding the file it read twenty turns ago. The agent didn’t get dumber. It ran out of room.

This module is about the resource that bounds every long-running agent: the context window. Everything an agent “knows” at any instant — the system prompt, the task, every tool call it has made, every result it got back, its own reasoning — lives in one fixed-size buffer that you resend on every single iteration. There is no swap. There is no malloc that returns more. When the buffer is full, the agent is done, whether or not the task is.

If you’ve built systems under memory pressure, the whole module is an analogy you already know. The context window is RAM. The transcript is an append-only log that never shrinks on its own. Tool outputs are bulky pages that blow your working set. And the techniques — truncation, compaction, eviction, spilling to disk, address-space isolation — are the same moves an OS makes when physical memory runs short. Context engineering is memory management for agents, and most of the failure modes are paging failures wearing a different hat.

Learning objectives

By the end of this module you will be able to:

  • Explain why the transcript grows every iteration and why input_tokens climbs even though you “only added one message.”
  • Describe context rot: why retrieval quality degrades before you hit the hard token limit, not just at it.
  • Apply the full toolkit in order of leverage: truncation at the tool boundary, compaction, context editing/pruning, externalizing state to disk, sub-agents as context firewalls, and long-term memory.
  • Implement output truncation, a token-budget monitor, DIY compaction with a cheap model, a filesystem-backed plan, and a delegating sub-agent — all in Scout.
  • Pick the right technique per situation, and understand how they compose in a real long-running agent.
  • Recognize the production failure modes: context exhaustion, lossy compaction dropping load-bearing detail, huge tool outputs, lossy sub-agent summaries, stale memory, and the cache-vs-rewrite tension.

The defining constraint

📖 The context window is a fixed buffer. Claude’s current Opus, Sonnet, and Fable models give you 1M tokens; Haiku gives you 200K. That number is a hard ceiling, not a target. It is the sum of everything you send: tools, system prompt, and the entire message history.

Here is the part that surprises people coming from stateful systems. The Messages API is stateless. It does not remember your conversation. Every turn, you resend the whole transcript — every prior user message, every assistant turn, every tool_use block and every tool_result — and the model reads all of it from scratch. The “conversation” is a fiction your client maintains by appending to a list and replaying it.

That has a direct, measurable consequence:

import anthropic

client = anthropic.Anthropic()
messages = []

def step(user_text):
    messages.append({"role": "user", "content": user_text})
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})
    # input_tokens is the size of EVERYTHING we just sent, not just the new turn
    print(f"input_tokens this call: {resp.usage.input_tokens}")
    return resp

step("Hello.")            # input_tokens: ~10
step("Tell me about RAM") # input_tokens: ~120  (resent the first turn too)
step("And paging?")       # input_tokens: ~400  (resent both prior turns)

resp.usage.input_tokens grows every iteration because you are resending a longer and longer prefix. The transcript is append-only: in a tool-using loop you never remove a turn, you only add the next tool_use/tool_result pair. Cost and latency both scale with transcript length, and the buffer fills monotonically.

To measure the buffer before you send it — to decide whether you’re about to blow the budget — use token counting:

count = client.messages.count_tokens(model="claude-sonnet-4-6", messages=messages)
print(count.input_tokens)   # exact prompt size, same tokenizer the model uses

(Don’t reach for tiktoken — that’s OpenAI’s tokenizer and it’ll be off by 15-20% on Claude, more on code.)

Tool outputs are the bulk

In a chat app, turns are small — a sentence each. In an agent, the bulk is tool output, and tool output is enormous. A single pytest run can be 30,000 tokens of tracebacks. cat-ing a 2,000-line file is ~25,000 tokens. A directory listing of node_modules, a verbose build log, a big JSON API response — each one is a page-sized chunk that lands in your transcript and stays there forever. Read five files and run the tests twice and you’ve spent 100K+ tokens on context you’ll mostly never look at again.

This is the number-one reason long agent tasks die. Not reasoning failures — context exhaustion, driven by bulky tool results that pile up faster than the useful signal.

Context rot: degradation before the limit

Here’s the subtler problem, and the one that separates “it technically fit” from “it actually worked.” You do not get the model’s full quality right up to the last token and then a clean cutoff. Quality degrades gradually as the transcript grows — a phenomenon usually called context rot, and closely related to the “lost in the middle” effect where models attend less reliably to information buried in the middle of a long context than to information at the start or end.

The systems analogy: it’s not a hard page fault at the boundary, it’s cache thrashing as your working set grows. The relevant facts are still technically “in memory,” but they’re diluted among 400K tokens of stale tracebacks, and the model’s effective retrieval over that haystack gets worse. An agent at 600K tokens of mostly-junk transcript is measurably worse at using the 5K tokens that matter than the same agent at 50K tokens would be.

The practical upshot: more context is not always better. Padding the window with “just in case” history actively hurts. The goal of every technique below is not just to fit under the hard limit — it’s to keep the working set small and high-signal, so the model is operating in the regime where it’s sharp.

The toolkit

The techniques below are ordered roughly by when they appeared and how much sophistication they demand. Reach for them in this order: the cheapest, highest-leverage fix first.

a. Truncation at the tool boundary

This is the single highest-value, lowest-effort change you can make, and most agents that fall over are missing it. Cap every tool result before it enters the transcript. A test run that produces 30,000 tokens almost never needs all 30,000 in context — the model needs the first chunk (what’s being run, early failures) and the last chunk (the summary line, the final error). The middle is noise.

The OS analogy is bounded buffers and pagination: you don’t read() an entire file into a fixed buffer, you read up to N bytes and offer a way to read more.

🛠️ A truncation wrapper for Scout’s tools:

MAX_TOOL_TOKENS = 2000  # per-result cap; tune per tool

def truncate_output(text: str, max_tokens: int = MAX_TOOL_TOKENS) -> str:
    # Rough heuristic: ~4 chars/token. For precision, call count_tokens,
    # but that's a network round trip per tool call — usually not worth it.
    max_chars = max_tokens * 4
    if len(text) <= max_chars:
        return text
    head = text[: max_chars // 2]
    tail = text[-max_chars // 2 :]
    dropped = len(text) - len(head) - len(tail)
    dropped_lines = text[len(head):len(text) - len(tail)].count("\n")
    return (
        f"{head}\n"
        f"\n[... truncated {dropped} chars / ~{dropped_lines} lines. "
        f"Re-run with a narrower query, or use read_file(path, offset, limit) "
        f"to page through the full output ...]\n"
        f"{tail}"
    )

Two design points that matter more than they look:

  • Head + tail beats head-only. For most tool output the conclusion is at the bottom (test summary, final error, exit status). Truncating only the head throws away the answer.
  • Always leave an escape hatch. The truncation marker should tell the model how to get more — a paginated read_file(path, offset, limit), a grep to narrow, a “re-run with -q”. Without it, the model can’t recover the dropped data and may hallucinate it. With it, truncation is lossy-but-recoverable rather than lossy-and-stuck.

Make file reads paginated by default (“read up to 200 lines from offset N”) and your single biggest context sink is handled.

b. Compaction

Truncation bounds each result. But the transcript still grows turn over turn, and eventually even well-truncated history crosses the threshold where you want to shrink the whole thing. Compaction summarizes older turns and replaces them with the summary, freeing room while preserving the gist.

The systems analogy: this is generational GC. Recent turns are the nursery — kept verbatim, churning fast. Old turns get compacted into a tenured summary that survives but takes far less space.

The hard sub-problem is not how to summarize — it’s what must survive. Naive summarization optimizes for narrative readability and drops exactly the load-bearing details an agent needs 40 turns later: the absolute file path it edited, the precise error string it’s chasing, the constraint the user stated once (“must stay Python 3.10 compatible”), the approach it already tried and ruled out. A summary that says “explored the auth module and made progress” is worse than useless — it costs tokens and tells the agent nothing actionable.

📖 Server-side compaction (beta). Claude offers this as a managed feature so you don’t have to implement the summarization yourself. It triggers automatically when the context approaches a threshold:

resp = client.beta.messages.create(
    betas=["compact-2026-01-12"],
    model="claude-sonnet-4-6",
    max_tokens=4096,
    messages=messages,
    context_management={"edits": [{"type": "compact_20260112"}]},
)
# CRITICAL: append the FULL resp.content back, including the compaction block.
messages.append({"role": "assistant", "content": resp.content})

⚠️ The one mistake that silently breaks this: people extract resp.content[0].text and append only the string. Don’t. The response carries a compaction block that holds the compaction state; the API uses it on the next request to replace the compacted history. Append the whole resp.content list. Extract only text and you lose the compaction entirely.

🛠️ DIY compaction — worth building once even if you use the managed feature, because it makes the mechanism concrete and gives you control over the survival policy. When the transcript exceeds a budget, summarize the oldest turns with a cheap model and replace them with a single system note:

COMPACT_THRESHOLD = 100_000   # tokens
KEEP_RECENT = 6               # most-recent turns to keep verbatim

COMPACT_PROMPT = """You are compacting an agent's working memory to save context space.
Summarize the conversation below into a dense progress note. You MUST preserve, verbatim:
- The original task / user goal
- Every file path touched and what was done to it
- Exact error strings and failing test names still unresolved
- Decisions made and approaches already tried and REJECTED (so we don't repeat them)
- Any hard constraints the user stated
Drop: narration, redundant tool output, anything already superseded.
Write it as notes-to-self, not prose. Be specific over readable."""

def compact(client, messages):
    if len(messages) <= KEEP_RECENT + 1:
        return messages
    old, recent = messages[:-KEEP_RECENT], messages[-KEEP_RECENT:]
    summary = client.messages.create(
        model="claude-haiku-4-5",   # cheap model; this is a side computation
        max_tokens=2048,
        system=COMPACT_PROMPT,
        messages=old + [{"role": "user", "content": "Produce the progress note now."}],
    )
    note = next(b.text for b in summary.content if b.type == "text")
    return [{"role": "user", "content": f"[COMPACTED HISTORY]\n{note}"}] + recent

Notice the prompt does the heavy lifting. It’s explicitly biased toward identifiers, paths, and constraints over narrative — because those are what the agent will need to act, and what naive summarization throws away.

c. Context editing / pruning

Compaction summarizes. Context editing clears — it removes stale blocks outright rather than condensing them. The two are different beta features and easy to confuse.

The insight: an agent rarely needs the full text of a file it read 80 turns ago and has since edited three times. The current state lives on disk (or in a later turn); the original tool_result is dead weight. Pruning it reclaims the tokens with zero summarization cost. The systems analogy is plain eviction — drop the cold page, don’t bother writing a summary of it.

📖 Context editing (beta) clears old tool results (and optionally thinking blocks):

resp = client.beta.messages.create(
    betas=["context-management-2025-06-27"],
    model="claude-sonnet-4-6",
    max_tokens=4096,
    tools=tools,
    messages=messages,
    context_management={"edits": [{"type": "clear_tool_uses_20250919"}]},
    # optionally add {"type": "clear_thinking_20251015"} to drop old thinking blocks
)

Anthropic reports this is not a minor optimization: in a 100-turn web-search evaluation, context editing combined with the memory tool cut token use by ~84% and improved task quality — a direct demonstration of the context-rot point. Clearing the dead pages didn’t just save money; it made the model sharper by shrinking the haystack.

Use editing when old tool results are recoverable from elsewhere (the file is still on disk; the state is captured later) — those are exactly the cold pages safe to evict. Use compaction when the old turns contain reasoning or decisions you can’t reconstruct, only condense.

d. Externalize state to disk (filesystem-as-memory)

This is the technique that turns a fragile demo into a system that can run for hours, and it’s the most important pattern in the module. Have the agent write its plan, its todo list, and its findings to files — then re-read them — instead of holding everything in context.

The systems analogy is exact: this is spilling to disk under memory pressure. Context is RAM; the filesystem is the disk you page out to. The agent keeps a small working set in context and parks the rest in files it can reload on demand. You get two wins from one move:

  1. Bounded context. A 50-item todo list lives in PLAN.md, not in 50 turns of transcript. The agent reads it when it needs it and the window stays lean.
  2. Crash recovery for free. If the process dies at iteration 200, the plan and progress notes are on disk. Restart, re-read PLAN.md, continue. Context is ephemeral; the filesystem persists. (This is the backbone of the long-running and durable-agent patterns in Modules 12-13.)

🛠️ Scout writing and re-reading a plan:

PLAN_PATH = "PLAN.md"

def write_plan(content: str) -> str:
    """Write or overwrite the agent's working plan/todo list to PLAN.md."""
    with open(PLAN_PATH, "w") as f:
        f.write(content)
    return f"Wrote {len(content)} chars to {PLAN_PATH}."

def read_plan() -> str:
    """Re-read the current plan. Call this when resuming or after compaction."""
    try:
        with open(PLAN_PATH) as f:
            return f.read()
    except FileNotFoundError:
        return "No plan yet. Use write_plan to create one."

Expose these as tools, and tell Scout in its system prompt to maintain a plan: write a todo list at the start, check items off as it goes, and re-read the plan after any compaction (because compaction may have dropped the details, but PLAN.md still has them). The plan file becomes the durable spine of the task; the context window becomes a scratchpad for the current step.

e. Sub-agents as context firewalls

The most context-expensive operations are exploratory: “search the whole codebase for everywhere AuthToken is used,” “read these twelve files and tell me which one has the bug.” Done in the main loop, each of these dumps thousands of tokens of file content into your transcript, and most of it is irrelevant the moment the question is answered. You paid permanent context for a transient need.

A sub-agent fixes this by isolation. Spawn a child agent with its own fresh context window, hand it the sub-task, let it burn through 80K tokens of searching and reading in its window, and have it return only a few-sentence summary to the parent. The parent’s window absorbs the summary, not the search.

The systems analogy: the parent rents address space instead of mapping every page into its own. The child does the dirty work in an isolated address space that gets torn down when it returns; only the result crosses the boundary. (Multi-agent orchestration — coordination, fan-out, error handling — is Module 06. Here the motivation is purely context: a sub-agent is a context firewall.)

🛠️ A minimal delegate tool — a fresh inner loop that returns a short result:

def delegate(subtask: str) -> str:
    """Run a sub-agent on `subtask` in a fresh context window.
    Returns only its final summary, so the parent's context stays small."""
    sub_messages = [{"role": "user", "content": subtask}]
    for _ in range(20):  # bound the child's loop
        resp = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            system=(
                "You are a sub-agent. Do the task, then return a concise, "
                "self-contained summary — include the specific facts the caller "
                "needs (file paths, line numbers, exact findings). Be complete "
                "but brief; the caller will NOT see your intermediate work."
            ),
            tools=SCOUT_TOOLS,          # the child gets its own truncated tools
            messages=sub_messages,
        )
        sub_messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return next(b.text for b in resp.content if b.type == "text")
        # ... execute the child's tool calls, append results, loop ...
    return "Sub-agent hit its iteration limit without finishing."

The parent calls delegate("Find every call site of AuthToken.refresh and report file:line for each") and gets back ten lines instead of ten files. The summary prompt is doing critical work — see the production-issues section for why this interface is lossy and how to harden it.

f. Long-term memory (cross-session)

Everything above operates within a single session. Compaction and editing shape one run’s transcript; when the process exits, it’s gone. But some state should outlive the session: a user’s stated preferences, a hard-won lesson (“this repo’s tests need DATABASE_URL set”), a fact the agent learned last week and shouldn’t have to rediscover.

That’s long-term memory: a persistent store the agent reads and writes across runs.

📖 The memory tool. Claude exposes a client-implemented memory tool. The model issues commands to read/write files in a /memories directory; you implement the backend (the view/create/str_replace/insert/delete/rename operations against whatever storage you choose — local disk, S3, a database).

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=4096,
    tools=[{"type": "memory_20250818", "name": "memory"}],
    messages=messages,
)
# When resp contains a memory tool_use, YOU execute the file op against your
# backend and return the result. The Python SDK ships BetaAbstractMemoryTool
# as a helper you subclass to implement view/create/str_replace/insert/delete/rename.

The distinction to hold onto:

Horizon Mechanism Lifetime
Short-term (within a session) compaction, context editing, sub-agents until the process exits
Long-term (across sessions) memory tool / a /memories directory persists indefinitely

Filesystem-as-memory (technique d) is the conceptual bridge: it’s disk-backed like long-term memory, but typically scoped to one task. Promote a finding from the task scratchpad to the memory store when it’s worth remembering next time, not just this time.

Decision guide

These compose. A serious long-running agent uses several at once — truncation always on, a plan file as its spine, compaction or editing when the window fills, sub-agents for the heavy exploration, and memory for cross-session learnings. The table is about which one solves a given symptom:

Situation Reach for Why
Any tool can produce big output Truncation (always-on) Highest leverage, lowest cost. Bounds the #1 context sink at the source.
Transcript nearing the limit; old turns hold reasoning/decisions you can’t reconstruct Compaction Condenses while preserving gist. Pay summarization cost to keep the irreplaceable.
Old tool results are stale and recoverable elsewhere (file on disk, state captured later) Context editing Evict the dead page for free — no summary needed.
The task is long, multi-step, or must survive a crash Externalize to disk Bounded context + free recovery. The backbone of durable agents.
A sub-task needs heavy, throwaway exploration (broad search, many file reads) Sub-agent Isolates the context cost; only the summary returns.
State must outlive the run (prefs, learnings) Memory tool The only one that persists across sessions.

🛠️ Exercise: harden Scout’s context handling

Take the Scout agent from Module 03 and make it survive a long task. Build these in order; each one is independently useful.

(a) Output truncation on all tools. Wrap every tool’s return value in the truncate_output helper above. Cap to ~2000 tokens with a [... truncated N chars / M lines ...] marker that names how to read more. Add a paginated read_file(path, offset, limit) tool so the model can recover dropped content. This alone will roughly double how long Scout survives.

(b) Token-budget monitor. After each iteration, call count_tokens on the current messages and print the transcript size. Warn loudly when it crosses a threshold (say 70% of a budget you set — use a small budget like 50K to make it trigger quickly in testing):

def report_budget(client, messages, budget=50_000):
    n = client.messages.count_tokens(model="claude-sonnet-4-6", messages=messages).input_tokens
    pct = n / budget
    flag = "  ⚠️ APPROACHING BUDGET" if pct > 0.7 else ""
    print(f"[budget] transcript={n} tokens ({pct:.0%} of {budget}){flag}")
    return n

(c) DIY compaction. When the monitor reports the transcript over your budget, run the compact() function from above: summarize the oldest turns with claude-haiku-4-5 into a single system note and replace them, keeping the last few turns verbatim. Preserve task, decisions, paths, and unresolved errors. Verify by printing the transcript size after compaction — it should drop sharply.

(d) A write_plan / read_plan tool. Add the filesystem-as-memory tools. Update Scout’s system prompt: “At the start of a multi-step task, write a todo list to PLAN.md. Update it as you complete steps. After any compaction, re-read PLAN.md to recover your plan.” Confirm the plan survives a compaction that drops the original planning turns.

(e) Stretch: a delegate(subtask) tool. Add the sub-agent firewall. Give Scout a task that benefits from delegation (“search the repo for all usages of X, then fix the bug in the right file”) and confirm the parent transcript stays small while the child does the searching.

The payoff to observe: run Scout on a task long enough to trigger compaction — e.g. “read these eight files, run the tests, and fix the failure.” Watch the budget monitor. Without your changes, the transcript climbs monotonically until the model degrades or the request fails. With them, you should see the transcript climb, hit the threshold, drop at compaction, and climb again — bounded, sawtooth, indefinitely. That sawtooth is the whole point: the agent can now run longer than its context window.

Real production issues

  • Context exhaustion kills long tasks. The default failure mode of an un-engineered agent on a real task. It doesn’t error gracefully at 90% — it degrades, then dies. Truncation + compaction is the baseline that makes long tasks possible, not an optimization.
  • Huge tool outputs are the #1 killer. Before anything fancy, cap your tool results. One un-truncated pytest run or one cat of a generated file can blow your entire budget in a single turn. If you fix exactly one thing in this module, fix this.
  • Naive compaction drops the detail you need 40 turns later. This is the deepest trap. The summarizer optimizes for readable prose and silently discards the exact error string, the absolute path, the rejected approach. Then the agent, 40 turns on, re-tries the thing it already ruled out, or edits the wrong file. Bias your compaction policy hard toward preserving identifiers, paths, and constraints over narrative. A summary you can’t act on is negative-value: it costs tokens and misleads.
  • The lossy-summarization policy problem is fundamental. You decide what to drop at write time, but you don’t know what you’ll need until read time, which is later. There is no compaction policy that’s safe against every future question — you’re guessing about the future. This is why externalizing to disk is so valuable: the file is the lossless backup the lossy summary can point back to. Compaction summarizes; the filesystem remembers.
  • Sub-agent summaries lose load-bearing detail. The firewall is also a lossy interface. If the child reports “found the bug in the auth module” but drops the file and line number, the parent has to re-search — you paid for the sub-agent and got nothing durable. Make the child’s summary prompt demand specifics (paths, line numbers, exact findings) and be self-contained, because the parent never sees the child’s work. (The lossy-interface problem is treated fully under orchestration in Module 06.)
  • Memory poisoning / stale memory. Long-term memory persists wrong facts as durably as right ones. A memory written as “the deploy command is make ship” survives after the command changes to make deploy, and silently misleads every future run until someone notices. Persistent memory needs a correction and expiry story, not just a write path. (Trust and validation of memory is Module 11.)
  • The cache-vs-rewrite tension. Prompt caching rewards a stable prefix — keep the front of the transcript byte-identical and you get cache hits at ~10% of input cost. But compaction and context editing rewrite history — they change the prefix, which invalidates the cache from the edit point onward. So the very techniques that keep you under the token limit also throw away cache savings. There’s no free lunch: you’re trading cache efficiency for context headroom. (The full economics are Module 10; for now, just know the two goals pull against each other, and time your compactions so you’re not invalidating a cache you just paid to build on every single turn.)
  • More context isn’t better — context rot is real. The instinct to “give the model everything just in case” is wrong. Past a point, additional low-signal context degrades retrieval and reasoning (lost-in-the-middle). Aggressive pruning isn’t only a cost play — it can make the agent measurably smarter by keeping its working set sharp.
