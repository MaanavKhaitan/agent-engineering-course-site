Module 01 — The Base Model & the Completion API

This module gives you a precise mental model of the thing every agent is built on: a stateless function from tokens to tokens, exposed through a completion API. Everything in the rest of the course — the loop, tools, memory, evals — is scaffolding around this one primitive, so it pays to understand it exactly. This is Part I, Module 1; it assumes you’ve done Module 0 (setup) and have a working API key.

Learning objectives

By the end of this module you should be able to:

  • Describe the LLM as a stateless pure function f(tokens) -> tokens, and explain why “conversation” is an illusion the caller maintains.
  • Explain what a token is, why tokenization exists, and predict the practical consequences (cost, context limits, the “count the r’s” failure class).
  • Explain sampling and temperature: how the model turns a probability distribution into one token, and when to want determinism vs. variance.
  • Use the Messages API fluently: roles, system prompt, max_tokens, stop_reason, usage, multi-turn, and streaming — and explain why each exists.
  • Get reliably machine-parseable output via structured outputs, and articulate why that boundary matters for building systems.
  • Enable extended thinking and know when it earns its cost.
  • Recognize the production failure modes that originate at this layer and the standard mitigations.

1. The model is a stateless pure function

Strip away the chat UI and the marketing, and a large language model is one function:

f(tokens_in) -> distribution over the next token

Call it repeatedly, appending each sampled token to the input, and you get text generation. That’s the whole engine. Three properties of this function are load-bearing for everything you’ll build, and all three are things it does not have:

  • No memory. The function holds no state between calls. It does not remember your last request. Each call is evaluated from scratch against whatever tokens you pass in this time.
  • No clock. It cannot tell you the current time or what happened after its training cutoff. “Today” is whatever its weights learned “today” usually means, plus whatever you put in the prompt.
  • No tools, no side effects. On its own it cannot read a file, call an API, or run code. It emits tokens. That’s it. (Turning those tokens into actions is Module 2 — tool use — and it’s the single change that turns a text model into an agent.)

If you’ve built stateless HTTP services, this is a familiar shape: the LLM is a stateless request/response service, and like any stateless service, all session state lives with the caller. The server is a pure compute function; the client holds the session.

“Conversation” is an illusion the caller maintains

Here is the part that surprises people coming from chat UIs. The model does not “remember” a conversation. When you have a multi-turn chat, what actually happens is: on every single turn, the entire conversation history is re-sent to the model as input. The model re-reads the whole thing from scratch and produces the next message. Then your client appends that message to its local history, and on the next turn re-sends the whole, now-longer transcript again.

The API is stateless. There is no conversation ID on the server holding your history. The “conversation” is a list of messages that you own and you resend. The model is doing the equivalent of being handed the full email thread every time and asked “what’s the next reply?” — it has no recollection of having written the earlier replies; it just reads them as input like everything else.

This single fact explains an enormous amount downstream:

  • Why context windows fill up (you’re resending an ever-growing transcript).
  • Why cost grows super-linearly over a long conversation (more on this in §”Real production issues”).
  • Why “memory” is something you engineer (Module 4), not something the model has.
  • Why an agent loop is just “resend the transcript, get the next action, execute it, append the result, repeat” (Module 3).

Systems analogy. Think of the model as a pure function in a functional language: same input tokens → same output distribution, no hidden state. The “conversation” is an accumulator you thread through repeated calls — like folding over a list, where the transcript is the accumulator. If that accumulator lives only in your process, the conversation lives only in your process.

2. Tokens

The model does not operate on characters or words. It operates on tokens — chunks of text drawn from a fixed vocabulary, typically 50k–200k entries. The pipeline is:

text  --(tokenizer)-->  [token IDs]  --(model)-->  [token IDs]  --(detokenizer)-->  text

What a token is, and why tokenization exists

A token is a subword chunk. Common words are usually a single token; rare words, names, and code fragments get split into several. The vocabulary is built by a process called BPE (byte-pair encoding): start from individual bytes and repeatedly merge the most frequent adjacent pair into a new vocabulary entry, until you hit your target vocabulary size. Frequent substrings (" the", "ing", " def") become single tokens; rare ones stay fragmented.

Why not just use characters or whole words?

  • Characters would make sequences far too long. A 2,000-word document is ~10,000+ characters; processing cost grows with sequence length, so a character-level model would be punishingly expensive and slow.
  • Whole words can’t handle the open-ended vocabulary of real text — new words, typos, code identifiers, other languages, emoji. You’d need an unbounded vocabulary and you’d choke on anything unseen.

Subword tokenization is the engineering compromise: a fixed vocabulary that covers any input (worst case, it falls back to bytes) while keeping sequences short for common text.

Mental model: the embedding table. Each of the ~N vocabulary entries maps to a row in a big lookup table — a learned vector (the embedding). Tokenizing turns your text into a list of integer IDs; the model’s first act is to look up each ID’s row. So “the model reads your prompt” literally means “index into an embedding table with these integers.” A token is a row number.

Practical consequences (this is the part that bites you)

~4 characters per token, in English. A useful rule of thumb: English text is roughly 4 characters (~0.75 words) per token. So 1,000 tokens ≈ 750 words ≈ a page and a half. This is an estimate, not a guarantee — always measure when it matters (below).

Non-English and code cost more. The vocabulary is optimized for the training distribution, which is English-heavy. Languages with different scripts, and code (with its punctuation, indentation, and identifiers), tokenize less efficiently — more tokens per character. The same idea expressed in, say, Japanese or in a dense block of JSON can cost noticeably more tokens than its English-prose equivalent. Since you pay per token, tokenization efficiency is a real cost factor for non-English and code-heavy workloads.

The “count the r’s in strawberry” failure class. The famous failure where a model miscounts the letters in a word is a direct consequence of tokenization. The model never sees s-t-r-a-w-b-e-r-r-y as ten characters; it sees a couple of tokens (something like straw + berry). It has no native, reliable view of the characters inside a token. Character-level tasks — counting letters, reversing strings, strict character manipulation — are exactly the operations the representation hides. The lesson for you as an engineer: don’t ask the model to do precise character-level work; do it in code. (This is your first instance of the course’s recurring theme — move correctness to the boundary.)

Token-boundary quirks. Leading spaces matter. "hello" and " hello" (with a leading space) are often different tokens. This rarely bites you in normal prose, but it surfaces in edge cases like stop sequences, exact-match logic, and prompt formatting. Just know that whitespace is part of the token, not separate from it.

Everything you care about is measured in tokens. Context window size, pricing, and rate limits are all denominated in tokens, not characters or requests. A “1M token context window” and “$3 per million input tokens” and “200K tokens/minute rate limit” are all the same unit. Internalizing tokens as the resource unit is half the battle for cost and capacity planning (Module 10).

Counting tokens correctly

Use the provider’s own tokenizer. For Claude:

import anthropic
client = anthropic.Anthropic()

n = client.messages.count_tokens(
    model="claude-sonnet-4-6",
    messages=[{"role": "user", "content": "How many tokens is this sentence?"}],
).input_tokens
print(n)

⚠️ Do not use tiktoken to count Claude tokens. tiktoken is OpenAI’s tokenizer. Different models use different vocabularies, so a tiktoken count is simply wrong for Claude (it can be off by 15–20% on prose and much more on code). Token counts are model-specific — always count with the tokenizer of the model you’re actually calling. The count_tokens endpoint is the source of truth for Claude.

🛠️ Quick exercise: Run count_tokens on (a) an English paragraph, (b) the same length of source code, and (c) the same text in another language. Note the differences in your notes.md. This is your first piece of cost intuition.

3. Sampling & temperature

At each step the model outputs not a single token but a probability distribution over the entire vocabulary — a number for every one of the ~N entries saying “how likely is this the next token.” Generation then has to pick one token from that distribution. How it picks is sampling, and the main knob is temperature.

How temperature reshapes the distribution

The raw outputs of the model are called logits (unnormalized scores). To turn them into probabilities you apply softmax. Temperature T is a divisor applied to the logits before softmax:

probabilities = softmax(logits / T)
  • T = 1 uses the distribution as-is.
  • T < 1 sharpens it — high-probability tokens get even more probable. At the limit T → 0 you get greedy decoding: always pick the single most likely token. Most deterministic.
  • T > 1 flattens it — probability mass spreads toward less likely tokens. More random, more “creative,” more prone to going off the rails.

Intuitively: low temperature = conservative and repetitive; high temperature = diverse and risky.

top-p and top-k (briefly)

Two related knobs restrict which tokens are eligible before sampling:

  • top-k: only consider the k most likely tokens.
  • top-p (nucleus): only consider the smallest set of tokens whose cumulative probability exceeds p (e.g. 0.9).

Both are truncation strategies to cut off the long tail of very unlikely tokens (which is where a lot of incoherent output comes from). You’ll rarely tune all three; temperature is the one people reach for.

When to use low vs. high temperature

Want Use Examples
Determinism, correctness, structure Low (~0) Extraction, classification, code, anything parsed downstream, agent tool-calling
Some variety, natural phrasing Mid (~0.7) Chat, drafting, summaries
Diversity, brainstorming, exploration High (~1.0+) Idea generation, creative writing, sampling multiple candidates

For agents, you almost always want low temperature: an agent’s job is to take correct, predictable actions, not to be surprising.

Two important caveats

T = 0 is not truly deterministic. Greedy decoding removes the sampling randomness, but you can still get different outputs across calls. Floating-point non-associativity, batching on the provider’s GPUs, hardware and kernel differences, and model updates all introduce variation. Treat T = 0 as “as deterministic as it gets,” not “guaranteed identical.” This matters a lot for testing agents — you cannot rely on byte-identical outputs (see §”Real production issues” and Module 8 on evals).

On the latest Claude models, temperature isn’t exposed. This is worth stating plainly because it will trip you up if you go looking for the parameter. On Claude’s current frontier models (the 4.7/4.8 generation and Fable 5), sampling parameters — temperature, top_p, top_k — are not accepted; passing them is a 400 error. The model manages its own sampling, and you steer behavior with prompting and with adaptive thinking (§6) instead. We still teach temperature as a fundamental concept because (a) it explains what sampling is, which you need in order to reason about determinism and testing, and (b) it’s a first-class parameter on most other APIs — OpenAI’s chat.completions, open models you run yourself, and older Claude models all expose it. So: understand it universally; just don’t expect a temperature= kwarg on the newest Claude calls.

✅ Self-check: You’re writing a function that classifies support tickets into one of five categories, and a separate function that generates three different marketing taglines. Which wants low temperature and which wants high — and why?

4. The Messages / Completion API in practice

Now the concrete interface. The modern shape is a messages API: you send a list of role-tagged messages, you get back a message. Here’s the minimal Claude call:

import anthropic
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": "In one sentence, what is a token?"}],
)

Reading the response

resp.content is a list of content blocks, not a string. Each block has a type. For plain text you’ll get a single text block, but the list shape exists because a response can contain multiple blocks (text, tool-use, thinking, …). Always check the type before reading .text:

for block in resp.content:
    if block.type == "text":
        print(block.text)

Two other fields you’ll read on every call once you care about production:

print(resp.stop_reason)   # why generation stopped
print(resp.usage)         # token accounting

stop_reason tells you why the model stopped:

stop_reason Meaning What you do
end_turn Finished naturally Normal — use the output
max_tokens Hit your max_tokens cap Output is truncated — raise the cap or stream; do not treat as complete
tool_use Wants to call a tool Execute it and continue (Module 2)
refusal Declined for safety reasons Handle it; don’t blindly read content[0]

That max_tokens row is a quiet footgun — see §”Real production issues.”

usage is your billing and capacity meter:

resp.usage.input_tokens                  # tokens you sent (the whole transcript)
resp.usage.output_tokens                 # tokens the model generated
resp.usage.cache_creation_input_tokens   # tokens written to prompt cache (Module 10)
resp.usage.cache_read_input_tokens       # tokens served from cache

You pay separately for input and output (output is usually 4–5× the input price). Logging usage from day one is how you avoid cost surprises later.

Roles and the system prompt

Messages carry a role. The two you send are user and assistant; the model produces assistant. There’s a separate top-level system prompt for instructions/configuration:

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system="You are a terse assistant. Answer in one sentence, no preamble.",
    messages=[{"role": "user", "content": "What is a context window?"}],
)

The system prompt sets the model’s standing instructions; the messages are the conversation. (More on the system prompt in §5.)

Multi-turn = resend the history

Because the API is stateless (§1), multi-turn is just list management. The rules:

  • The first message must be role: "user".
  • You alternate user / assistant, appending the model’s reply back into the list.
  • On each turn you resend the entire list.

A small manager that owns the history:

import anthropic

class ConversationManager:
    """Holds conversation state the API itself doesn't keep."""
    def __init__(self, model="claude-sonnet-4-6", system=None):
        self.client = anthropic.Anthropic()
        self.model = model
        self.system = system
        self.messages = []          # the accumulator we thread through calls

    def send(self, user_text, max_tokens=1024):
        self.messages.append({"role": "user", "content": user_text})
        resp = self.client.messages.create(
            model=self.model,
            max_tokens=max_tokens,
            system=self.system,
            messages=self.messages,  # resend the whole history every time
        )
        text = "".join(b.text for b in resp.content if b.type == "text")
        self.messages.append({"role": "assistant", "content": text})
        return text, resp.usage

chat = ConversationManager(system="You are a helpful assistant.")
print(chat.send("My name is Ada.")[0])
print(chat.send("What's my name?")[0])   # works — because WE resent the history

The model “remembers” Ada only because self.messages carried the first turn into the second call. Delete that line and the memory vanishes. This class is, in miniature, the thing you’ll grow into an agent loop in Module 3.

Streaming, and why it matters

By default messages.create blocks until the full response is generated, then returns it. For long outputs that’s a problem on two fronts: timeouts (a request that takes a minute to generate can exceed HTTP idle timeouts and get dropped) and UX (users stare at a spinner instead of watching text appear). Streaming fixes both by sending tokens as they’re produced:

with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=4096,
    messages=[{"role": "user", "content": "Explain BPE tokenization in detail."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()   # full Message object, with usage/stop_reason

get_final_message() reassembles the complete response (with usage and stop_reason) after the stream finishes, so you get streaming UX and the structured object. For large max_tokens, streaming is effectively required — the SDK will refuse a non-streaming request it estimates will run long enough to risk a timeout. Rule of thumb: small/quick responses can be non-streaming; anything with a big max_tokens or long generation should stream.

📖 Primary-source reading: the provider’s Messages API reference and streaming guide. Read the request/response schema once, end to end — it’s short, and knowing the exact shape pays off when you debug.

5. Prompting fundamentals for engineers

Prompting is a deep topic; this section is deliberately short and practical. The framing that matters for an engineer:

The system prompt is config — a runbook, not a chat message. It’s where the model’s role, constraints, output format, and standing rules live. Treat it like you’d treat a service’s configuration or a function’s docstring-plus-preconditions. It’s stable across turns; the messages are the variable input.

A few principles that earn their keep:

  • Be specific. Vague instructions get vague results. “Summarize this” is worse than “Summarize this in 3 bullet points, each under 15 words, focused on action items.” The model fills ambiguity with its priors, which may not be yours. Specificity is the cheapest quality lever you have.
  • Give clear, ordered instructions. State the task, the constraints, and the output format explicitly. If order matters, say so. If something is forbidden, say so directly.
  • Few-shot examples. For anything with a particular format or style, show don’t just tell. A couple of input→output examples in the prompt (the “few-shot” pattern) often outperforms paragraphs of description, because the model is very good at pattern-matching to demonstrations.
  • Positive instructions beat negative ones. “Respond in plain text” works better than “don’t use markdown.” Tell the model what to do, not just what to avoid.

And the framing that ties prompting to the rest of the course:

Prompts are code. They are the program you ship to the model. That means: version them (a prompt change is a deploy), test them (Module 8 — a prompt change can regress behavior exactly like a code change), and review them. Don’t bury prompts as string literals scattered through your codebase; treat them as first-class, versioned artifacts. The day a model upgrade silently changes how your prompt behaves (this will happen — see “prompt rot” below), you’ll be glad they’re managed like code.

We are intentionally not turning this into a prompt-engineering listicle. The high-leverage move at this layer is not clever phrasing — it’s pushing as much correctness as possible out of the prompt and into verifiable structure. Which is exactly the next section.

6. Structured output

A huge amount of agent engineering happens at the boundary between the model (which emits text) and your code (which needs typed data). If you ask the model for JSON in prose and then json.loads() the reply, you are one stray markdown fence or trailing comma away from a crash. Structured outputs make that boundary reliable by constraining the model’s output to a schema you define.

The clean way in Python is Pydantic plus messages.parse:

from pydantic import BaseModel
import anthropic

class Ticket(BaseModel):
    category: str
    priority: int
    summary: str

client = anthropic.Anthropic()
resp = client.messages.parse(
    model="claude-sonnet-4-6",
    max_tokens=512,
    messages=[{"role": "user", "content":
        "Triage: 'The export button 500s every time on the billing page. Blocking month-end close.'"}],
    output_format=Ticket,
)

ticket = resp.parsed_output      # a validated Ticket instance — typed, not a string
print(ticket.category, ticket.priority, ticket.summary)

resp.parsed_output is an actual Ticket object: the field types are enforced, and you didn’t write any parsing or validation code. Under the hood the SDK derives a JSON Schema from your Pydantic model and constrains generation to it. If you don’t use Pydantic, you can pass a raw JSON Schema directly:

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=512,
    messages=[{"role": "user", "content": "..."}],
    output_config={"format": {"type": "json_schema", "schema": {
        "type": "object",
        "properties": {
            "category": {"type": "string"},
            "priority": {"type": "integer"},
            "summary":  {"type": "string"},
        },
        "required": ["category", "priority", "summary"],
        "additionalProperties": False,
    }}},
)

A note on prefill. A classic older trick was to “prefill” the assistant turn — start the assistant message with { to coax JSON out. On current Claude models, assistant prefill is not supported (it returns a 400). Structured outputs are the supported, and frankly better, replacement: instead of nudging the model toward a format and hoping, you constrain it to one and validate.

Why this matters for building systems. Structured output is the first concrete instance of the course’s central engineering move: move correctness to the boundary. Rather than trusting that the model produced well-formed data, you define the shape, constrain generation to it, and validate. The model’s job shrinks to “fill in the fields”; the correctness of the shape is handled by schema and code, not by hope. You’ll see this same move again and again — exact-match edits, permission gates, forced verification — and it starts here, at the model/code boundary.

7. Extended thinking (reasoning mode)

Current frontier models support an extended thinking mode: before producing the final answer, the model generates intermediate reasoning. This consistently improves performance on hard, multi-step problems — math, complex coding, careful analysis, agentic planning — at the cost of more latency and more tokens.

On Claude 4.6+, you enable it adaptively and tune depth with an effort knob:

resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=4096,
    thinking={"type": "adaptive"},          # model decides when/how much to think
    output_config={"effort": "high"},       # low | medium | high | max
    messages=[{"role": "user", "content":
        "A bat and ball cost $1.10 total. The bat costs $1.00 more than the ball. "
        "How much does the ball cost? Reason carefully."}],
)
for block in resp.content:
    if block.type == "thinking":
        print("[thinking]", block.thinking)   # reasoning shows up as thinking blocks
    elif block.type == "text":
        print(block.text)

Notes for now (you’ll use this heavily in later modules):

  • thinking={"type": "adaptive"} lets the model decide how much to think per request; effort sets the overall depth/spend tradeoff. The older “fixed token budget for thinking” style is deprecated on the latest models — use adaptive.
  • Thinking appears in the response as blocks of type == "thinking", ahead of the text answer. This is why checking block.type (§4) is not optional.
  • When it helps: genuinely hard reasoning, planning, and verification. When it doesn’t: simple lookups, classification, formatting — it just adds latency and cost. Don’t reflexively turn it to max; it’s a dial, not a switch.

🛠️ Exercise — scout/llm.py, the thin wrapper

Everything you build in this course talks to the model through one thin layer. Build it now. The goal is a tiny, boring, well-instrumented wrapper — not a framework. You’ll import this in Module 3 when Scout gets its loop.

Part A — the wrapper. Create scout/llm.py with two helpers:

# scout/llm.py
import anthropic

_client = anthropic.Anthropic()
DEFAULT_MODEL = "claude-sonnet-4-6"

def chat(messages, system=None, model=DEFAULT_MODEL, max_tokens=1024, **kw):
    """Thin wrapper over messages.create. Returns (text, usage)."""
    resp = _client.messages.create(
        model=model, max_tokens=max_tokens, system=system,
        messages=messages, **kw,
    )
    if resp.stop_reason == "max_tokens":
        # Loud, not silent: truncation is a bug you want to see (see Real production issues).
        print(f"[warn] response truncated (stop_reason=max_tokens); raise max_tokens")
    text = "".join(b.text for b in resp.content if b.type == "text")
    return text, resp.usage

def count(text, model=DEFAULT_MODEL):
    """Token count for a string, using the CORRECT (model-specific) tokenizer."""
    return _client.messages.count_tokens(
        model=model, messages=[{"role": "user", "content": text}],
    ).input_tokens

Part B — prove statelessness. Write a script that holds a 3-turn conversation two ways:

  1. With history: build up a messages list, appending each assistant reply, and on turn 3 ask the model something that depends on turn 1 (e.g. tell it your name in turn 1, ask for it in turn 3). It should answer correctly.
  2. Without history: make three independent chat() calls, each with only the current user message. On turn 3, ask the same name question. It should fail — it has no idea.

Print both transcripts side by side. Seeing the model “forget” when you don’t resend history is the single most important intuition in this module.

Part C — tokens and cost. Take a ~200-word prompt. Use count() to get its token count. Then compute the input cost using Sonnet’s pricing ($3 / 1M input tokens): cost = tokens / 1_000_000 * 3. Print tokens and dollars. Repeat with a block of source code of similar length and note how the token count differs.

Part D — structured extraction. Define a Pydantic model (e.g. Contact with name: str, email: str, company: str | None) and use messages.parse to extract it from a messy sentence like “reach out to Dr. Lin Wei at lwei@acme.io, she runs ML infra at Acme.” Print the validated object. Then deliberately feed it an input with no email and observe what happens — this is your first taste of the boundary failing, which Module 8 will teach you to handle systematically.

Log everything in notes.md. For each part, record the usage (input/output tokens), the dollar cost, and any surprises. This notebook habit — writing down what the model actually did — is how you build taste. You’ll thank yourself in Module 8.

✅ When Part B’s “without history” run forgets your name and the “with history” run remembers it, you’ve internalized §1. That’s the win.

Real production issues

These are the failure modes that originate at this layer — the model and the API — and that practitioners hit in real systems. This section is the highest-value part of the module; the failures here recur in every later module, so meet them now.

Nondeterminism complicates testing. Even at the most deterministic settings, the same input can yield different outputs (§3). You cannot write assert output == "expected_string" and trust it. This breaks every testing instinct you have from deterministic software. The mitigation is a whole discipline — evals (Module 8): instead of exact-match, you grade outputs (programmatically, or with an LLM-as-judge), run multiple samples, and measure rates of correctness rather than asserting single results. For now, just internalize: the unit of correctness here is statistical, not exact. Don’t build a test suite that assumes byte-identical output.

Token cost surprises. Three independent ways the bill grows faster than you expect:

  • Non-English and code cost more tokens per character (§2). A pipeline benchmarked on English prose can cost noticeably more on code or other languages.
  • Verbose outputs. Output tokens are the expensive ones (often ~4–5× input price). A model that “thinks out loud” or pads its answers burns money. Constrain output length when you don’t need it.
  • The quadratic transcript. This is the big one for multi-turn and agents, and it’s worth seeing clearly. Because you resend the whole history every turn (§1), a conversation of N turns sends turn 1’s content N times, turn 2’s N-1 times, and so on. Total input tokens processed across the conversation grows roughly with the square of its length. A long agent run isn’t linear in cost — it’s quadratic. (This is the motivation for context management and prompt caching, Modules 4 and 10. Just register the shape now.)

Context-window limits are a hard wall. The context window (e.g. 1M or 200K tokens) is a fixed cap on input + output. It is not a soft suggestion — exceed it and the request fails or, worse, gets silently truncated depending on the path. “1M tokens” feels infinite until a long-running agent, resending its growing transcript, hits it routinely. Treat the window as a managed resource with a budget, exactly the way you’d treat a fixed memory region. (Managing it is Module 4.)

max_tokens truncation — the silent cutoff. max_tokens caps the output. If the model wants to write more than your cap allows, generation stops mid-sentence and stop_reason comes back as "max_tokens". Crucially, you do not get an error — you get a truncated response that looks like a complete one if you don’t check. Code that reads resp.content[0].text without inspecting stop_reason will happily process half a JSON object. Always check stop_reason == "max_tokens" and either raise the cap, stream, or handle the truncation explicitly. (The exercise wrapper warns on this deliberately.)

Structured-output drift and parse failures. Even with structured outputs, things can go wrong: a refusal (stop_reason == "refusal") means the output may not match your schema at all; a max_tokens cutoff can truncate the JSON mid-object; and if you’re hand-parsing model JSON without structured outputs, the model occasionally adds prose, fences, or trailing commas. Mitigations, in order of preference: (1) use structured outputs / messages.parse so the shape is enforced and validated; (2) check stop_reason before trusting the output; (3) wrap parsing in a try/except and, on failure, retry — often a single retry with the error message fed back fixes it. The pattern is detect cheaply, retry — the boundary’s job is to make failures visible and recoverable, not to never fail.

Prompt brittleness across model upgrades (“prompt rot”). A prompt carefully tuned for one model version can behave differently — sometimes worse — on the next. A model upgrade is, behaviorally, a dependency upgrade: it can change outputs even with your code untouched. This is why “prompts are code” (§5) is not a slogan: you want your prompts versioned and covered by evals (Module 8) so that when you bump the model, you can measure whether behavior regressed instead of finding out from users. The real-world cadence: pin your model ID, change it deliberately, and re-run your eval suite on every model change.

No clock, no fresh knowledge. The model has a training cutoff and no access to the current time or to anything that happened after that cutoff (§1). Ask it about today’s date, a recent event, or your private data, and it will either decline or — worse — confidently make something up (a “hallucination”). The model doesn’t know what it doesn’t know. This single limitation is the entire motivation for two later topics: tools (Module 2 — give it a clock, a search function, a way to fetch fresh data) and retrieval / RAG (Module 5 — give it access to your documents). When you find yourself wishing the model knew something it can’t, that’s the signal that you need to give it that knowledge through the harness, not hope it’s in the weights.
