Module 0 — Setup & Orientation

Goal: a working environment, an API key, and a clear picture of the model landscape you’ll be building on. ~30 minutes.

0.1 Environment 

# A fresh project directory and virtualenv
mkdir scout && cd scout
python3 -m venv .venv && source .venv/bin/activate
python --version   # need 3.10+

# Core libraries used across the course
pip install anthropic openai python-dotenv pydantic rich
# (later modules add: langgraph, langfuse, chromadb, etc. — installed as needed)

Create a .env file (and add it to .gitignore immediately):

ANTHROPIC_API_KEY=sk-ant-...
# Optional, used in a few comparisons:
OPENAI_API_KEY=sk-...

Load it in code:

from dotenv import load_dotenv
load_dotenv()  # now os.environ["ANTHROPIC_API_KEY"] is available

Never hardcode keys. Treat them like database credentials. The agent you build will execute model-chosen actions — you do not want a leaked key attached to that. (Security is Module 11; the habit starts now.)

0.2 Get an API key

  • Anthropic (Claude): console.anthropic.com → API keys. Used as the primary provider in this course.
  • OpenAI: platform.openai.com → API keys. Used in a couple of comparisons (Module 7).

You can do the entire course with just one provider. Examples default to Claude.

0.3 Hello, model — verify your setup 

import anthropic
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model="claude-sonnet-4-6",          # cheap + fast; great default for learning
    max_tokens=1024,
    messages=[{"role": "user", "content": "In one sentence: what is an agent?"}],
)
print(resp.content[0].text)
print(resp.usage)  # note input_tokens / output_tokens — you'll care about these

If that prints a sentence and a usage object, you’re ready.

0.4 The model landscape (as of mid-2026)

You don’t need to memorize this, but you should know the shape of the menu. Models are priced per million tokens (MTok), input and output billed separately. Bigger/smarter = more expensive and slower.

Model ID (string you pass) Context Input $/MTok Output $/MTok Use it for
Claude Opus 4.8 claude-opus-4-8 1M $5 $25 The hard reasoning / main agent loop. The default “smart” model.
Claude Sonnet 4.6 claude-sonnet-4-6 1M $3 $15 High-volume production; the learning default in this course.
Claude Haiku 4.5 claude-haiku-4-5 200K $1 $5 Cheap/fast subtasks: classification, sub-agent search, commit messages.
Claude Fable 5 claude-fable-5 1M $10 $50 The most capable model; longest-horizon agentic work.

(There are also claude-opus-4-7, claude-opus-4-6, etc. — previous generations, still available.)

Three facts that will matter throughout the course:

  1. Model tiering is an engineering lever, not a detail. A real agent uses a cheap model for grunt work (summarizing, searching, routing) and an expensive model only where judgment is needed. This is the single biggest cost lever (Module 10). For learning, default to Sonnet; switch to Opus/Fable when you want maximum capability.
  2. Context windows are large but finite. “1M tokens” sounds infinite; a long-running agent exhausts it routinely. Managing it is Module 4.
  3. The exact model ID string matters. Pass it verbatim — no date suffixes on these aliases. A typo’d model ID is a 404, not a fallback.

A note on “thinking” / reasoning

Current frontier models support an extended reasoning mode where the model thinks before answering. On Claude 4.6+ you enable it with thinking={"type": "adaptive"} (the model decides how much to think) and tune depth with output_config={"effort": "low"|"medium"|"high"|"max"}. You’ll use this in later modules; for now just know it exists and that it trades latency/cost for quality. (The old “fixed token budget” style of thinking is deprecated on the latest models — use adaptive.)

0.6 Mindset

Three framings to carry through the whole course:

  • The model is a CPU; the harness is the OS. The model does one “instruction” per call — given the current state, pick the next action. Everything else — tools (syscalls), context management (memory), the loop and sub-agents (scheduling), permissions (protection rings) — is the harness, and it’s where nearly all the engineering lives.
  • Move correctness out of the model and into the boundary. Exact-match edits, schema validation, permission gates, forced verification — each converts “hope the model is right” into “detect cheaply and let it retry.” You’ll see this pattern in every module.
  • Tokens are a scarce, priced resource with cache locality. Design transcript layout, truncation, delegation, and model tiering the way you’d design around a memory hierarchy.
