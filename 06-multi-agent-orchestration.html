Module 06 — Multi-Agent Systems & Orchestration

In Module 03 you built Scout: one loop, one context window, one model deciding everything. In Module 04 you spawned a delegate sub-agent — a child loop with its own window — but only as a context firewall, a way to keep the parent’s transcript small. This module is about the other reason to reach for multiple agents and, more importantly, when not to.

Here is the trap. “Multi-agent” sounds like the sophisticated thing to build, the architecture that separates a real system from a toy. It is mostly the opposite. Most of what gets sold as a “multi-agent system” is a handful of LLM calls wired together with ordinary code — a pipeline, a router, a fan-out — with at most one or two genuinely agentic leaves. The engineering skill here is not “how do I make agents talk to each other.” It’s recognizing which parts of your problem need a model deciding the control flow at runtime, and which parts you should just write as code — because every bit of model-driven autonomy you add trades latency, cost, and predictability for flexibility, and you only want that trade where flexibility actually pays.

The frame we’ll use throughout is Anthropic’s, from “Building Effective Agents”: the distinction between workflows and agents, and a small set of composable patterns that cover almost everything you’ll build. Frameworks (Module 07) are just packaging for these patterns — learn the patterns first and the frameworks become obvious.

Learning objectives

  • State the workflow-vs-agent distinction precisely (who controls the control flow: your code, or the model) and apply “start simple — only add autonomy where it clearly pays.”
  • Recognize and implement the five composable patterns: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-worker, and evaluator-optimizer.
  • Build the sub-agent process-tree mental model: a task description down, a summary up, isolated context in between.
  • Diagnose the lossy interface between parent and child — the central hard problem of multi-agent systems — and harden it with templated prompts, structured output, redundancy, and deterministic code orchestration.
  • Reason quantitatively about the cost and latency of fan-out: pipeline vs. barrier, and when multi-agent is worth 4–15× the tokens of a single agent.

Workflows vs. agents: who holds the control flow

This is the load-bearing distinction. Hold it in your head as a systems question about where the control flow lives.

📖 Workflows are systems where LLM calls and tools are orchestrated through predefined code paths. You wrote the if, the for, the sequence of steps. The model fills in the blanks at each step, but it does not decide what the next step is.

Agents are systems where the model dynamically directs its own process and tool use — it chooses which tool to call, in what order, when to stop. The control flow is decided at runtime, by the model, inside the loop.

Scout is an agent: its loop hands the model a set of tools and the model decides, turn by turn, what to do. A function that calls the model to classify a ticket, then matches on the label to call one of three other prompts, is a workflow: the model classifies, but your code routes.

The dataflow analogy: a workflow is a static dataflow graph you compiled ahead of time — you can read it, test each node, predict its shape. An agent is a graph that rewrites itself as it runs. The agentic graph is strictly more powerful and strictly less predictable, and that’s the entire tradeoff.

Why this matters for what you build. Autonomy is not free. Each time you let the model decide the next step instead of writing that decision in code, you pay:

  • Latency — an extra round trip (or several) where code would have branched instantly.
  • Cost — more tokens, re-sent history every turn, often a bigger model to make the decision reliably.
  • Unpredictability — a path you can’t fully enumerate, can’t unit-test exhaustively, and can’t reason about the way you reason about a switch.

You buy flexibility — the ability to handle inputs and trajectories you didn’t anticipate. That’s worth a lot for open-ended tasks (“turn this design doc into a PR”) and worth nothing for closed ones (“extract the invoice total from this PDF”). The discipline, straight from “Building Effective Agents”:

Find the simplest thing that works. Add agentic autonomy only when the flexibility from model-driven decisions clearly improves the outcome. Sometimes the right answer is a single LLM call. Sometimes it’s a workflow. Sometimes — honestly — it’s no LLM at all.

A useful gut check before reaching for “an agent” (or worse, “several agents”): is the task genuinely hard to specify up front, does the outcome justify the extra latency and cost, is the model actually good at this task type, and can you catch and recover from its mistakes? If any answer is “no,” drop down a tier. Most production systems that feel agentic are 90% workflow with one or two agentic leaves — and that’s a feature, not a compromise.

The composable patterns

These five patterns, again from Anthropic’s taxonomy, are the building blocks. They compose: a real system is usually a workflow whose nodes are sometimes single calls, sometimes other patterns, and occasionally a full agent. We’ll teach each with a text diagram, when to use it, and a code sketch. All sketches reuse Scout’s client and its run_agent / sub-agent loop from Modules 03–04; only the orchestration around them changes.

A note on models, carried through every sketch: the orchestrator and judge are the expensive, intelligence-sensitive roles — default them to claude-opus-4-8. The workers and routers are high-volume and narrow — run them on claude-haiku-4-5 (or claude-sonnet-4-6 when a worker needs more reasoning). This split is where most of the cost control in a multi-agent system lives.

1. Prompt chaining

Decompose a task into a fixed sequence of steps, each an LLM call, feeding the previous output into the next. Optionally gate between steps — a programmatic check that can short-circuit or retry.

input → [call 1] → (gate?) → [call 2] → [call 3] → output
                     │
                     └─ fail → stop / retry

When to use it: the task cleanly splits into fixed subtasks, and trading latency for accuracy is worth it. Each call does one thing well instead of one call doing three things poorly. Classic example: draft an outline → check the outline meets a criterion → write the doc from the outline.

def write_brief(topic: str) -> str:
    outline = one_shot(f"Write a 5-bullet outline for a brief on: {topic}")
    # Gate: a deterministic check between steps.
    if outline.count("\n-") < 3:
        raise ValueError("outline too thin; not proceeding")
    return one_shot(f"Write the brief from this outline:\n{outline}")

def one_shot(prompt: str, model="claude-sonnet-4-6") -> str:
    resp = client.messages.create(
        model=model, max_tokens=2048,
        messages=[{"role": "user", "content": prompt}],
    )
    return next(b.text for b in resp.content if b.type == "text")

The control flow is entirely in your code. The model never decides what comes next.

2. Routing

Classify the input, then dispatch to a specialized handler — a different prompt, a different tool set, a different model.

                 ┌─ "billing"  → [billing prompt]
input → [classify] ─ "technical" → [technical prompt + tools]
                 └─ "refund"   → [refund prompt, opus]

When to use it: distinct categories of input are better served by distinct handling, and you can classify reliably. Routing lets you keep each handler’s prompt focused (no mega-prompt trying to cover every case) and send cheap categories to a cheap model while reserving the expensive model for the hard ones.

def route(query: str) -> str:
    # A cheap, narrow classifier — perfect Haiku job.
    label = one_shot(
        f"Classify into exactly one of [billing, technical, refund]. "
        f"Reply with only the label.\n\n{query}",
        model="claude-haiku-4-5",
    ).strip()

    handlers = {
        "billing": lambda q: one_shot(BILLING_PROMPT + q),
        "technical": lambda q: run_agent(TECH_PROMPT + q),  # a full Scout loop
        "refund": lambda q: one_shot(REFUND_PROMPT + q, model="claude-opus-4-8"),
    }
    return handlers.get(label, handlers["technical"])(query)

Note the leaves differ in kind: one is a single call, one is a full agent, one is a single call on a bigger model. Routing is the join.

3. Parallelization

Run multiple LLM calls concurrently and aggregate. Two distinct flavors:

Sectioning — split a task into independent subtasks that run in parallel because they don’t depend on each other.

Voting — run the same task N times and aggregate the answers (majority vote, take-any-that-passes, etc.) to raise reliability or coverage.

sectioning:                       voting:
        ┌─[subtask A]─┐                  ┌─[run 1]─┐
input ──┼─[subtask B]─┼─[merge]   input ─┼─[run 2]─┼─[aggregate]
        └─[subtask C]─┘                  └─[run 3]─┘

When to use sectioning: the work decomposes into parts with no data dependency (analyze 5 documents; review code for security, style, and performance separately). When to use voting: you want higher confidence on a single hard judgment, or broader coverage of a search space, and you’re willing to pay N× for it.

from concurrent.futures import ThreadPoolExecutor

def section(subtasks: list[str]) -> list[str]:
    with ThreadPoolExecutor(max_workers=8) as pool:
        return list(pool.map(lambda t: one_shot(t, model="claude-haiku-4-5"),
                             subtasks))

def vote(prompt: str, n: int = 3) -> str:
    answers = section([prompt] * n)
    return max(set(answers), key=answers.count)  # crude majority

The Anthropic SDK is synchronous per call; ThreadPoolExecutor is the simplest way to fan out (each call is I/O-bound, so threads are fine — no GIL contention on network waits). asyncio with AsyncAnthropic is the same idea with explicit concurrency.

4. Orchestrator-worker

A coordinator agent decomposes a task at runtime and delegates subtasks to worker sub-agents, then synthesizes their results. The key difference from sectioning: the subtasks are not fixed in advance — the orchestrator (a model) decides how many workers to spawn and what each one does, based on the input.

              ┌─ spawns ─→ [worker 1] ─ summary ─┐
[orchestrator]─── spawns ─→ [worker 2] ─ summary ─┼─→ [synthesize] → output
   (opus)     └─ spawns ─→ [worker N] ─ summary ─┘
                            (haiku, fresh loops)

When to use it: the subtasks can’t be enumerated ahead of time because they depend on the specific input. The canonical case is open-ended research: you can’t know in advance which five sub-questions a research query decomposes into — the orchestrator reads the query and decides. This is the pattern the exercise builds.

Sectioning is a workflow (you wrote the split); orchestrator-worker is agentic at the top (the model wrote the split). That difference is exactly the workflow-vs-agent line drawn through the parallelization pattern.

5. Evaluator-optimizer

One model generates, a second evaluates against explicit criteria, and if the work falls short, it goes back for revision — looping until it passes or you hit a cap.

          ┌──────────────────────────────┐
input → [generate] → [evaluate] ─ pass → output
              ↑           │
              └─ revise ──┘ (fail: feedback)

When to use it: you have clear evaluation criteria and iterative refinement measurably helps — translation with a quality bar, code that must pass a review, a research synthesis that must cover certain points. The separation matters: a fresh model judging against a rubric catches things the generator, anchored on its own output, won’t. This is the same generate/judge split you’ll formalize as LLM-as-judge in Module 08 on evals — here it runs inline, as a control structure.

def generate_and_refine(task: str, rubric: str, max_rounds=2) -> str:
    draft = one_shot(task, model="claude-sonnet-4-6")
    for _ in range(max_rounds):
        verdict = judge(draft, rubric)           # returns (passed, feedback)
        if verdict.passed:
            return draft
        draft = one_shot(f"{task}\n\nRevise to fix:\n{verdict.feedback}\n\n"
                         f"Current draft:\n{draft}", model="claude-sonnet-4-6")
    return draft  # best effort after the cap

We’ll make judge return structured output below — that’s how you get a reliable passed boolean instead of parsing prose.

Sub-agents in depth: the process tree

The orchestrator-worker and evaluator-optimizer patterns both rest on sub-agents, so let’s make the mental model precise. It’s the process tree.

📖 A sub-agent is a fresh inner agent loop — its own messages list, its own (possibly restricted) tool set, its own iteration budget — that the parent spawns to do a scoped piece of work and that returns a short summary string to the parent. The parent holds the goal; the children do scoped work in isolated context windows. The interface is exactly two natural-language strings: a task description going down, a summary coming up.

Map it onto a Unix process tree and the engineering intuition snaps into focus. The parent forks a child, hands it arguments (the task prompt), the child runs in its own address space (its own context window) where it can allocate and free as much as it wants without touching the parent’s memory, and on exit it returns a small status (the summary). The child’s heap — all that searching and reading — is torn down. Only the return value crosses back.

Why spawn children at all? Three reasons, and they’re distinct:

  1. Context isolation (the Module 04 firewall motivation — we won’t re-teach it). The child can burn 80K tokens exploring; the parent absorbs three sentences. This keeps the parent’s window — and thus its coherence and its bill — bounded.
  2. Parallelism. Independent children run concurrently. Three research workers in parallel finish in roughly the time of the slowest one, not the sum.
  3. Specialization. Each child gets a tailored system prompt, a restricted tool set (a search worker doesn’t need write_file), and an appropriate model. A narrow agent on a narrow task is more reliable than a generalist juggling everything.

There’s real evidence this pays off for the right shape of problem. Anthropic reported that a multi-agent research system — an orchestrator fanning out to parallel search sub-agents — substantially outperformed a single agent on broad, open-ended research queries, where the work parallelizes across many independent search directions and the bottleneck is breadth of exploration. The crucial caveat in the same breath: it burned far more tokens (multi-agent research used on the order of 15× the tokens of a plain chat interaction). Multi-agent buys you parallel breadth; you pay for it in tokens. That trade is great for high-value research and terrible for a task a single well-managed agent handles fine.

Here’s an orchestrator-worker skeleton — the shape the exercise fleshes out. The orchestrator decomposes, fans out fresh Scout-style loops as workers (each with web_search / search_knowledge from Module 03), collects summaries, and synthesizes:

def research(question: str) -> str:
    # 1. Orchestrator (opus) decomposes into sub-questions at runtime.
    sub_qs = decompose(question)                  # model decides how many & what

    # 2. Fan out one worker per sub-question, in parallel.
    with ThreadPoolExecutor(max_workers=5) as pool:
        findings = list(pool.map(research_worker, sub_qs))

    # 3. Orchestrator synthesizes the collected summaries.
    return synthesize(question, findings)

def research_worker(sub_q: str) -> str:
    """A fresh Scout loop: web_search/search_knowledge only, returns a summary."""
    messages = [{"role": "user", "content": sub_q}]
    for _ in range(8):                            # bound the child
        resp = client.messages.create(
            model="claude-haiku-4-5", max_tokens=2048,
            system=WORKER_SYSTEM,                 # "research, then summarize..."
            tools=SEARCH_TOOLS,                   # restricted: no write/bash
            messages=messages,
        )
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return next(b.text for b in resp.content if b.type == "text")
        messages.append({"role": "user", "content": run_tools(resp.content)})
    return "Worker hit its iteration cap."

The lossy interface: the hard part

Everything above is the easy 80%. This is the 20% that decides whether your multi-agent system works or quietly produces garbage.

📖 The parent↔child interface is two natural-language strings: the task prompt down and the summary up. Both are lossy. Compression happens at both ends, and the parent never sees the child’s actual work — only the summary. There is no shared memory, no return of the full transcript, no type checking on natural language. Whatever didn’t make it into those two strings is gone.

This is, in spirit, Conway’s law inside a single program: the structure of communication between your agents shapes — and limits — what they can produce together. Two failure modes dominate, and they’re the multi-agent analog of the sub-agent pitfalls flagged back in Module 04:

The child solves a slightly different problem than intended. The task prompt was ambiguous, or under-specified, or the child interpreted “find the auth bug” as “find an auth issue” and confidently reported a different one. The parent has no way to notice — the summary reads fine. You get a plausible answer to the wrong question. This is the most insidious failure because nothing errors; it just drifts.

The child buries the load-bearing detail. The child did the right work, found the exact file and line, then wrote a tidy summary — “fixed the issue in the parser” — that dropped the file path. The parent reads the summary, can’t act on it, and has to re-do the search it paid the child to do. The firewall worked; the interface leaked the one fact that mattered.

Both failures come from treating a natural-language string as if it were a typed return value. The mitigations all push in the same direction — make the interface less lossy, or make the orchestration not depend on the model getting the interface right:

1. Explicit, templated task prompts. Tell the child exactly what to report and in what shape. Not “investigate the bug” but “find the function that raises KeyError on empty input; report the file path and line number, the failing condition, and a one-line fix — not prose.” You’re writing the child’s contract. The Module 04 sub-agent prompt already gestured at this (“include file paths, line numbers, exact findings”); here it’s the primary defense.

2. Structured output for child results. This is the strongest single fix. Instead of free text, have the child return a schema-validated object. With the Anthropic SDK, define a Pydantic model and use client.messages.parse(..., output_format=Model) → resp.parsed_output:

from pydantic import BaseModel

class WorkerFinding(BaseModel):
    key_findings: list[str]    # the load-bearing facts, itemized
    sources: list[str]         # urls / file:line — forces specificity
    confidence: float          # 0–1, so the parent can weight it

def research_worker(sub_q: str) -> WorkerFinding:
    resp = client.messages.parse(
        model="claude-haiku-4-5", max_tokens=2048,
        system=WORKER_SYSTEM, tools=SEARCH_TOOLS,
        messages=[{"role": "user", "content": sub_q}],
        output_format=WorkerFinding,
    )
    return resp.parsed_output   # a validated WorkerFinding, not a string

Now the “buried detail” failure is structurally harder: sources is a required field, so an empty list is a visible signal, not a silent omission. The schema is the contract, and the API enforces it.

3. Overlap, redundancy, and voting for high-stakes work. For a judgment you can’t afford to get wrong, run the sub-task more than once (the voting pattern) or give two workers overlapping scopes and reconcile. Redundancy is how you buy reliability across a lossy channel — same reason you’d checksum a flaky link.

4. Keep orchestration control flow as deterministic code. This is the big one. The loops, the fan-out, the barriers, the retry-on-empty-sources — write all of that in Python. Put the model only inside the leaves. Do not ask a model to manage other models freehand — “you are a manager agent, spawn whatever sub-agents you need and coordinate them” is the anti-pattern. A model orchestrating models compounds the lossy interface at every hop and gives you a system whose control flow you can neither see nor test. The orchestrator model should decide the decomposition (what the sub-questions are); your code should execute the orchestration (spawn, collect, barrier, synthesize). Decision in the model, mechanism in code.

That last point is the synthesis of the whole module: the workflow-vs-agent line isn’t drawn once at the top of your system — you redraw it at every level. Let the model decide where deciding pays; let code do everything else.

Cost and latency: think like a scheduler

Fan-out has a price, and the dataflow-scheduling intuition tells you when to pay it.

Tokens. N workers means roughly N× the worker tokens, plus the orchestrator’s decompose and synthesize calls (which re-send the collected summaries). This is why multi-agent runs 4–15× the tokens of a single agent — the high end being broad parallel research, the low end a modest two-or-three-worker fan-out. Before you fan out, ask whether a single well-managed agent with good context handling (Module 04) gets you there for a fifth of the cost. Often it does.

Pipeline vs. barrier. A barrier is a synchronization point where you wait for all parallel work to finish before proceeding — pool.map returns only when every worker is done. Barriers are correct when the next stage genuinely needs every prior result: the synthesizer can’t write the final answer until all the findings are in. But don’t barrier reflexively. If stage B only needs worker 1’s output, don’t make it wait for workers 2–5 — that’s the dataflow-scheduling lesson: synchronize on actual data dependencies, not on convenience. A barrier costs you the slowest worker every time; a pipeline that streams results as they finish hides that latency.

The slowest-worker tax. At a barrier, your latency is the max over workers, not the mean. One worker that takes a slow tool call or hits a retry stalls the whole stage. Mitigations: cap each worker’s iteration budget tightly, set per-call timeouts, and consider returning partial results if a worker exceeds its deadline rather than blocking the barrier indefinitely.

When multi-agent is worth it. Worth it: broad, parallelizable exploration where breadth is the bottleneck and the outcome is high-value (research, large-scale review, multi-document analysis). Not worth it: anything a single agent with truncation, compaction, and a plan file handles inside its window. The honest default is one good agent; reach for many only when the problem’s shape — independent, parallel, breadth-bound — actually rewards it.

🛠️ Exercise

Build an orchestrator-worker research agent on top of Scout, then bolt an evaluator-optimizer loop onto it, and measure it against a single Scout instance. This exercises every concept in the module: runtime decomposition, parallel sub-agents, the structured-output fix for the lossy interface, the generate/judge loop, and the cost/latency reality.

Build it in stages.

(a) The orchestrator. Write decompose(question) -> list[str] using claude-opus-4-8. Prompt it to break the research question into 3–5 independent sub-questions, and return them as structured output (a Pydantic Decomposition model with a sub_questions: list[str] field) so you get a clean list, not prose you have to parse. This is the agentic leaf at the top — the model decides the decomposition.

(b) The workers, in parallel, with structured returns. Write research_worker(sub_q) -> WorkerFinding as a fresh Scout loop on claude-haiku-4-5 (or claude-sonnet-4-6 if Haiku struggles), restricted to web_search and search_knowledge — no write_file, no run_bash. Return the WorkerFinding Pydantic model from the lossy-interface section (key_findings, sources, confidence) via messages.parse. Fan out one worker per sub-question in parallel with concurrent.futures.ThreadPoolExecutor (or asyncio + AsyncAnthropic). This barrier is justified — synthesis needs all findings.

(c) Synthesis. Write synthesize(question, findings) -> str on claude-opus-4-8: hand it the original question and all the WorkerFinding objects (their structure makes the prompt clean — itemized findings with sources), and have it write the final answer with the sources woven in.

(d) The evaluator-optimizer loop. Write judge(answer, question) -> Verdict on claude-opus-4-8, scoring the synthesis against a small rubric (coverage of the sub-questions, are claims sourced, internal consistency) and returning a structured Verdict(passed: bool, score: int, feedback: str). If passed is false, send the synthesis back through synthesize once with the judge’s feedback appended. Cap at one revision — this is a control structure, not an infinite polish loop.

(e) The bake-off — this is the point of the exercise. Run the same research question two ways: through your multi-agent pipeline, and through a single Scout instance with the same search tools. For each, log to notes.md: answer quality (your own read, plus the judge’s score on both), total tokens (sum usage.input_tokens + usage.output_tokens across every call — orchestrator, all workers, synthesis, judge), and wall-clock latency.

What to observe and write up. You should see the multi-agent run cost several times the tokens of the single agent (quantify it — is it 4×? 10×?), take comparable or better wall-clock time despite more work (because the workers ran in parallel), and produce a broader, better-sourced answer on a genuinely broad question. Then try a narrow question — one a single agent handles in three tool calls — and watch the multi-agent version pay the full fan-out tax for no quality gain. That contrast is the entire module in one experiment: multi-agent earns its cost only when the problem’s shape rewards parallel breadth. Note in notes.md which question type each architecture won, and why.

Real production issues

  • Orchestration complexity scales badly. Agents waiting on agents waiting on agents; a worker that itself spawns workers; race conditions when two children touch shared state (a file, a database, a rate limit); cascading failures where one child’s bad output poisons the synthesis. Every layer of model-managed coordination multiplies the failure surface. This is the strongest argument for keeping orchestration in deterministic code: code’s failure modes are the ones you already know how to handle.
  • The lossy hand-off causes wrong-problem solving. The single most common subtle bug: a child confidently, fluently answers a slightly different question than the one intended, and the parent has no way to detect it because the summary reads perfectly. Templated prompts and structured output reduce it; they don’t eliminate it. Build in a verification step for anything load-bearing.
  • Cost blowup. Multi-agent routinely costs 4–15× the tokens of a single agent. Teams discover this when the bill arrives, not when they design the system. Budget the token cost before you fan out, and re-check whether a single agent suffices.
  • Coordination latency — the slowest worker bottlenecks the barrier. Your p99 latency is dominated by the one worker that hit a retry or a slow tool. Tight per-worker iteration caps, per-call timeouts, and partial-result fallbacks are not optional at scale.
  • Non-determinism compounds across agents. One non-deterministic agent is hard enough to debug; five in a tree, each making model-driven decisions, produce a different trajectory every run. Reproducing a failure becomes a research project. This is what makes observability (Module 09) non-negotiable for multi-agent systems — you need traces that span the whole tree, with every task prompt and summary captured, or you’re debugging blind.
  • Over-engineering with multi-agent when a single agent suffices. The most common architectural mistake in the whole space: reaching for orchestration because it’s impressive, when a single agent with the context management from Module 04 would do the job faster, cheaper, and more reliably. “Could one good agent do this?” should be the first question, asked seriously, every time.
  • The “LLM orchestrating LLMs freehand” anti-pattern. Giving a model a spawn_agent tool and telling it to coordinate the team itself feels elegant and is a trap: it compounds the lossy interface at every hop, makes the control flow invisible and untestable, and fails in ways you can’t reproduce. Deterministic code orchestration — model decides the decomposition, code executes the fan-out, barrier, and synthesis — is what holds up in production.

Check yourself

  • Give a one-sentence test that decides whether a given piece of your system is a workflow or an agent. (Hint: it’s about who chooses the next step.)
  • You’re handed a task: “classify incoming support emails and reply.” Which pattern(s) fit, and where — if anywhere — does a genuinely agentic leaf belong?
  • Sectioning and orchestrator-worker both fan out to parallel sub-agents. What is the one difference, and why does it put them on opposite sides of the workflow/agent line?
  • A worker reports key_findings: ["the rate limit is 600 rpm"] but sources: []. Your code is about to pass this to synthesis. What should it do, and which production issue does that guard address?
  • Your multi-agent research agent costs 12× a single agent and produces a marginally better answer on your test question. What’s your next move, and what does it tell you about the question?
  • Why is “give the model a tool to spawn and manage other agents” tempting, and why is it the wrong default? Phrase the fix as “decision in __, mechanism in __.”
