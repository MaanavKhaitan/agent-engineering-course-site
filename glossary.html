Glossary

Terms used throughout the course, defined plainly. Cross-references in bold.

Core

  • Token — the atomic unit a model reads/writes; a subword chunk (~4 chars of English) from a fixed vocabulary, produced by a tokenizer (usually byte-pair encoding). Pricing, context limits, and several model quirks are all downstream of tokenization. (Module 1)
  • Context window — the fixed-size buffer of tokens a model can attend to in one call (e.g. 200K–1M). The transcript must fit inside it. (Modules 1, 4)
  • Tokenizer — the deterministic codec mapping text ↔ integer token IDs. Frozen at training time. Use the provider’s count_tokens, never a different model’s tokenizer.
  • Temperature — sampling knob; divides logits before softmax. T=0 ≈ greedy/deterministic-ish; higher = more random/creative. (Module 1)
  • Logits / softmax — the model’s raw per-token scores (logits) turned into a probability distribution (softmax) that’s sampled from.
  • Base model — the LLM itself: a stateless function from tokens-in to tokens-out. No memory, no tools, no clock. (Module 1)

Agents

  • Agent — a base model placed in a closed loop with an environment: it picks an action, the harness executes it, the result is fed back, repeat until done. (Module 3)
  • Agent loop — the while loop at the center of every agent: call model → execute tool calls → append results → call model again, until the model stops calling tools. (Module 3)
  • Harness — everything around the model in the loop: tool implementations, the loop, context management, permissions, state, orchestration. Where most engineering lives.
  • Tool / function calling — the trained ability of a model to emit a structured request to call a named function with JSON arguments, instead of (or with) prose. The model requests; the harness executes. (Module 2)
  • Tool schema — name + description + JSON Schema for a tool’s parameters, sent to the model. The model reads the description at runtime; description quality changes behavior.
  • System prompt — the engineered prefix configuring the agent’s behavior, conventions, and environment facts; sent on every call.
  • Sub-agent — a child agent spawned with its own fresh context window and (often restricted) toolset; runs a scoped task and returns only a summary. Used as a context firewall. (Modules 4, 6)
  • MCP (Model Context Protocol) — a standard protocol for exposing tools/data to any agent harness (“USB for agent tools”). Write an integration once, use it across products. (Modules 7, 13)

Context & memory

  • Context engineering — the discipline of deciding what goes into the context window and when, to keep the agent effective and cheap. (Module 4)
  • Compaction — summarizing older transcript turns and replacing them, to stay under the context limit. (Module 4)
  • Context editing / pruning — clearing stale tool results or thinking blocks from the transcript (removed, not summarized). (Module 4)
  • Context rot — degradation of retrieval/attention quality as the transcript grows, before the hard limit is hit. (Module 4)
  • Memory (long-term) — state persisted outside the context window (files, a memory tool, a store) that survives across sessions. (Modules 4, 12)
  • Filesystem-as-memory — the pattern of having the agent write plans/findings/state to files and re-read them, instead of holding everything in context (spilling to disk under memory pressure). (Modules 4, 13)

Retrieval

  • RAG (Retrieval-Augmented Generation) — fetching relevant documents and putting them in context before the model answers. (Module 5)
  • Embedding — a vector representation of text such that similar meanings are nearby; the basis of semantic search. (Module 5)
  • Vector database — a store optimized for nearest-neighbor search over embeddings (Chroma, pgvector, etc.). (Module 5)
  • Agentic RAG — retrieval driven by the agent itself: it decides when/what to search, reads, critiques, and re-searches in a loop, rather than a single fixed retrieval step. (Module 5)
  • Chunking — splitting documents into retrievable pieces. (Module 5)
  • Reranking — a second, more precise scoring pass over retrieved candidates. (Module 5)

Orchestration

  • Workflow — a system where LLM calls and tools are orchestrated through predefined code paths. Predictable. (Module 6)
  • Agent (vs workflow) — a system where the model dynamically directs its own process and tool use. Flexible. (Module 6)
  • Orchestrator-worker — a coordinator agent that decomposes a task and delegates subtasks to worker sub-agents. (Module 6)
  • Evaluator-optimizer — one model generates, another critiques/scores, loop until good. (Module 6)
  • Routing — classifying an input and sending it to the appropriate specialized handler. (Module 6)
  • Handoff — one agent explicitly transferring control (and context) to another (OpenAI Agents SDK term). (Module 7)

Evaluation

  • Eval (evaluation) — any measurement of whether a model/agent does what you want. Usually private and bespoke to your task. (Module 8)
  • Benchmark — a standardized, shared eval used to compare models (e.g. SWE-bench). All benchmarks are evals; most evals aren’t benchmarks. (Module 8)
  • Grader — the component that scores an output: programmatic (code checks), LLM-as-judge, or human. (Module 8)
  • LLM-as-judge — using a model to score outputs against a rubric. A fallible component you must calibrate. (Module 8)
  • pass@k / pass^k — succeeds in at least one of k tries (pass@k) vs. all k tries (pass^k, the reliability metric). (Module 8)
  • Regression eval — a fixed suite run on every change to catch silent degradation; CI for agents. (Module 8)
  • Contamination — a benchmark’s questions leaking into training data, inflating scores. (Module 8)
  • Goodhart’s law — “when a measure becomes a target, it ceases to be a good measure”; overfitting to an eval set. (Module 8)

Observability & reliability

  • Trace / span — a trace is the full record of one agent run; spans are the nested steps (model calls, tool calls) within it. (Module 9)
  • LLM-as-judge online eval — sampling production traces and grading them continuously to catch drift. (Module 9)
  • Prompt caching — provider feature that caches a request’s stable prefix so repeat requests pay ~10% for the cached part. Requires an append-only, prefix-stable transcript. (Module 10)
  • Model tiering / routing — sending each subtask to the cheapest model that can handle it. (Module 10)
  • Quadratic transcript — because the whole transcript is re-sent each loop iteration, naive token cost grows ~O(n²) over a task. (Module 10)
  • Structured output / constrained decoding — forcing the model’s output to conform to a schema (e.g. JSON), validated at the boundary. (Modules 1, 10)

Security

  • Prompt injection — adversarial instructions hidden in data the agent reads (a web page, a file) that the model may follow; “the SQL injection of this stack.” (Module 11)
  • Excessive agency — giving an agent more capability/autonomy than the task needs, enlarging blast radius. (Module 11)
  • Permission engine — the policy layer between “model emitted a tool call” and “tool runs”: allowlists, gating, human confirmation. (Modules 3, 11)
  • Sandboxing — isolating tool/code execution (containers, VMs, seccomp) to limit blast radius. (Module 11)
  • Human-in-the-loop (HITL) — requiring human approval for high-risk or irreversible actions. (Modules 11, 12)
  • Guardrail — an input/output filter or check that blocks unsafe content or actions. (Module 11)

Deployment

  • Durable execution — an execution model (e.g. Temporal) that journals every step so a crashed run resumes mid-way instead of restarting. (Module 12)
  • Checkpointing — persisting agent state so a run can be paused/resumed/recovered (LangGraph checkpointer, etc.). (Module 12)
  • Long-running / persistent agent — an agent that operates over hours/days against an ongoing goal, across many context windows and sessions. (Modules 12, 13)
  • Background agent — an agent that runs asynchronously (often in the cloud), not in a live request/response. (Modules 12, 13)
  • Event-sourcing — modeling state as an append-only log of events; the natural fit for durable, resumable agents. (Module 12)

Frontier

  • Goal-directed loop / outer loop — restarting the agent against a goal repeatedly until done (vs. the inner tool loop). The “loop engineering” discourse. (Module 13)
  • Computer use — an agent controlling a GUI via screenshots + mouse/keyboard actions. (Module 13)
  • Time horizon (METR) — the length of task an agent can complete autonomously at some reliability; observed to be doubling every few months. (Module 13)
