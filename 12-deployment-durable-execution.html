Module 12 — Deployment & Durable Execution

Everything so far has assumed Scout runs in a terminal. You type a task, the loop spins, you read the answer, the process exits. That’s a fine place to learn an agent, and a terrible place to operate one. The moment an agent has to serve more than one caller, survive longer than a request timeout, or pick up tomorrow where it left off today, you’re no longer writing an agent — you’re writing a distributed system whose request handler happens to be stochastic and slow.

You already know how to operate distributed systems. The new material here is small but it’s exactly the part your intuition will misfile. An agent’s “handler” runs for minutes to hours, not milliseconds. Its “request” is a growing transcript that is the application state. Its side effects are real (it sends emails, opens PRs, deletes files), it’s non-deterministic, and any individual step can fail transiently — model rate limits, a sandbox eviction, a deploy that rolls your process. The good news: the patterns that make this tractable are ones you already trust. Statelessness. Event sourcing. Idempotency. Sagas. Replay. This module is about mapping those onto agents and then reaching for the production answer — durable execution — when run duration outgrows a single process.

Learning objectives

By the end of this module you should be able to:

  • Place a given agent workload on the script → sync API → async job → persistent agent spectrum, and pick the deployment shape its run duration demands.
  • Explain why the harness, not the model, owns all state — and externalize that state durably as an append-only event log (event sourcing applied to a stochastic handler).
  • Reason about the brain / hands / session split and why the session (the log) is the source of truth, not the process memory.
  • Survive the “discrete sessions with amnesia” problem with the initializer / worker pattern: continuity lives in files, not context.
  • Describe what a durable execution engine (Temporal; LangGraph checkpointing) buys you — journal-and-replay resumption — and the one footgun it forces you to confront (non-idempotent side effects on replay).
  • Choose between hosted (Anthropic Managed Agents) and self-hosted (your loop + Temporal/LangGraph + a sandbox vendor), and name the tradeoffs.
  • Implement checkpoint + resume for Scout, and a FastAPI service that streams its events.

📖 This module is the infrastructure. Module 13 is the persistent-agent concept — what an agent that runs for days against an ongoing goal can become. Here we build the floor it stands on.

1. From script to service: the spectrum

There is no single “deploy an agent” answer because there is no single agent. The deployment shape is dictated almost entirely by one variable: how long does a run take? That number decides whether the run can live inside an HTTP request, must move to a background worker, or must outlive the process entirely.

Shape Run duration Where it lives State concern
(a) CLI / script seconds–minutes one process, foreground in-memory; dies with the process
(b) Sync request/response API seconds–~minute inside an HTTP request in-memory per request; must stream
(c) Async background job minutes–hours queue + worker pool externalized; survives the request
(d) Long-running / persistent agent hours–days a durable workflow append-only log is the source of truth

Scout today is (a). Most of this module is about earning your way down the table.

The jump from (a) to (b) is mechanical: wrap the loop in a handler. The jump from (b) to (c) is the one that breaks naive designs — a 40-minute agent run cannot block an HTTP connection (load balancers, proxies, and clients all give up around 30–120s), so the run must detach from the request and report progress out-of-band. The jump from (c) to (d) is the one this module spends the most time on, because “the process might die in the middle and that has to be fine” is a property you have to design for, not bolt on.

A deployment shape: FastAPI wrapping Scout with streaming

Here is shape (b)/(c) for Scout: a service that accepts a task, runs the loop in the background, and streams events (via Server-Sent Events) to the client as they happen, keyed by a session_id, with an endpoint to interrupt a run mid-flight. Streaming isn’t a nicety here — a multi-minute run with no output looks identical to a hung server, and (callback to Module 1) the Anthropic API itself wants streaming for any long call so you don’t hit request timeouts.

# service.py — FastAPI front end for Scout
import asyncio, json, uuid
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()

# session_id -> live run handle. In-memory here for clarity; in production this
# is Redis or a DB so multiple service replicas can find a run (see §2).
RUNS: dict[str, "Run"] = {}

class Run:
    def __init__(self, session_id: str, task: str):
        self.session_id = session_id
        self.task = task
        self.queue: asyncio.Queue = asyncio.Queue()   # events out to the client
        self.interrupt = asyncio.Event()              # steering: stop signal in

class StartReq(BaseModel):
    task: str

@app.post("/runs")
async def start_run(req: StartReq):
    session_id = str(uuid.uuid4())
    run = Run(session_id, req.task)
    RUNS[session_id] = run
    asyncio.create_task(_drive(run))   # detach from the request
    return {"session_id": session_id}

@app.get("/runs/{session_id}/events")
async def stream_events(session_id: str):
    run = RUNS[session_id]
    async def sse():
        while True:
            event = await run.queue.get()
            yield f"data: {json.dumps(event)}\n\n"
            if event["type"] in ("done", "error", "interrupted"):
                break
    return StreamingResponse(sse(), media_type="text/event-stream")

@app.post("/runs/{session_id}/interrupt")
async def interrupt_run(session_id: str):
    RUNS[session_id].interrupt.set()    # the loop checks this each iteration
    return {"ok": True}

async def _drive(run: Run):
    try:
        # scout_loop is an async generator that yields events and checks
        # run.interrupt at the top of each iteration (see below).
        async for event in scout_loop(run.task, interrupt=run.interrupt):
            await run.queue.put(event)
        await run.queue.put({"type": "done"})
    except asyncio.CancelledError:
        await run.queue.put({"type": "interrupted"})
    except Exception as e:
        await run.queue.put({"type": "error", "message": str(e)})

The Module 3 loop becomes an async generator that emits an event per meaningful step and honors the interrupt flag:

# scout_async.py — the loop, instrumented to stream and to be steerable
import anthropic
async_client = anthropic.AsyncAnthropic()

async def scout_loop(task: str, interrupt):
    messages = [{"role": "user", "content": task}]
    system = build_system_prompt()
    for step in range(MAX_ITERS):
        if interrupt.is_set():
            return                                   # steering: bail cleanly
        async with async_client.messages.stream(
            model="claude-opus-4-8", max_tokens=4096,
            system=system, tools=[t.to_schema() for t in TOOLS],
            messages=messages,
        ) as stream:
            async for text in stream.text_stream:
                yield {"type": "token", "text": text}     # live tokens to the UI
            resp = await stream.get_final_message()
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            yield {"type": "final",
                   "text": "".join(b.text for b in resp.content if b.type == "text")}
            return
        results = [dispatch(b) for b in resp.content if b.type == "tool_use"]
        for b in resp.content:
            if b.type == "tool_use":
                yield {"type": "tool_use", "name": b.name, "input": b.input}
        messages.append({"role": "user", "content": results})

This service is real, and for short interactive runs it’s enough. But notice what’s load-bearing and fragile: messages lives in process memory. If this worker is OOM-killed at step 30 of a 50-step task, the run is gone. There is no resume. That single fact is what the rest of the module is about.

✅ Checkpoint: You can run Scout behind an HTTP API that streams tokens and tool-use events to a client, with a session id and an interrupt endpoint. You have not yet made a run survive the process dying.

2. State is the central problem

Lean on your intuition here, because it’s exactly right: the model is a stateless function. Every messages.create call is pure — same inputs, (roughly) same output distribution; the API server remembers nothing about your previous call (Module 1). All the state that makes an agent an agent — the transcript, the working directory, scratch memory, open tool sessions — lives in the harness, the code you wrote around the model.

That has a sharp consequence. For a single request, in-memory state is fine; the request and the state are born and die together. For anything that must outlive a single request — a job that runs across a deploy, an agent that resumes tomorrow — you must externalize the state durably. This is not an agent-specific insight. It’s the same move that took web tiers from sticky-session stateful boxes to stateless app servers backed by a database. The app server can die and be replaced; the session lives in Postgres. We are going to do exactly that to Scout: make the worker disposable and move the run into durable storage.

The brain / hands / session split

The convergent architecture for serious long-running agents (Anthropic’s framing, and most practitioners’) decomposes the harness into three parts with very different durability requirements:

        ┌─────────────────────────────────────────────────────────┐
        │  BRAIN  — model + loop (stateless, restartable)          │
        │  decides the next action from the current log            │
        └───────────────┬──────────────────────────┬──────────────┘
                        │ tool calls               │ append events
                        ▼                          ▼
        ┌──────────────────────────┐   ┌──────────────────────────┐
        │  HANDS — ephemeral        │   │  SESSION — append-only    │
        │  sandboxed execution      │   │  EVENT LOG                │
        │  (Module 11): bash, files │   │  the durable source       │
        │  disposable, rebuildable  │   │  of truth                 │
        └──────────────────────────┘   └──────────────────────────┘
  • Brain — the model plus your loop. Stateless and restartable. Given the current log, it produces the next action. If the process dies, you spin up a new brain and hand it the same log.
  • Hands — the ephemeral, sandboxed place where tool calls actually run (Module 11’s territory: a container, a microVM). Disposable by design. Its contents are derived state — anything important the hands produce gets recorded in the session.
  • Session — an append-only event log that is the single durable source of truth. Every user message, model response, tool call, and tool result is an immutable entry. Recovery means: rebuild a brain, replay/reload the log, continue.

If “append-only log that is the source of truth, from which you reconstruct current state” sounds familiar, it should: this is event sourcing, applied to a handler that happens to be a language model. Name the analogy and the rest follows. The transcript isn’t a convenience buffer you keep around for the model’s benefit — it’s the event store. Current state (the messages array, the cursor into the task) is a projection you fold from the log. And the log gives you the two things event sourcing always gives you: recovery (replay to reconstruct) and audit (a complete, immutable record of exactly what the agent did and why — which, for an autonomous system taking real actions, you will be very glad to have).

📖 The bridge from Module 4: there we treated files as memory to fit a task into a finite context window. Here the same idea does double duty — files and the event log are how state survives a process boundary, not just a context boundary. Files-as-memory is the thing that makes durability possible. Hold that thought; §3 leans on it hard.

3. Discrete sessions with amnesia

Here is the reality that trips up everyone coming from request/response systems. A long-running agent does not run in one continuous, ever-growing context. It runs as a sequence of discrete sessions, each bounded by a context window and, often, a process lifetime. A multi-day task is not one 9,000,000-token conversation. It’s hundreds of sessions, each of which starts with no memory of the last. The agent has amnesia at every session boundary. (Module 13 will treat this as a feature to design around; here it’s the constraint that forces our hand.)

So where does continuity live? Not in context — context is reset every session. It has to live in files and durable state the next session can read. This is the §2 bridge made concrete: the stateless-web-tier-plus-database pattern, one layer down. Each session is a stateless worker; the filesystem and event log are the database; a fresh session rehydrates from disk and carries on.

Anthropic’s pattern for this is a clean two-role split:

  • The initializer agent runs once, on first start. It sets up the environment and writes the durable artifacts the workers will depend on: a PLAN.md (the goal, broken into steps), an empty progress.log, any scaffolding (a repo cloned, a venv built, fixtures fetched). It is the constructor.
  • The worker agent runs every subsequent session. It does the same four things every time: (1) read PLAN.md and progress.log to figure out where things stand, (2) do the next increment of work, (3) record what it did and learned by appending to progress.log and updating state files, (4) leave clear artifacts so its successor — which shares none of its context — can pick up cleanly. It is the request handler, and it’s stateless.
session 1 (initializer):  write PLAN.md, init progress.log, scaffold env
session 2 (worker):       read PLAN+progress → do step 1 → append progress, commit
session 3 (worker):       read PLAN+progress → do step 2 → append progress, commit
   …                      (each session amnesiac; continuity is on disk)
session N (worker):       read PLAN+progress → all steps done → write RESULT.md

The discipline this imposes on prompts and tools is the real work. The worker’s system prompt must insist on the read-first / record-last ritual, because a worker that forgets to write its progress has, from its successor’s point of view, done nothing — the next session will redo it. The artifacts must be written for a reader with no shared context: “fixed the bug” is useless; “step 3 (parser): fixed off-by-one in tokenize(), line 88; tests green; next: step 4, wire up the CLI flag” is a handoff. You are, in effect, writing the agent’s commit messages for it to read.

📖 This is the conceptual core that Module 13 builds the persistent-agent vision on top of. The infrastructure point for this module: continuity is a file/state design problem, not a context-window problem. No bigger context window makes the amnesia go away — only durable artifacts do.

4. Durable execution: the production answer to long-running reliability

Now the hard part. You have a 3-hour agentic run. It fails at step 47 of 60 — a rate-limit storm, a transient sandbox eviction, a deploy that rolled the worker out from under it. It must not restart from step 1. Re-running 46 expensive, slow, side-effecting steps to get back to where you were is unacceptable on cost, on latency, and (if those steps had side effects) on correctness. Crash recovery for a multi-hour stochastic process is the problem durable execution exists to solve.

The mechanism will be deeply familiar, because it’s a write-ahead log plus replay — the same primitive under every database’s crash recovery. A durable execution engine journals every step as an immutable event to durable storage as it happens. On failure, it doesn’t restart your workflow; it replays the event history, feeding each already-completed step its recorded result instead of re-executing it, until it reaches the step that hadn’t finished — and resumes there. The 46 completed steps are not re-run; their results are replayed from the journal in milliseconds. This is your saga / workflow-engine intuition, applied to an agent loop.

Temporal — the canonical engine

Temporal is the engine most serious long-running agents use; OpenAI runs it for Codex, and Replit, Lovable, and others build on it. (It raised $300M at a $5B valuation in early 2026, which tells you how central durable execution has become to this space.) The OpenAI Agents SDK ships a GA Temporal integration.

Temporal’s model is “workflow as code.” You write your orchestration as ordinary code; Temporal makes it durable by recording every step’s result to an event history and replaying that history to reconstruct state after any failure. Two concepts:

  • Workflow — your orchestration logic. It must be deterministic, because Temporal re-executes it during replay and the re-execution must follow the exact same path. So a workflow may not do I/O, call time.now(), or hit the network directly. (Sound restrictive? It’s the same constraint as a pure reducer folding an event log — and for the same reason.)
  • Activity — a unit of non-deterministic, side-effecting work: a model call, a tool call, anything that touches the outside world. Temporal records each activity’s result in the history. On replay, completed activities are not re-run — their recorded result is handed back.

The mapping onto an agent is direct: the model call is an activity; each tool call is an activity; the loop that strings them together is the workflow. A tiny conceptual sketch (Temporal Python, illustrative):

from temporalio import workflow, activity

@activity.defn
async def model_step(messages: list) -> dict:
    # The one non-deterministic thing in the loop. Its result is journaled.
    resp = await async_client.messages.create(
        model="claude-opus-4-8", max_tokens=4096,
        system=SYSTEM, tools=TOOL_SCHEMAS, messages=messages)
    return resp.model_dump()

@activity.defn
async def run_tool(name: str, args: dict) -> str:
    return dispatch_tool(name, args)        # side effects happen HERE, journaled

@workflow.defn
class ScoutWorkflow:
    @workflow.run
    async def run(self, task: str) -> str:
        messages = [{"role": "user", "content": task}]
        for _ in range(MAX_ITERS):
            resp = await workflow.execute_activity(
                model_step, messages, start_to_close_timeout=TIMEOUT)
            messages.append({"role": "assistant", "content": resp["content"]})
            tool_uses = [b for b in resp["content"] if b["type"] == "tool_use"]
            if not tool_uses:
                return final_text(resp)
            results = []
            for tu in tool_uses:
                out = await workflow.execute_activity(
                    run_tool, tu["name"], tu["input"], start_to_close_timeout=TIMEOUT)
                results.append(tool_result(tu["id"], out))
            messages.append({"role": "user", "content": results})

Crash at iteration 47? Temporal spins up a fresh worker, replays the history (46 model_step and their run_tool results come back instantly from the journal, no API calls, no re-execution), and the loop continues at iteration 47 as if nothing happened. You wrote a for loop; you got crash-proof resumption. That is the whole pitch.

LangGraph checkpointing — the lighter-weight, in-framework alternative

If you’re already in LangGraph (Module 7), you don’t need a separate engine for a large class of cases. LangGraph models the agent as a state graph and offers a checkpointer that persists the graph’s state after every node transition to a backing store (in-memory, SQLite, Postgres). Attach one and you get:

  • Resume — pass the same thread_id and the graph rehydrates from its last checkpoint and continues from the node it stopped at.
  • Time-travel — load any prior checkpoint and branch a new run from it. Invaluable for debugging a long agent (“re-run from the state right before it deleted the file”) and for human steering.
from langgraph.checkpoint.sqlite import SqliteSaver
graph = build_scout_graph().compile(checkpointer=SqliteSaver.from_conn_string("scout.db"))
cfg = {"configurable": {"thread_id": session_id}}
graph.invoke({"task": task}, cfg)     # crash, then re-invoke with the same thread_id → resumes

LangGraph Platform packages this for deployment (managed runs, persistence, a streaming API). The tradeoff vs Temporal: LangGraph’s checkpointing is lighter to adopt and tightly integrated with the graph model, but it’s checkpoint-of-state, not journal-and-replay of every step; for very long, very high-stakes orchestration with complex retry/timeout/compensation needs, Temporal’s model is more battle-tested. Inngest and Restate occupy similar ground — durable functions/workflows with journaling — and are worth a look if you want durable execution without adopting the full Temporal operational footprint.

✅ The shape to remember: journal every step → on failure, replay the journal to skip completed work → resume at the failure. It’s a saga with a write-ahead log. Whatever engine you pick, that’s what you’re buying.

5. Human-in-the-loop, at the infrastructure level

Module 11 made the case for human approval on dangerous actions. Durable execution makes implementing it natural, because pausing-and-waiting is just another kind of “this step isn’t done yet.” An agent that needs an approval can suspend, persist its entire state, and resume when a human responds — and crucially, it can wait for hours or days without holding a process, a thread, or a connection open. The waiting state lives in the journal, not in memory.

In Temporal this is a workflow that blocks on a signal: the workflow reaches an approval step, parks (durably — you could deploy through the wait and it survives), and resumes the instant a POST /approve delivers the signal. In LangGraph it’s an interrupt before a node: the graph checkpoints, returns control, and resumes on the next invoke with the human’s decision. Either way, escalation/approval becomes a first-class durable step, not a hack with a polling loop and a sleep. The agent that asks “may I delete this production table?” and waits a day for a human to say yes — without burning a single token or process while it waits — is a direct payoff of durable execution.

6. Hosted vs self-hosted

You now have two ways to run a durable, long-lived agent in production.

Self-host the whole thing. Your loop, your durable execution engine (Temporal / LangGraph / Inngest / Restate), and a sandbox vendor for the hands — E2B, Modal, Daytona, or raw Firecracker microVMs (Module 11). Maximum control, maximum ops burden: you operate the workflow engine, the worker pool, the sandbox fleet, the autoscaling, the upgrades. This is the right call when you need deep control over the loop, custom tools, specific compliance/residency, or you’re running at a scale where margins matter.

Use Anthropic Managed Agents. Anthropic runs the loop and hosts a per-session sandbox container for you. The flow (verified, from Module-1’s API surface) is: create an Agent once (model, system prompt, tools — a persisted, versioned config) → create a Session per run → stream events back over SSE while you send messages and tool results in. Anthropic runs the brain loop and provisions the hands (the per-session container) on its infrastructure. It supports scheduled deployments (run an agent on a cron cadence — the platform’s answer to “run this every night”), and self-hosted sandboxes are an option if you want the loop hosted but the hands on your own infra. You own state in the sense that matters — the API is stateless and the session log is yours — but you don’t run the orchestration.

The tradeoff is the usual hosted-vs-self-hosted axis, sharpened by how new and fast-moving this layer is:

  Self-hosted (loop + Temporal/LangGraph + sandbox vendor) Hosted (Managed Agents)
Control over loop/tools total bounded by the platform
Ops burden you run engine + sandbox fleet Anthropic runs it
Lock-in low (portable workflow code) higher (platform-shaped)
Time to production slower fast (create agent → session)
Best when deep control, scale, custom infra speed, less ops, standard shapes

Neither is “correct.” A team shipping a standard coding-assistant flow should probably start hosted and not build a Temporal cluster. A team whose agent is the product, running at scale with bespoke tools, will likely self-host. Most importantly: the concepts — brain/hands/session, the event log, journal-and-replay, idempotent side effects — are identical across both. Pick the operations model; the engineering doesn’t change.

7. Operational concerns

Durability fixes “the process died.” It surfaces a set of problems that didn’t exist when runs were ephemeral.

Idempotency of side effects across replays — the one that bites everyone. This is the single most important paragraph in the module. Replay re-drives your workflow code, and replaying a step that already ran must not run its side effect again. If run_tool("send_email", …) succeeded and was journaled, but a crash happened before the workflow recorded the next step, recovery will pass back the recorded result — good. But if you wrote a side effect in the deterministic workflow body instead of inside an activity, replay will execute it again — and your customer gets the email twice. The rule: all side effects go inside journaled activities (or are otherwise made idempotent), never in the replayed workflow body. And belt-and-suspenders: make the effect itself idempotent with a key, so even a duplicated delivery is a no-op. A non-idempotent side effect re-firing on replay is the canonical durable-execution footgun (more in §Real production issues).

Observability of long runs (Module 9). A multi-hour run that you can’t see inside of is a multi-hour outage waiting to happen. The event log is your friend here — it’s already a structured, append-only trace. Emit spans per step, surface per-run cost and progress, and make “where is run X right now and what has it done” a one-query answer.

Cost over long runs (Module 10). An agent with no budget and no timeout is a way to spend money in your sleep. Every long-running agent needs a hard token budget and a wall-clock timeout, enforced by the harness — a runaway or looping agent burning tokens unattended at 3 a.m. is a real and expensive failure mode. Cap iterations, cap dollars, cap time.

Versioning while runs are in flight. You deploy a new system prompt. Runs started yesterday are mid-flight on the old prompt, their journals full of the old behavior. Changing the prompt under a replaying workflow can break determinism outright. Durable engines have explicit answers (Temporal’s workflow versioning / patching; pinning a run to an agent version, exactly as Managed Agents does). The point: an in-flight run is bound to the agent version it started under. Plan for old runs draining on old configs.

Graceful shutdown and resume across deploys. Because state is in the journal, a deploy is no longer a catastrophe — drain workers, let the engine reschedule in-flight runs onto fresh workers, resume from the journal. This is the payoff for all the discipline above: deploys, scale-downs, and spot-instance evictions stop being incidents and become routine. That’s the whole reason you externalized the state.

🛠️ Exercise: Deploy & durabilize Scout

Goal: an agent that survives a crash and resumes. You’ll wrap Scout in a service, give it a durable event log keyed by session, prove resumption by killing the process mid-run, implement the initializer/worker pattern, and make one tool side effect idempotent.

(a) Wrap Scout in a streaming FastAPI service

Stand up the service from §1: POST /runs starts a run (detached from the request) and returns a session_id; GET /runs/{session_id}/events streams events as SSE; POST /runs/{session_id}/interrupt sets the steering flag the loop checks each iteration. Convert Scout’s loop to the async generator shown in §1 so it yields token / tool_use / final events. Test: start a run in one terminal, curl -N the events endpoint in another, and confirm you see tokens and tool-use events stream in, and that hitting interrupt stops the run cleanly.

(b) Make Scout’s state durable: checkpoint + resume

This is the heart of the exercise. Give Scout an append-only event log on disk, keyed by session_id, written after each step, so a restarted process can reload it and continue.

# checkpoint.py — the session log is the source of truth (event sourcing)
import json, os
def log_path(session_id): return f"sessions/{session_id}.jsonl"

def append_event(session_id, event: dict):
    os.makedirs("sessions", exist_ok=True)
    with open(log_path(session_id), "a") as f:
        f.write(json.dumps(event) + "\n")
        f.flush(); os.fsync(f.fileno())          # durable before we proceed

def load_messages(session_id) -> list:
    """Fold the event log back into a messages array (a projection)."""
    if not os.path.exists(log_path(session_id)): return []
    messages = []
    for line in open(log_path(session_id)):
        ev = json.loads(line)
        if ev["type"] == "user":      messages.append({"role": "user", "content": ev["content"]})
        elif ev["type"] == "assistant": messages.append({"role": "assistant", "content": ev["content"]})
        elif ev["type"] == "tool_results": messages.append({"role": "user", "content": ev["content"]})
    return messages

Now make Scout’s loop resumable: on start, load_messages(session_id); if it’s empty, this is a fresh run, so append the user task; otherwise it’s a resume, so continue from the rebuilt messages. After every model response and every batch of tool results, append_event before doing anything else. The invariant: the on-disk log always reflects completed steps, so a reload never loses or duplicates a step.

def run_resumable(session_id: str, task: str | None):
    messages = load_messages(session_id)
    if not messages:                                   # fresh run
        append_event(session_id, {"type": "user", "content": task})
        messages = load_messages(session_id)
    while len(messages) < MAX_ITERS * 2:
        resp = client.messages.create(model=MODEL, max_tokens=4096,
            system=build_system_prompt(), tools=TOOL_SCHEMAS, messages=messages)
        append_event(session_id, {"type": "assistant", "content": serialize(resp.content)})
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return final_text(resp)
        results = [dispatch(b) for b in resp.content if b.type == "tool_use"]
        append_event(session_id, {"type": "tool_results", "content": results})
        messages.append({"role": "user", "content": results})

Test the resume — this is the point of the whole module. Start a multi-step task (the “fix the bug in buggy.py” task from Module 3 works; pad it so it takes several steps). Kill the process with Ctrl-C (or kill -9) partway through. Then re-run with the same session_id and no task. Scout should reload the log, skip the work it already did, and finish from where it stopped. Verify by diffing the event logs of an uninterrupted run and a killed-and-resumed run: same final state, no duplicated steps.

(c) Implement the initializer / worker pattern

Split a longer task across multiple “sessions.” Write an initializer that runs once and produces PLAN.md (the task as an ordered checklist) and an empty progress.log. Write a worker session whose system prompt requires it to: read PLAN.md + progress.log, do exactly one unchecked step, append a clear handoff line to progress.log, and stop. Run the worker repeatedly (each invocation a fresh process — the amnesia is real) until PLAN.md is fully checked off. The deliverable: a task completed across N amnesiac sessions where the only thing carried between them is on disk.

(d) Make one tool side effect idempotent

Pick a side-effecting tool (write_file is fine; a mock send_notification is better because the double-fire is visible). Give the operation an idempotency key — for write_file, the target path + a content hash; for send_notification, a caller-supplied idempotency_key. Keep a small on-disk set of keys already executed. On invocation, if the key is present, return the recorded result without re-executing. Then simulate a replay: feed the same tool call twice and prove the effect happens once. This is the §7 footgun, defused.

(e) Stretch: sketch it as a durable workflow

Take your resumable loop from (b) and rewrite it as either a Temporal workflow (model call and each tool call as activities, per §4) or a LangGraph graph with a checkpointer. You don’t need to run a Temporal cluster — a faithful sketch is enough. Then write one paragraph answering: what did the durable execution engine give me for free that I hand-rolled in (b)? (Answers should include: journaling and replay you didn’t write, retry/timeout/backoff per activity, the suspend-for-human-approval primitive from §5, versioning of in-flight runs, and graceful resume across deploys.)

Real production issues

  • Runs lost to crashes, rate-limit storms, and deploys — for want of durability. The default failure mode of the §1 service: a worker dies at step 30 and the run is simply gone, with no resume. A deploy mid-run, a 529 storm, a spot eviction — all total losses. Durability (§2–4) is the fix, and the reason it’s not optional at scale.
  • Non-idempotent side effects double-firing on replay — the #1 durable-execution footgun. A step sends an email, the workflow crashes before recording it, replay sends the email again. Or a side effect written in the replayed workflow body instead of a journaled activity fires on every replay. This is the bug that turns “durable execution saved us” into “durable execution emailed every customer three times.” Side effects go in activities; effects get idempotency keys (Exercise (d)).
  • State drift across sessions: the successor misreads stale artifacts. A worker writes an ambiguous or out-of-date progress.log line; the next amnesiac session reads it, misjudges where things stand, and redoes or skips work. The fix is discipline in how artifacts are written (write for a reader with zero shared context) plus treating the log as append-only truth, not a mutable scratchpad.
  • Hung / runaway background agents burning tokens unattended. An agent with no timeout and no budget loops at 3 a.m. and bills you for it (Module 10). Every background run needs a hard token budget, a wall-clock cap, and an iteration cap, enforced by the harness — and an alert when it trips them.
  • Versioning an agent mid-flight: in-flight runs on old prompts. You ship a new system prompt; runs started before the deploy are mid-journal on the old behavior, and replaying them under the new prompt breaks determinism or changes the agent’s mind mid-task. Pin runs to the agent version they began on; let old runs drain.
  • The hosted-vs-self-hosted lock-in / control tradeoff. Hosted (Managed Agents) gets you to production fast and off the ops treadmill, at the cost of control and some platform lock-in. Self-hosting (Temporal/LangGraph + a sandbox vendor) gives you total control and portability, at the cost of running the whole stack. The concepts port across both — choose on operations, not architecture.
  • Sandbox provisioning cost and latency at scale (the hands layer). A per-session container that takes seconds to provision and costs money to keep warm is fine for one agent and a real bill for ten thousand. The hands layer (E2B/Modal/Daytona/Firecracker) is where long-running-agent infra cost and cold-start latency actually live — pool, pre-warm, and cap aggressively.
  • Observability of multi-hour runs. You cannot debug what you cannot see. Lean on the event log as a native trace, emit per-step spans and per-run cost/progress (Module 9), and make “where is this run and what has it done” answerable without grepping logs.
  • “Discrete sessions with amnesia” means continuity is a file/state design problem. The deepest one. No context window is big enough to make a multi-day agent into one conversation; continuity must live in durable artifacts that an amnesiac successor can read. If you design the agent assuming a continuous memory it doesn’t have, it will silently forget across every session boundary.
